1Backup & Recovery / 1 — Backup / 1

Introduction

  • Earlier topics: transactions (ACID), serializability, deadlocks.
  • Failures can still occur → backup & recovery is essential.
  • Goal: restore the database to a consistent state after failure.

Key definitions

  • Backup: a copy of the database (data + control files)
  • Recovery: the process of restoring the database after a failure

Why backup is important

  • Disaster recovery: handles system crashes, hardware failure
  • Business changes: roll back to older versions
  • Auditing & legal needs: maintain historical data
  • Minimise downtime: keep systems running smoothly

What data should be backed up?

  • Business data: customers, sales, inventory
  • System data: config files, logs, software setup
  • Media data: images, videos, large files

Physical vs logical backup

  • Physical backup: a copy of the actual files (data + logs); fast to restore.
  • Logical backup: an export of tables, views, procedures; more flexible, smaller in size.

Backup strategies

  • Full backup: entire database copy — easy recovery, but time-consuming and needs large storage.
  • Incremental backup: only changes since the last backup — saves time & space, but recovery is complex and needs all previous backups.
  • Differential backup: changes since the last full backup — faster recovery than incremental, but size grows over time.

Cold vs hot backup

  • Cold backup: database is offline — simple and safe, but the system is unavailable.
  • Hot backup: database is running, uses transaction logs — no downtime (24/7 systems), but complex, costly and error-sensitive.
Key insight
  • Full = simple but heavy
  • Incremental = efficient but risky
  • Differential = balance between both
  • Hot backup = availability priority
  • Cold backup = safety priority

2Backup & Recovery / 2 — Recovery / 1

Types of failures

  • Transaction failure — causes: logical errors (bugs in code), system issues (e.g. deadlock rollback). Only the specific transaction fails, not the entire system.
  • System crash — causes: power failure, OS crash. Assumption: disk (non-volatile storage) is safe; only main-memory data is lost.
  • Disk failure — causes: hardware damage (e.g. head crash). Results in data loss on disk; detected using checksums.

Storage types

  • Volatile storage — example: RAM, cache. Data lost on crash.
  • Non-volatile storage — example: disk, flash. Data survives a crash.
  • Stable storage (ideal concept) — never loses data; practically achieved by multiple copies stored in different locations.

Stable storage implementation

Writing strategy

  • Write to Block 1 → then Block 2.
  • Output is complete only if both succeed.

Handling errors

  • Use checksums.
  • One copy corrupt → replace with the correct one.
  • Both correct but different → the first copy overwrites the second.

Optimisation

  • Track in-progress writes.
  • Avoid full disk comparisons (faster recovery).

Data access protocol

  • Transactions do not directly access disk.
  • System buffer → main memory (shared); local buffer → private to each transaction.
  • Read: system buffer → local buffer
  • Write: local buffer → system buffer
  • Output: system buffer → disk

Log-based recovery

Log: a record of all database changes (audit trail).

Log format:

<Ti start>         → transaction begins
<Ti, X, V1, V2>     → X changed from V1 to V2
<Ti commit>         → transaction completed
  • Immediate modification: changes can be written before commit; the log must be written first (write-ahead logging).
  • Commit point: a transaction commits only when <Ti commit> is saved to stable storage and all previous logs are also saved.

Undo & redo operations

  • Undo: restores the old value (V1); used for uncommitted transactions.
  • Redo: applies the new value (V2); used for committed transactions.
  • Compensation log: records undo actions; helps maintain consistency.

Checkpoints

Why needed: full log scanning is slow.

Checkpoint steps:

  1. Pause transactions.
  2. Save all logs to stable storage.
  3. Save all modified buffers to disk.
  4. Write <checkpoint L> (L = list of active transactions).

Recovery using checkpoint:

  • Ignore: transactions committed before the checkpoint
  • Redo: transactions committed after the checkpoint
  • Undo: transactions active during the crash
Quick memory trick:
  • Undo → uncommitted
  • Redo → reliable (committed)
  • Checkpoint → shortcut for recovery

3Backup & Recovery / 3 — Recovery / 2

Purpose & storage types

Why backup & recovery? Ensures atomicity, consistency and durability (ACID), and protects against system crashes, power failures and disk failures.

Storage types used:

  • Volatile → lost on crash (RAM)
  • Non-volatile → survives crash (disk, flash)
  • Stable storage → ideal (multiple copies)
  • Cold backup: periodic full/differential/incremental backup, stored on slower media (disk/tape); a snapshot of the database.
  • Hot backup: real-time backup of transaction logs, stored on fast storage; captures changes between cold backups.

Transactional logging

Why logging?

  • Full database backup in real time is expensive.
  • Solution → log every operation.

Log contents

  • Read/write operations
  • Updates to: data, indexes (e.g. B+ trees), free space
Key rule — write-ahead logging (WAL): the log is written before the actual database update.

Advantages: logs are smaller, faster, and efficient for recovery.

Recovery vs restoration

  • Recovery: fetch the last backup and the transaction logs.
  • Restoration: reapply logs to the database, bringing the DB to a consistent state.
  • Important: systems usually replay full logs, not selective updates.

Concurrent transactions & buffers

  • Rule for consistency: if transaction Ti modifies data, no other transaction can modify it until commit or abort.
  • Buffer structure: local buffer → private (per transaction); system buffer → shared memory; disk → permanent storage.
  • Flow: the transaction works on the local buffer while the system handles disk I/O separately.

Checkpointing

Why needed: logs grow very large → recovery becomes slow.

Checkpoint process:

  1. Pause the system briefly.
  2. Save all updates to disk.
  3. Mark the checkpoint.
Transaction categories
TransactionStatusAction
TaCommitted before checkpointIgnore
Tb, TcCommitted after checkpointRedo
TdNot committedUndo

Redo & undo phases

  • Redo phase (forward scan): reapply all updates after the checkpoint, including committed, uncommitted and aborted.
  • Undo phase (backward scan): reverse incomplete transactions and restore old values.
  • Compensation log records (CLR): written during undo; track rollback actions.
Key insight: always redo first, then undo — first reach the exact crash state, then fix inconsistencies.
Quick memory tricks:
  • WAL → write log first
  • Redo → repeat changes
  • Undo → uncommitted remove
  • Checkpoint → recovery shortcut

One-line summary

Backup saves data, logging tracks changes, checkpoints speed up recovery, and undo/redo ensure consistency.

4Backup & Recovery / 4 — Recovery / 3

Introduction

  • Real systems deal with physical storage: disks, files, indexes.
  • Operations go beyond simple read/write → include complex structures like B+ trees.
  • Requires advanced concurrency control and recovery mechanisms.

Recovery with early lock release

Concept: locks are released before a transaction commits → improves performance and concurrency.

Problem: multiple transactions can modify the same data structure before commit.

T1 inserts → node splits T2 inserts before T1 commits → structure changes Physical undo fails: restoring the old node state removes T2's valid changes → inconsistent database

Logical undo operations

Solution: logical undo instead of physical undo — reverse the operation rather than restoring the old state.

  • Insert → undo by delete
  • Delete → undo by insert

Used for: index structures (B+ trees) and system-level structures (free space tracking, block management).

Logging for logical operations

Logging steps:

  • Operation begin → <Oi start> for transaction Ti
  • During execution → physical logs (old/new values)
  • Operation end → <Oi end, U> where U = logical undo operation

Redo vs undo:

  • Redo → physical (simpler, safe)
  • Undo → logical (avoids conflicts from early lock release)

Handling rollbacks & crashes

  • Case 1 — crash before operation end: no <Oi end> found → use physical undo.
  • Case 2 — crash after operation end: <Oi end> exists → use logical undo (U), ignore physical undo.

Rollback process:

  1. Scan the log backward.
  2. If <Oi end> found → perform logical undo, log it, write <Oi abort>.
  3. Skip to <Oi start>.
  4. Finish with <Ti abort>.

Backup & recovery planning

Key factors:

  1. Data importance → critical vs non-critical
  2. Frequency of change → frequent vs rare updates
  3. Recovery speed → downtime tolerance vs cost
  4. Cost & resources → hardware, software, skilled staff
  5. Storage strategy → on-site vs off-site backups, number of copies
Key takeaways
  • Early lock release → better performance but more complex recovery
  • Physical undo fails in shared structures
  • Logical undo = safest solution
  • Redo is always physical
  • Checkpoints + logs = efficient recovery

One-line summary

Modern recovery uses logical undo and physical redo to handle concurrency safely while maintaining performance.

5Backup & Recovery / 5 — Backup / 2

Introduction to RAID

Definition: RAID = Redundant Array of Independent Disks. It combines multiple physical disks so they act as one logical disk.

Purpose:

  • High capacity → store large data
  • High speed → parallel data access
  • High reliability → data recovery even if a disk fails
Important insight: more disks → higher chance of failure. RAID ensures no data loss using redundancy.

Core RAID techniques

  • Mirroring (shadowing): duplicate data on multiple disks — fast reads, but double the storage required.
  • Striping: splits data across disks — bit-level, byte-level, or block-level (most used); improves speed via parallel access.
  • Parity: uses extra data (via XOR) for error recovery — less storage than mirroring, and can recover from disk failure.

RAID levels

  • RAID 0 (striping): high speed & full storage use, no fault tolerance.
  • RAID 1 (mirroring): high reliability, 50% storage efficiency.
  • RAID 2: bit-level striping + Hamming code, rarely used.
  • RAID 3: byte-level striping + 1 parity disk.
  • RAID 4: block-level striping + 1 parity disk; parity disk bottleneck.
  • RAID 5 (most popular): block-level + distributed parity — good performance + reliability, handles 1 disk failure.
  • RAID 6: dual parity — handles 2 disk failures, slightly slower writes.

Hybrid RAID (nested RAID)

  • RAID 01 (mirror of stripes): RAID 1 over RAID 0
  • RAID 10 (stripe of mirrors): RAID 0 over RAID 1 — very fast + reliable, widely used in databases
RAID comparison
RAIDBenefitUse case
0SpeedTemporary data
1SafetyOS, transactions
5BalanceWeb servers
6High safetyArchives
10Speed + safetyDatabases

Limitations of RAID

  • Not a backup: cannot protect from fire, theft, human error, malware.
  • No 100% uptime: failures can still occur.
  • Low flexibility: hard to expand, often requires a full rebuild.
Quick memory tricks:
  • RAID 0 → 0 safety
  • RAID 1 → 1 copy extra
  • RAID 5 → 1 disk failure
  • RAID 6 → 2 disk failure
  • RAID 10 → best combo

One-line summary

RAID improves speed, capacity, and reliability using striping, mirroring, and parity — but it is not a replacement for backup.
