Lecture 1: Relational Database Design / 6 — Normal Forms

What is Normalization?

Normalization is the process of organizing data in a database to remove redundancy (duplicate data), ensure proper data relationships, and improve data integrity.

Simple Idea "Store data once, use it everywhere correctly."

Why Normalization? (Goals)

Main Objectives:

  • Eliminate data redundancy
  • Avoid data anomalies
  • Maintain data consistency

Types of Anomalies

Anomaly TypeMeaningExample
InsertionCannot insert data without other dataCannot add a student without course
DeletionDeleting one data removes useful infoDeleting last student removes course info
UpdateSame data must be updated in multiple placesChanging teacher name everywhere

Important Properties of Decomposition

When breaking a table into smaller tables, we must ensure:

1. Lossless Join After decomposition, we should be able to reconstruct the original table.
Example: Student(ID, Course, Teacher) → Student(ID, Course) + Course(Course, Teacher)
Joining them gives the original table ✔️
2. Dependency Preservation All functional dependencies should be maintained without JOIN. Meaning: we should not need to combine tables just to check constraints.

First Normal Form (1NF)

Rule: All values must be atomic (single value); no multi-valued attributes.

Not in 1NF: Student(ID, Subjects)
101{Math, Science}
In 1NF: Student(ID, Subject)
101Math
101Science

Second Normal Form (2NF)

Rule: Must be in 1NF; no partial dependency.

Key Concepts:

  • Prime Attribute → Part of candidate key
  • Non-prime Attribute → Not part of key
Problem — Partial Dependency Student(ID, Course, Teacher), Key = (ID, Course).
Teacher depends only on Course ❌

Solution — Split table:

  • Student(ID, Course)
  • Course(Course, Teacher)

Third Normal Form (3NF)

Rule: Must be in 2NF; no transitive dependency.

Transitive Dependency If A → B and B → C, then A → C.
Example Student(ID, Dept, HOD)
ID → Dept, Dept → HOD, so ID → HOD (transitive).

Solution:

  • Student(ID, Dept)
  • Department(Dept, HOD)
Formal Rule For every dependency X → A: either X is a superkey, or A is a prime attribute.

Why 3NF is Important?

Advantages: Removes most redundancy; prevents anomalies; easy to implement.

Maintains: Lossless join; dependency preservation.

That's why 3NF is widely used in real-world databases.

Higher Normal Forms (Brief)

Mostly, 3NF is enough in practice.

Normal FormFocus
BCNFStronger version of 3NF
4NFMulti-valued dependencies
5NFComplex join dependencies
6NFRare, very advanced

Normalization Hierarchy

1NF → 2NF → 3NF → BCNF → 4NF → 5NF — each level includes all previous rules.

Final Summary — Quick Revision
  • 1NF → Atomic values
  • 2NF → No partial dependency
  • 3NF → No transitive dependency
  • Goal: Remove redundancy + anomalies
  • Must ensure: Lossless Join and Dependency Preservation

Lecture 2: Relational Database Design / 7 — Normal Forms

Third Normal Form (3NF)

Definition A relation is in 3NF if for every dependency X→A, at least one is true: it's a trivial dependency (A already part of X), X is a superkey, or A is a prime attribute (part of some candidate key).

Shortcut to remember: "Either key determines it OR it is part of a key."

Example — Not in 3NF Student(ID, Dept, HOD)
Dependencies: ID → Dept, Dept → HOD.
ID is key. Dept is NOT key. HOD depends on Dept (not key) → transitive dependency exists.

Convert to 3NF: Student(ID, Dept) + Department(Dept, HOD) — no transitive dependency, relation is in 3NF.

Testing 3NF

  • Checking 3NF is NP-hard because we must find all candidate keys (can be many).
  • Trick: instead of checking full closure (F⁺), check only given dependencies (F).

3NF Decomposition Algorithm

  1. Find Canonical Cover (Fc).
  2. Remove redundant dependencies.
  3. Create relations: for each FD X→Y, make table (X∪Y). Example: A→B ⇒ Table(A,B); B→C ⇒ Table(B,C).
  4. Ensure candidate key exists — if no table contains a key, add one.
  5. Remove redundant tables (if one table is subset of another).

Properties of 3NF

  • Lossless Join
  • Dependency Preserving
  • Removes most redundancy

Boyce-Codd Normal Form (BCNF)

Definition A relation is in BCNF if for every dependency X→A: either trivial, OR X must be a superkey. (No relaxation allowed unlike 3NF.)
Example — Not in BCNF Course(Student, Subject, Teacher)
Dependencies: (Student, Subject) → Teacher; Teacher → Subject.
Teacher is NOT a superkey but determines Subject → violates BCNF.

BCNF Decomposition: Teacher(Teacher, Subject) + Course(Student, Teacher) — now all determinants are superkeys.

Testing BCNF

  • For original relation: check only given dependencies (F).
  • For decomposed relations: must use attribute closure (X⁺).

BCNF Decomposition Steps

  1. Find violating dependency X→Y.
  2. Decompose: R1 = (X∪Y), R2 = (R−(Y−X)).
  3. Repeat until all relations satisfy BCNF.

Properties of BCNF

  • Always lossless join
  • May not preserve dependencies

Dependency Preservation

Meaning: After decomposition, we should be able to check all dependencies without joining tables.

Methods:

  1. Exponential Algorithm: uses full closure (F⁺); always correct; very slow.
  2. Polynomial Algorithm: faster method; no false positives; may give false negatives (may say "not preserved" even if it is).

3NF vs BCNF (Comparison Table)

Feature3NFBCNF
RedundancyAllows someAlmost none
Dependency PreservationAlwaysNot guaranteed
Lossless JoinAlwaysAlways
ConditionX is superkey OR A is primeX must be superkey
StrictnessLess strictMore strict
ComplexityTesting NP-hardUses closure
Final Quick Revision
  • 3NF: Removes transitive dependency; allows slight redundancy; always safe choice.
  • BCNF: Removes all redundancy; stricter than 3NF; may lose some dependencies.
  • Key Difference: 3NF = Practical + Safe. BCNF = Pure + Strict.

Lecture 3: Relational Database Design / 8 — Case Study

Process Overview

Designing a database follows these steps:

  1. Identify Entities & Attributes
  2. Identify Relationships (ER Model)
  3. Convert ER → Tables (Relational Schema)
  4. Apply Normalization (3NF / BCNF)
  5. Practical Refinement (for fast queries)
Simple Idea "From real-world description → clean, efficient tables"

Example (Library System)

From description: "Students borrow books from library"

We extract:

  • Entities → Student, Book
  • Relationship → Issue

Entity & Attribute Identification

Types of Entities:

  • Tangible Entities (Physical): Book, Member, Staff
  • Intangible Entities (Conceptual): Rules like Quota (max books, time limit)

These may be hidden in text and must be identified carefully.

Unique Identifiers

IdentifierMeaning
ISBNSame for all copies of a book
Accession No.Unique for each physical copy
Example Book Title: DBMS. ISBN: 12345 → same for all copies. Accession No: A1, A2, A3 → different copies.

Composite vs Atomic Attributes

  • Composite: Name = "Rahul Sharma"
  • Atomic: First_Name = Rahul, Last_Name = Sharma

Always convert to atomic values.

Implicit Entities

Some entities are not directly mentioned but needed. Example: "Library system" → needs Staff entity, even if not written explicitly.

Constraints & Relationships

Value Constraints — restrict allowed values: Member_Type ∈ {UG, PG, Faculty}

Relationship Attributes — some attributes belong to relationships, not entities.

  • Wrong: Assign Date of Issue (DOI) to Book or Member
  • Correct: Issue(Member, Book, Date_of_Issue)

Cardinality (Relationship Type)

Example — Issue Relationship One member → many books. One book copy → one member (at a time). So: Many-to-One relationship.

Functional Dependencies & Normalization

Why Needed? To remove redundancy.

Example Problem Book(Accession_No, ISBN, Title, Author, Publisher)
FD: ISBN → Title, Author, Publisher.
Problem: Same ISBN repeated for every copy → redundancy.

Solution (Decomposition):

  • Book_Copy(Accession_No, ISBN)
  • Book_Details(ISBN, Title, Author, Publisher)

Now: no redundancy, achieves BCNF.

Pragmatics & Query Efficiency

Real Problem: A design can be theoretically perfect but practically inefficient.

Example Problem Separate tables: Student(ID, Name), Faculty(ID, Name)
Query: "Who issued a book?" — problem: need to check BOTH tables.

Solution: Generalization — create one table:

Member(ID, Name, Member_Class, Member_Type)

Where Member_Class → Student / Faculty, Member_Type → UG / PG / Faculty.

Benefit: Single query works; still normalized; efficient.

Final Summary — Quick Revision
  • Workflow: Identify → Model → Convert → Normalize → Optimize
  • Key Concepts: Entities = Objects; Attributes = Properties; Relationships = Connections
  • Important Rules: use atomic attributes; identify hidden entities; place attributes in correct relationships
  • Normalization: remove redundancy using FDs; use decomposition
  • Practical Design: balance theory + performance; use generalization for efficient queries

Memory Trick: "Good database = Clean structure + Fast queries"

Lecture 4: Relational Database Design / 9 — MVD & 4NF

Introduction to Advanced Redundancy

Core Idea:

  • Traditional normalization (FDs, 3NF, BCNF) handles functional dependencies.
  • Real-world data often has multivalued attributes.

Example: A person can have multiple phone numbers and multiple hobbies.

Problem: Even after 1NF (atomic values), redundancy still exists.

Example: Person(Name, Phone, Hobby)

NamePhoneHobby
Rahul123Cricket
Rahul123Music
Rahul456Cricket
Rahul456Music

All combinations are stored, causing duplication.

Conclusion Functional dependencies alone are not enough. Need Multivalued Dependencies (MVDs).

Multivalued Dependency (MVD)

Definition If one attribute determines multiple independent values: A ↠ B (A multi-determines B).
Example Student(Name, Course, Hobby)
If courses are independent of hobbies: Name ↠ Course, Name ↠ Hobby.

Cartesian Effect

If Rahul → {Math, Science} and Rahul → {Cricket, Music}, the table stores:

  • Rahul, Math, Cricket
  • Rahul, Math, Music
  • Rahul, Science, Cricket
  • Rahul, Science, Music

This cartesian product causes redundancy.

Key Insight MVD occurs when two independent relationships are stored in one table.

Relationship: FD vs MVD

Golden Rule: If Y→Z, then Y↠Z. Reverse is not true: Y↠Z ≠ Y→Z. MVD does not imply FD.

MVD Rules & Triviality

Important Rules:

  1. Complementation: If X↠Y, then X↠(R−(X∪Y)).
  2. Transitivity: If X↠Y and Y↠Z, then X↠(Z−Y).

Trivial MVD: An MVD is trivial if β ⊆ α, or α∪β = R. Similar to trivial FD.

Fourth Normal Form (4NF)

Definition A relation is in 4NF if for every non-trivial MVD α↠β, α must be a superkey.

Key Point: 4NF removes multivalued redundancy.

Example — Violation Student(Name, Course, Hobby) with Name ↠ Course, Name ↠ Hobby.
Here, Name is not a superkey → violates 4NF.

Convert to 4NF — split into:

  • Student_Course(Name, Course)
  • Student_Hobby(Name, Hobby)

Now: no redundancy, no cartesian product.

4NF Decomposition Algorithm

  1. Find violating MVD: α ↠ β (α not superkey).
  2. Decompose: R1 = (α∪β), R2 = (R−β).
  3. Repeat until all relations are in 4NF.

Properties: Lossless Join; may not preserve dependencies.

Final Concepts & Higher Forms

Why 4NF? Removes redundancy caused by multiple independent attributes.

Hierarchy: 1NF → 2NF → 3NF → BCNF → 4NF → 5NF — Note: 4NF ⊂ BCNF.

Higher Normal Forms: 5NF handles join dependencies; rarely used in practice.

Final Quick Revision — Key Differences

ConceptMeaning
FDOne value determines another
MVDOne value determines multiple independent values
Final Summary
  • MVD handles independent multi-values.
  • Causes cartesian redundancy.
  • 4NF removes this by splitting tables.
  • Ensures clean structure and no duplication.

4NF Rule: "No multi-valued dependency unless key."
Memory Trick: "If combinations explode → use 4NF."

Lecture 5: Relational Database Design / 9 — MVD & 4NF (continued)

Core Design Goals

Aim to design databases in:

  • BCNF (Boyce-Codd Normal Form) or
  • 4NF (Fourth Normal Form)

Ensure:

  • Lossless Join → Original table can be reconstructed after decomposition
  • Dependency Preservation → Functional dependencies (FDs) remain enforceable
Example If a table Student(Course, Teacher) is split into Student(Course) + Course(Teacher), a lossless join ensures no data is lost when joining back.

Fallback Strategy (When BCNF/4NF Fails)

Sometimes BCNF/4NF cannot preserve all dependencies. Then we choose 3NF.

Two choices:

  1. Accept some redundancy (use 3NF)
  2. Keep BCNF but enforce dependencies using joins or application logic
Exam Tip 3NF = practical compromise between theory & usability.

SQL Limitations

SQL mainly enforces Primary Keys / Superkeys. SQL cannot directly enforce general FDs.

Assertions exist but are rarely used and expensive.

Example FD: RollNo → Name. SQL cannot enforce this unless it is a key.

Starting Points of Design

Design usually begins from:

  • ER Diagram → Convert entities into tables
  • Universal Relation → Start with one big table, then decompose
  • Ad-hoc Design → Later normalize

Design Refinement

Identify real-world entities properly.

Wrong Employee(Name, DeptName, DeptLocation)
Correct Employee(Name, DeptID)
Department(DeptID, DeptName, Location)

Reason: Because DeptName → Location (FD exists), Department should be a separate entity.

Trade-off (Normalization vs Performance)

NormalizationDenormalization
Less redundancyMore redundancy
More joinsFaster queries
Clean designComplex updates

Denormalization: Intentionally adding redundancy for performance.

Example: Instead of joining Orders + Customer, store customer name directly in Orders.

Alternative: Materialized Views

Precomputed results stored as tables.

Benefits: Faster queries; no manual redundancy.

Common Design Mistakes

Year-wise Tables (Bad Design): Sales_2022, Sales_2023

Problem: Hard to query all years together.

Better: Sales(Product, Year, Amount)

Crosstabbing (Bad Design): Sales(Product, 2022, 2023, 2024)

Problems: Many NULL values; hard to extend.

Better: Sales(Product, Year, Amount)

Temporal Databases (Time-based Data)

What is Temporal DB? Stores historical data, not just current state.

Examples: Medical records; stock prices.

Types of Time:

  1. Valid Time → When data is true in real world. Example: Salary = ₹50k (Jan–March).
  2. Transaction Time → When data is stored in DB. Example: Salary updated on April 1.

Types of Temporal Relations:

  • Uni-temporal → Stores one time (valid OR transaction)
  • Bi-temporal → Stores both
Bi-temporal Example Salary(Employee, Amount, ValidTime, TransactionTime)
Can answer: past real-world data, and when DB recorded it.

Pros & Cons of Temporal DB

Advantages: Full history tracking; accurate analysis.

Disadvantages: More storage needed; complex queries (time ranges); hard maintenance.

Final Quick Summary
  • Goal → BCNF/4NF + lossless + dependency preservation
  • If not possible → Use 3NF
  • SQL cannot enforce all FDs
  • Start from ER / Universal relation
  • Identify entities correctly
  • Denormalization → Faster but complex
  • Avoid year-wise tables & crosstabs
  • Temporal DB → handles historical data
  • Bi-temporal = most powerful but costly
