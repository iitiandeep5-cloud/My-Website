1Indexing / 1

Database indexing

  • A technique to speed up data retrieval in a database.
  • Instead of scanning the whole table, an index helps locate data quickly.
Analogy: Book index → you don't read the whole book, you jump directly to the page.

Why do we need indexing?

  • Without index: search requires linear search — O(n)
  • With index: faster search using structures like binary search — O(log n)

Basic structure of an index

  • Search key: attribute used for searching (e.g. Name, Roll No, Phone Number)
  • Pointer: address of the actual record in memory/disk
Example
NamePointer
Aditi→ Record 101
Rahul→ Record 205

ISAM (Indexed Sequential Access Method)

  • Combines sequential storage with index-based access.
  • Helps in both fast lookup and ordered traversal.

Types of ordered index

1. Primary (clustering) index

  • Data is physically sorted based on this key.
  • Usually (but not always) the primary key.
  • Example: records sorted by roll number.

2. Secondary (non-clustering) index

  • Data is not sorted on this key.
  • Used for searching on other attributes.
  • Example: file sorted by Roll No, but index on Name.

3. Dense index — contains an entry for every record

KeyPointer
A→ R1
B→ R2
C→ R3
  • Fast access
  • More storage required

4. Sparse index — entries for some records only (usually the first record of each block)

KeyPointer
A→ Block 1
M→ Block 2
  • Less storage
  • Slightly slower than dense

Multi-level indexing

  • When the index becomes too large, create an index on the index (hierarchy).
  • Inner index: the original index
  • Outer index: points to inner index blocks
  • Keeps search efficient even for large data.
Analogy: Book → Chapters → Topics → Pages

Index maintenance (costs)

  • Storage overhead: extra space required for index files
  • Insert: new key must be added to the index — in a sparse index, only if a new block is created
  • Delete: remove the key from the index if no record exists — sparse index may need adjustment

Performance factors

  1. Access type: equality search (WHERE id = 5), range queries (WHERE age BETWEEN 20 AND 30)
  2. Access time: time to retrieve data
  3. Update time: cost of insert/delete
  4. Query pattern: analyse frequent queries and optimise the index accordingly
Dense vs sparse at a glance
FeatureDense indexSparse index
EntriesEvery recordSome records
SpeedFasterSlower
SpaceMoreLess
MaintenanceHighLow

Key formulas / complexity

  • Linear search: O(n)
  • Binary search / indexed: O(log n)

Final summary

  • Index = search accelerator
  • Uses key + pointer
  • Types: primary, secondary, dense, sparse
  • Multi-level indexing improves scalability
  • Trade-off = speed vs storage vs update cost

2Indexing / 2

Introduction to external indexing

Context

  • Previously: primary, secondary, dense, sparse indexing.
  • Now: how indexing works on disk (external memory).

Goal

  • Handle huge data (millions of records).
  • Work efficiently on disk storage.
Solution: use B-Trees / B+ Trees.

Balanced binary search trees (BSTs)

Basic idea: a BST improves search compared to linear search.

MethodTime complexity
Linear searchO(n)
BST (ideal)O(log n)

Problem: tree height

  • Search time depends on height h; complexity = O(h).
  • Worst case: tree becomes skewed → O(n).
  • Balanced tree definition: height is always O(log n).

Balancing strategies

  1. AVL trees (strict balance)
    • Condition: |hL − hR| ≤ 1
    • Uses rotations to rebalance
    • Guarantees O(log n)
    • Rotations are costly
  2. Randomized BST
    • Random decisions maintain balance
    • Works well on average
    • High probability of O(log n)
  3. Skip lists
    • Multi-level linked lists
    • Random promotion of elements
    • Search: O(log n)
    • Simple alternative to trees
  4. Splay trees (amortized)
    • Frequently accessed elements move to the top
    • Average cost O(log n) over many operations

Limitations of standard trees

Not suitable for databases because they:

  • Cannot handle millions of records
  • Require frequent rotations
  • Are not efficient for disk storage

2-3-4 tree concept

Need a better structure → multi-way trees.

Key idea

  • Store multiple values per node.
  • Keep all leaves at the same level.
Node types
Node typeKeysChildren
2-node12
3-node23
4-node34

Example (3-node)

  • Keys: S, L
  • Branches: left → values < S · middle → between S and L · right → > L

Search in a 2-3-4 tree

  • Compare with multiple keys.
  • Choose the correct branch.
  • Complexity: O(log n).

Insertion in a 2-3-4 tree

Steps: find the correct leaf, then insert the key.

Cases:

  • 2-node → becomes 3-node
  • 3-node → becomes 4-node
  • 4-node → split required

Splitting rule — if a node has [S, M, L]: M goes up to the parent, and S and L become separate nodes.

Before split: [S M L] After split: M / \ S L

Height change: height increases only if the root splits; the tree remains perfectly balanced.

Splitting strategies:

  • Early split: split while moving down → faster insertion
  • Late split: split only when needed → fewer operations

Deletion

  • Reverse of splitting → merge nodes.
  • If a node underflows: borrow from a sibling, or merge nodes.

Advantages of 2-3-4 trees

  • Always balanced
  • Height = O(log n)
  • Sorted data maintained
  • Efficient for large data

From 2-3-4 trees → B-Trees

  • Generalization: instead of small nodes, use large nodes (disk blocks).
  • Half-full rule: every node (except the root) must be at least 50% full.

Why: reduces height, minimises disk access, improves performance.

Final complexity summary
OperationComplexity
SearchO(log n)
InsertO(log n)
DeleteO(log n)

Final summary

  • BST → fast but can become slow
  • Balanced trees → fix height
  • Still not good for disks
  • 2-3-4 trees → multi-value nodes
  • Leads to → B-Trees / B+ Trees (used in DBMS)

3Indexing / 3 — B+ Trees

What is a B+ Tree?

  • A balanced multi-level index structure.
  • Used in databases for fast searching on disk.

Purpose: avoid the performance issues of sequential files and reduce reorganisation overhead.

Relation to 2-3-4 trees

  • A B+ Tree is an advanced version of the 2-3-4 tree.
  • Properties: multi-value nodes · always balanced · all leaf nodes at the same level.

Structure of a B+ Tree

Key properties

  • Balanced height: all leaves at the same level → equal access time.
  • Half-full rule: if max pointers = n, each node must have at least n/2 pointers. The root is an exception (it can have fewer).

Node types

  • Leaf nodes: store actual data pointers/records; connected like a linked list; benefit — fast range queries and easy sequential access.
  • Internal nodes: store only keys + pointers; do not store actual data; their role is to guide the search path.

Operations

Search: start at root → compare key → follow pointer → reach leaf → linear search. Complexity: O(log n).

Insertion:

  • Insert into the leaf node.
  • If the node is full → a split occurs.
  • Splitting rule: divide keys into two nodes, push the middle key up.
  • The split may propagate upward.
  • Height increases only at the root.

Deletion:

  • Remove the key from the leaf.
  • If node < n/2 → borrow from a sibling or merge nodes.
  • Height may decrease.

Performance & efficiency

Height formula: Height ≈ O(log(n/2) K), where n = max pointers and K = number of keys.
Comparison example
StructureHeight (1M records)
Binary tree~20
B+ Tree (n = 100)~4
  • Fewer levels → fewer disk accesses.

Trade-off: increasing node size means fewer levels, but slower search inside a node.

Advanced concepts

Handling duplicates

  • Buckets (list of pointers)
  • Store multiple records
  • Add a unique ID

Record relocation problem

  • If data moves, updating all indices is costly.
  • Solution: the secondary index stores the primary key instead of the physical address.

String indexing

  • Use prefix compression.
  • Example: instead of storing "DATABASE", store "DATA" (enough for uniqueness).
  • Saves space.

B-Tree vs B+ Tree

FeatureB-TreeB+ Tree
Data storageInternal + leafOnly leaf
Key repetitionNoYes
Internal node sizeLargeSmaller
Fan-outLowHigh
PerformanceSlowerFaster

Why the B+ Tree is preferred: higher fan-out → smaller height; better disk efficiency; faster range queries (linked leaves).

Final summary

  • B+ Tree = best indexing structure for a DBMS
  • Balanced → O(log n)
  • Leaf nodes store data
  • Internal nodes guide the search
  • Efficient for large-scale data on disk

4Hashing

What is hashing?

Hashing is a technique to convert large data (keys) into small numeric values using a hash function.

Purpose: enable fast searching (almost O(1)) and avoid full table scans.

Basic idea: Key (e.g. Name) → hash function → bucket address. Example: "Rahul" → h(key) → Bucket 5.

Buckets

  • Storage locations (usually disk blocks).
  • Each bucket stores one or more records.

Collisions occur when two different keys map to the same bucket. For example, h("Aman") = 3 and h("Ravi") = 3 — both go to the same bucket.

An ideal hash function distributes keys uniformly and minimises collisions.

Static hashing

Concept

  • Fixed number of buckets.
  • Hash function remains constant.

Overflow handling: if a bucket is full → create an overflow bucket (chain).

Limitations:

  • Long overflow chains → slow search
  • Wastage if too many buckets
  • Hard to resize
  • Rehashing required for changes

Dynamic (extendable) hashing

Concept

  • Buckets grow/shrink dynamically.
  • No fixed size limitation.

Key idea — prefix bits: use the first i bits of the hash value. Example: hash = 101101; if i = 3 → use 101.

Directory (bucket table): a table of size 2i that points to buckets.

Depth concepts
TypeMeaning
Global depthNumber of bits used
Local depthBits used by a bucket

Bucket splitting: when a bucket is full → split the bucket, redistribute records, increase depth if needed.

Trade-off: adapts to growth, but directory expansion is costly.

Hashing vs ordered indexing

FeatureHashingB+ Tree
Search (exact match)Very fastGood
Range queriesNot efficientExcellent
StructureUnorderedOrdered

Conclusion: use hashing for exact search (WHERE id = 5); use a B+ Tree for range queries (BETWEEN 10 AND 50).

Bitmap index

Used for attributes with few possible values (low cardinality) — e.g. Gender, City, Income Level. Instead of storing values, it uses bit arrays (0/1).

Example table

Fast query using bit operations: to find "Male AND High Income", perform a bitwise AND.

Advantages: very fast queries, memory efficient, ideal for data warehouses.

Final summary

  • Hashing = fastest for exact match
  • Static hashing = simple but rigid
  • Dynamic hashing = flexible but complex
  • Collisions handled via chaining/splitting
  • Bitmap index = best for low-cardinality data

5Index Design

Creating & dropping an index

CREATE INDEX index_name
ON table_name (column1, column2);

Example:

CREATE INDEX idx_name
ON Student(name);
DROP INDEX index_name;

Example:

DROP INDEX idx_name;

Types of index

1. Simple index — created on a single column

CREATE INDEX idx_roll
ON Student(roll_no);

2. Composite index — created on multiple columns (max ≈ 32); order matters (left → right)

CREATE INDEX idx_name_city
ON Student(name, city);

3. Unique index — ensures no duplicate values; acts like a candidate key

CREATE UNIQUE INDEX idx_email
ON Student(email);

Used when queries apply functions — a normal index won't work here:

Multi-key access strategy

  • Query on multiple columns.
  • Option 1: use multiple single indexes → intersect results.
  • Option 2: use a composite index.

Seven golden rules of indexing

  • Rule 0 — trade-off: faster reads, but slower updates and more storage.
  • Rule 1 — correct table: use an index if the query retrieves < 15% of rows.
  • Rule 2 — correct column: choose columns with high uniqueness; use bitmap for low distinct values.
  • Rule 3 — limit indices: too many indices → slow inserts/updates.
  • Rule 4 — column order: in a composite index, put the most selective column first, e.g. (name, city) if name is more unique.
  • Rule 5 — gather statistics: COMPUTE STATISTICS; helps the query optimiser.
  • Rule 6 — drop unused index: saves space, improves performance.

Physical vs logical design

  • Logical design: done during the design phase — e.g. normalization removes redundancy.
  • Physical design: done during execution/runtime; includes indexing and hashing; depends on query patterns and data size.
Composite index size rule: index key size ≤ ½ of the data block size.

Final summary

  • Index improves search speed
  • Types: simple, composite, unique
  • Advanced: function-based, bitmap
  • Follow the 7 rules for best performance
  • Trade-off: speed vs storage vs update cost
