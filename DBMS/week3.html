Lecture 1: SQL Examples

Basic Query Structure (SELECT–FROM–WHERE)

Core Structure

SELECT column_name
FROM table_name
WHERE condition;
  • FROM → specifies table(s) to use
  • WHERE → filters rows based on condition
  • SELECT → chooses which columns to display

Duplicates Handling

  • SQL returns duplicates by default (multiset)
  • DISTINCT → removes duplicates
  • ALL → keeps duplicates (default)

Joins & Cartesian Product

Multiple tables → SQL first creates a Cartesian product (all combinations).

Join Condition

WHERE student.dept = department.name

Aliases (AS)

FROM student AS s
  • Renames tables/columns for clarity
  • Essential for self-joins

Advanced Predicates & Logic

Logical Operators

  • AND, OR, NOT
  • Use parentheses for correct precedence

IN Operator

WHERE dept IN ('CSE', 'ECE')

Pattern Matching (LIKE)

  • _ → exactly one character
  • % → any number of characters
WHERE name LIKE 'A%'

Sorting Results

ORDER BY

ORDER BY column_name;
  • Default → Ascending (ASC)
  • Use DESC for descending

Multiple Columns

ORDER BY dept, credits DESC;

Set Operations

Work like mathematical sets (duplicates removed by default).

Operators

  • UNION → combines results
  • INTERSECT → common rows
  • EXCEPT → rows in first but not second
  • Use ALL → to keep duplicates

Aggregate Functions & GROUP BY

Aggregate Functions

  • AVG() → average
  • MIN() → minimum
  • MAX() → maximum
  • COUNT() → number of rows
  • SUM() → total

GROUP BY

GROUP BY department;
  • Groups rows with same values

Filtering Groups (HAVING)

HAVING AVG(salary) > 50000;
  • WHERE → filters rows
  • HAVING → filters groups

Quick Summary

  • SELECT–FROM–WHERE → basic query
  • DISTINCT → remove duplicates
  • JOIN + WHERE → combine tables
  • IN / LIKE → advanced filtering
  • ORDER BY → sorting
  • UNION / INTERSECT / EXCEPT → set operations
  • GROUP BY + HAVING → aggregation

Lecture 2: Intermediate SQL / 1

Introduction

  • Moves beyond basic SQL → focuses on advanced querying and data modification
  • Two main topics:
    • Nested Subqueries
    • Data Manipulation (INSERT, UPDATE, DELETE)

Nested Subqueries

Definition: A subquery is a query inside another query, written using SELECT–FROM–WHERE.

Key Idea: Output of one query (relation) is used as input to another query.

A. Subqueries in WHERE Clause

  1. Set Membership
    • IN / NOT IN → check if value exists in subquery result
    WHERE dept IN (SELECT dept FROM instructor)
  2. Set Comparison
    • SOME (ANY) → true if condition holds for at least one value
    • ALL → true if condition holds for all values
  3. Empty Relation Test
    • EXISTS → true if subquery returns any row
    • NOT EXISTS → true if no rows returned
  4. Correlated Subqueries
    • Inner query depends on outer query
    WHERE salary > (
  SELECT AVG(salary)
  FROM instructor i2
  WHERE i2.dept = i1.dept
)
  5. Uniqueness Test
    • UNIQUE → checks no duplicates in subquery result

B. Subqueries in FROM Clause

  • Acts like a temporary table
  • Useful for breaking complex queries
  • Alternative to HAVING
FROM (SELECT dept, AVG(salary) AS avg_sal
      FROM instructor
      GROUP BY dept) AS temp

C. Subqueries in SELECT Clause

  • Must return a single value (scalar)
  • If multiple values returned → error
SELECT name,
       (SELECT COUNT(*) FROM teaches) AS total_courses

D. WITH Clause (CTE)

  • Creates temporary named relation
  • Improves readability and reuse
WITH temp AS (
  SELECT dept, AVG(salary) AS avg_sal
  FROM instructor
  GROUP BY dept
)
SELECT * FROM temp;

Data Manipulation (Modification)

A. DELETE

DELETE FROM table_name WHERE condition;
  • Deletes selected rows
  • No WHERE → deletes all rows
  • Subqueries are evaluated before deletion starts

B. INSERT

INSERT INTO table_name VALUES (...);
INSERT INTO table_name (col1, col2) VALUES (...);

Key Points:

  • Order must match schema (if columns not specified)
  • NULL allowed for unknown values

Insert from Query:

INSERT INTO table_name
SELECT * FROM another_table;
  • SELECT runs completely first (avoids infinite loops)

C. UPDATE

UPDATE table_name
SET column = value
WHERE condition;

CASE Expression (Multiple Conditions):

UPDATE instructor
SET salary = CASE
  WHEN salary < 50000 THEN salary * 1.1
  ELSE salary * 1.05
END;

Using Subqueries in UPDATE:

UPDATE instructor
SET salary = (
  SELECT AVG(salary) FROM instructor
);

Quick Summary

  • Subqueries → query inside query
  • WHERE subqueries → IN, EXISTS, SOME, ALL
  • FROM subqueries → temporary tables
  • SELECT subqueries → scalar values only
  • WITH → improves readability
  • Data Modification:
    • DELETE → remove data
    • INSERT → add data
    • UPDATE → modify data
    • CASE → handle multiple update conditions

Lecture 3: Intermediate SQL / 2

Join Operations

Purpose: Combine data from multiple tables meaningfully.

  • Based on Cartesian Product + condition

Types of Joins

  1. Cross Join
    • Pure Cartesian Product
    • Every row of table A × every row of table B
    • If A has m rows and B has n rows → result = m × n
  2. Inner Join
    • Keeps only matching rows
    • Non-matching rows are discarded
    • Represents intersection of data
    SELECT *
FROM A INNER JOIN B
ON A.id = B.id;
  3. Outer Joins
    • Used to avoid data loss (fills missing values with NULL)
    • Left Outer Join → keeps all rows from left table
    • Right Outer Join → keeps all rows from right table
    • Full Outer Join → keeps all rows from both tables

Join Conditions & Keywords

  1. NATURAL JOIN
    • Automatically joins on same attribute names
    • Removes duplicate columns
  2. ON Clause
    • Specifies join condition explicitly
    ON A.id = B.id
  3. USING Clause
    • Joins using common attributes
    USING (id)

Performance Note

  • Joins are expensive operations
  • Large tables → huge intermediate results
  • Example: 1M × 1M = 1 trillion combinations

Database Views

Definition: A view is a virtual table.

  • Does not store data physically
  • Used for:
    • Security (hide sensitive data)
    • Simplification (complex queries)

Creating a View

CREATE VIEW view_name AS
SELECT ...;

Key Properties

  • View is recomputed every time it is used
  • Always shows latest data from base tables

View Expansion

  • System replaces view with its original query
  • Continues until only real tables remain

View Dependencies

  • Views can be built on other views
  • Creates a dependency chain

Updating Views

  • Possible only if convertible to base table operations
  • Limitations:
    • Fails if required columns are hidden
    • Fails if view is too complex (joins, aggregates)
  • Most DBMS allow updates only on simple views (single table)

Materialized Views

  • Stored physically as tables
  • Faster access but:
    • Can become outdated
    • Need regular refresh

Quick Summary

  • Cross Join → all combinations
  • Inner Join → only matches
  • Outer Join → keeps unmatched with NULL
  • NATURAL / ON / USING → join conditions
  • View → virtual table (no storage)
  • Materialized View → stored but needs updates

Lecture 4: Intermediate SQL / 3

Transactions

Definition: A transaction is a group of SQL operations treated as one unit.

Properties (ACID – simplified)

  • Atomicity → All or nothing (success or rollback)
  • Isolation → Transactions don't interfere with each other

Control Commands

COMMIT;    -- save changes
ROLLBACK;  -- undo changes

Integrity Constraints

Ensure data correctness and consistency.

A. Single Relation Constraints

  • NOT NULL → no empty values
  • UNIQUE → values must be distinct (can allow NULL)

B. CHECK Clause

Applies custom conditions.

CHECK (semester IN ('fall', 'winter', 'spring', 'summer'))

C. Referential Integrity (Foreign Key)

  • Ensures valid relationships between tables
  • Example: instructor's department must exist in department table

D. Cascading Actions

  • Automatically propagate changes
  • ON DELETE CASCADE → delete dependent rows
  • ON UPDATE CASCADE → update dependent rows

E. Constraint Checking

  • Used in complex cases (like self-referencing tables)
  • Can be delayed (deferred checking)

SQL Data Types & Schema Concepts

A. Date & Time

  • Types: DATE, TIME, TIMESTAMP
  • Difference stored as INTERVAL
  • Supports arithmetic (add/subtract time)

B. Index

  • Improves search speed
  • Uses structures like B-tree

Trade-off:

  • Faster queries
  • Slower updates (maintenance cost)

C. User-Defined Types

CREATE TYPE dollar AS numeric(10,2);
  • Alias for existing type
  • Example: dollar for currency

D. Domain

CREATE DOMAIN age INT CHECK (age >= 18);
  • Type + constraints
  • Reusable & stricter

E. Large Objects

  • BLOB → binary data (images, videos)
  • CLOB → large text data
  • Stored externally → DB stores reference

Authorization

Controls who can access what.

A. Privileges

  • Data operations: SELECT, INSERT, UPDATE, DELETE
  • Schema operations: create/alter tables, indices
  • REFERENCES: needed for foreign keys

B. Commands

GRANT privilege TO user;
REVOKE privilege FROM user;

C. WITH GRANT OPTION

Allows user to grant permissions to others.

D. Roles

  • Group of privileges
  • Assign roles instead of individual permissions
  • Example: role = instructor, admin

E. Views & Security

  • Permissions can be given on views
  • Users can access limited data without seeing full tables

Quick Summary

  • Transaction → unit of work (COMMIT / ROLLBACK)
  • Constraints → ensure valid data (NOT NULL, UNIQUE, FK)
  • CASCADE → automatic updates/deletes
  • Index → faster search
  • Domain → reusable constrained type
  • BLOB/CLOB → large data storage
  • GRANT/REVOKE → control access
  • Roles & Views → simplify security

Lecture 5: Advanced SQL

Functions & Procedures in SQL

Purpose: Add programming logic inside SQL.

Integration Models

  • External Invocation → SQL calls functions written in C, Java, Python
  • Embedded SQL → SQL written inside another programming language
  • Native SQL (SQL:1999) → Procedures/functions written fully in SQL

Why Use External Languages?

  • Handle complex logic
  • Work with special data (images, geometry)
  • Support object-oriented features

Table-Valued Functions

  • Return a table instead of a single value
  • Used like a table in FROM
SELECT *
FROM TABLE(function_name(...));

Defining Functions

CREATE FUNCTION func_name(parameters)
RETURNS data_type
BEGIN
  -- logic
END;
  • Returns a single value
  • Supports overloading

Procedures

  • Do not return value directly
  • Use IN / OUT parameters
CALL procedure_name(...);

Procedural Language Constructs

Compound Statements

BEGIN
  -- multiple statements
END;

Loops

  • WHILE → runs while condition is true
  • REPEAT → runs at least once
  • FOR → loops over query results

Conditionals

  • IF–THEN–ELSE
  • CASE:
    • Simple CASE → like switch
    • Searched CASE → complex conditions

Variables

SET variable = value;

Exception Handling

  • SIGNAL → raise error
  • HANDLER → manage errors

Triggers

Definition: Automatic actions executed on data changes.

Trigger Events

  • INSERT
  • UPDATE
  • DELETE

Trigger Timing

  • BEFORE → runs before change (validation/modification)
  • AFTER → runs after change (logging/integrity)

Trigger Types (Granularity)

  • Statement-level → once per query
  • Row-level → once per row affected

Data Referencing

  • OLD → previous data
  • NEW → updated/new data

When to Use Triggers

  • Logging & auditing
  • Maintaining integrity
  • Simple validation

When to Avoid

  • Too many triggers
  • Complex logic
  • Recursive triggers
  • Expensive operations

Quick Summary

  • Functions → return value
  • Procedures → use IN/OUT, no direct return
  • Table functions → return tables
  • Loops & IF/CASE → control flow
  • Triggers → automatic actions on DB changes
