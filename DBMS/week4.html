Lecture 1: Formal Relational Query Languages / 1

Overview: Formal query languages form the theoretical foundation of databases, underlying SQL. There are three main types:

  • Relational Algebra → Procedural (how to do)
  • Tuple Relational Calculus (TRC) → Non-procedural (what to get)
  • Domain Relational Calculus (DRC) → Non-procedural

Key Idea

  • Procedural = step-by-step operations
  • Non-procedural = describe final result only

Relational Algebra Basics

  • Developed by Edgar F. Codd (1970)
  • Procedural query language

Key Properties

  • Works on relations (tables)
  • Input → Relation
  • Output → Relation
  • Based on set theory
  • No duplicate tuples allowed

Basic Relational Algebra Operators

Unary Operators (Single Relation)

  1. Selection (σ)
    • Filters rows (tuples) based on condition
    • Example: σ(age > 20)
  2. Projection (Π)
    • Selects specific columns
    • Removes duplicates automatically
    • Example: Π(name, age)
  3. Rename (ρ)
    • Renames table or attributes
    • Useful for avoiding conflicts

Binary Operators (Two Relations)

  1. Union (∪)
    • Combines tuples from both relations
    • Conditions: same number of columns, compatible data types
  2. Set Difference (−)
    • Tuples in R but not in S
    • Condition: must be union compatible
  3. Cartesian Product (×)
    • Combines every tuple of R with every tuple of S
    • Can produce very large results
    • Attribute names must be distinct

Derived (Optional) Operations

These are not basic but can be built from basic operators.

  1. Intersection (∩)
    • Common tuples in both relations
    • Formula: r∩s = r−(r−s)
  2. Join (⋈)
    • Combines related tuples from two relations
    • Types:
      • Theta Join → condition-based (>, <, =)
      • Equi Join → only equality condition
      • Natural Join → joins on same attribute names automatically

Division Operator (÷)

Purpose: Used for "for all" queries
Example: Find students who passed all subjects

Concept

  • If R(Z), S(X)
  • Result has attributes Y = Z − X
  • A tuple appears in result if it is related to every tuple in S

Note: Division is not a basic operator. It can be expressed using:

  • Projection (Π)
  • Cartesian Product (×)
  • Set Difference (−)

Lecture 2: Formal Relational Query Languages / 2

Foundation: Predicate Logic

Relational calculus is based on predicate logic, which extends Boolean logic using predicates and quantifiers.

Predicate

  • Represents a property of a variable
  • Written as: P(x)
  • Example:
    • P(x): x > 3
    • P(5) → True
    • P(2) → False

Quantifiers

  1. Universal Quantifier (∀) → "For all"
    • Property must hold for every value
    • Example: ∀ x(x + 2 > x) → True (for natural numbers)
  2. Existential Quantifier (∃) → "There exists"
    • Property must hold for at least one value
    • Example: ∃ x(x > 3) → True (e.g., 4, 5)

Tuple Relational Calculus (TRC)

Idea: TRC describes what result we want, not how to compute it.

Basic Formula: {t ∣ P(t)}
Meaning: Set of all tuples t such that P(t) is true.

Components of TRC

  • Attributes: t.age, t.name
  • Constants: 10, "DBMS"
  • Comparison Operators: <, >, =
  • Logical Connectives: ∧ (AND), ∨ (OR), ¬ (NOT)
  • Implication: x ⇒ y ≡ ¬x∨y
  • Quantifiers: ∀, ∃

Safety of Expressions

  • A query is safe if it produces a finite result
  • Unsafe queries may attempt to return infinite data
  • Example (unsafe): Returning all values not in a table

Domain Relational Calculus (DRC)

Key Difference from TRC

TRCDRC
Uses one variable (t) for whole tupleUses separate variables for each attribute

Representation

  • TRC: t
  • DRC: x₁, x₂, …, xₙ

Example: Relation with 3 attributes:

  • TRC → t
  • DRC → x₁, x₂, x₃

Equivalence with Relational Algebra

Important Concept: Relational Algebra = TRC = DRC. All have the same expressive power.

Examples of Equivalence

Relational AlgebraTRC Equivalent
σB = 17(r){t ∣ ...}
Projection (π)Specify required attributes
JoinUsing ∧ and ∃

TRC Query Examples

  1. Simple Selection: Get first names of students older than 21: 
    {t.firstName ∣ student(t) ∧ t.age > 21}
  2. Join-Type Query: Students who took "DBMS": 
    {s.name ∣ student(s) ∧ ∃c(course(c) ∧ c.id = s.courseID ∧ c.name = 'DBMS')}
  3. Multi-Table Query: Employee IDs of pilots certified for "Boeing": 
    {c.eid ∣ certified(c) ∧ ∃a(aircraft(a) ∧ a.name = 'Boeing' ∧ a.id = c.id)}

Lecture 3: Entity Relationship Model / 1

Database Design Process

Starting Point

  • Begins with Requirement Specification (Functional Requirements)
  • Defines what the system should do

Key Considerations

  • Stakeholders: Users or people affected (students, admins, customers)
  • Constraints: Business rules (e.g., one student can enroll in max 5 courses)
  • Target Medium:
    • Small shop → PC
    • Large system → servers/supercomputers
  • Performance Metrics:
    • Fast response time (e.g., < 1 sec in banking)
    • Supports multiple users (concurrency)

Three Main Phases

  1. Requirement Analysis → Understand and define system needs
  2. Database Design
    • Logical Design: Conceptual (E-R model)
    • Physical Design: Storage (files, pages, memory)
  3. Implementation → Data migration + testing

Abstraction & Modeling

Abstraction: Focus only on relevant details, ignore unnecessary ones

Example:

  • Academic system → ignore teacher salary
  • Budget system → salary is important

Modeling: Represent real-world systems using mathematical/logical models

Example (Physics Model): S = ut + ½at²
Where: S = distance, u = initial velocity, t = time, a = acceleration

Other examples:

  • Circuit laws (Kirchhoff)
  • Maps (geography)
  • Scientific models

Entity-Relationship (E-R) Model

Purpose: Used for conceptual database design

Entities & Attributes

  • Entity: A real-world object (e.g., Student, Instructor)
  • Entity Set: Collection of similar entities (e.g., All students)

Types of Attributes

TypeMeaningExample
SimpleBasic valueAge, ID
CompositeMultiple partsName (first, last)
Multi-valuedMultiple valuesPhone numbers
DerivedCalculatedAge from DOB

Domain

  • Set of valid values
  • Example: Age ∈ (0–120)

Primary Key

  • Uniquely identifies each entity
  • Example: Student_ID

Relationships

Definition: Connection between entities
Example: Student enrolls in Course

Relationship Attributes: Relationships can have attributes
Example: Advisor relationship → "date assigned"

Degree of Relationship

TypeEntities InvolvedExample
Binary2Student–Course
Ternary3Student–Instructor–Project

Redundancy: Duplicate/unnecessary data should be avoided
Example: Instructor's department stored twice

Cardinality Constraints

Defines how many entities are related.

Types of Cardinality

Participation

  • Total Participation: Every entity must participate
  • Partial Participation: Some entities may not participate

Example:

  • Every student must enroll (total)
  • Some teachers may not guide projects (partial)

Lecture 4: Entity Relationship Model / 2

ER Diagram Components

ER diagrams visually represent database structure (similar to UML style).

Entity Sets

  • Represented by rectangles
  • Contains entity name and attributes
  • Example: Student (ID, Name, Age)

Primary Key

  • Underlined attribute
  • Uniquely identifies each entity
  • Example: Student (ID, Name, Age)

Relationships

  • Represented by diamonds
  • Connect entity sets
  • Example: Student —— Enrolls —— Course
  • By default: connects primary keys of entities

Relationship Attributes

  • Attached to relationship (diamond)
  • Shown using dashed line
  • Example: Advisor (date_assigned)

Roles (Recursive Relationship)

  • When entity relates to itself
  • Example: Course —— prerequisite —— Course
  • Roles: Course ID, Prerequisite ID

Cardinality & Participation

Cardinality Symbols

  • Arrow (→) → One
  • Line (—) → Many

Min..Max Notation

NotationMeaning

0..1Optional
0..*Zero or many
1..*At least one

Participation

TypeRepresentationMeaning
TotalDouble lineMust participate
PartialSingle lineOptional

Example:

  • Every student must enroll → Total
  • Some teachers may not guide → Partial

Attribute Types in ER

Composite Attribute: Made of multiple parts
Example: Name → First, Middle, Last; Address → Street, City, State

Multi-valued Attribute: Represented using { }
Example: {phone_number}

Derived Attribute: Computed from other attributes
Represented using ( )
Example: Age() from Date_of_Birth

Weak Entity Sets

Definition: No primary key of its own. Depends on a strong entity.

Representation

ComponentSymbol
Weak EntityDouble rectangle
Identifying RelationshipDouble diamond

Discriminator

  • Attribute to distinguish weak entities
  • Dashed underline

Primary Key Formula: Primary Key (Weak Entity) = Primary Key (Strong Entity) + Discriminator

Example:

  • Strong: Employee(ID)
  • Weak: Dependent(Name)
  • Key = (Employee_ID + Dependent_Name)

ER to Relational Schema (Reduction)

Entity → Table

  • Entity name → Table name
  • Attributes → Columns
  • Example: Student(ID, Name, Age)

Relationship → Table

Create new table using primary keys of both entities
Example: Enroll(Student_ID, Course_ID)

Composite Attributes

Flatten into separate columns
Example: Address → Street, City, State

Multi-valued Attributes

Create separate table
Example:

  • Student(ID)
  • Student_Phone(ID, Phone_Number)

Schema Optimization

Key Idea: Reduce unnecessary tables and joins

Rule: If relationship is Many-to-One (M:1) and participation is total on many side → Add foreign key directly

Example: Instead of:

  • Student_Department(Student_ID, Dept_Name)

Use: Student(ID, Name, Dept_Name)

Benefits

  • Fewer joins
  • Faster queries
  • Less overhead

Lecture 5: Entity Relationship Model / 3

Ternary & Non-Binary Relationships

Concept: Relationships are usually binary (two entities). Non-binary relationships involve three or more entities (e.g., ternary).

Ternary Relationship Example

  • Project – Instructor – Student
  • Represents: which instructor guides which student for which project

Cardinality Issue

  • Arrows become ambiguous in ternary relationships
  • Example confusion:
    • Does A map to one (B, C)?
    • Or does (A, B) map to one C?

Ground Rule: Only one arrow allowed in non-binary relationships → avoids ambiguity.

Decomposition into Binary

  • Convert ternary → binary using a new entity E
  • Mapping Formula:
    • Original tuples: (ai, bi, ci)
    • Create: (ei, ai), (ei, bi), (ei, ci)
    • Where ei = identifier in new entity E

Limitation

  • Binary relations cannot fully capture ternary constraints
  • May lose original relationship meaning

Specialization & Generalization (ISA)

Specialization (Top-Down): Break one entity into sub-entities.
Example: Person → Student, Employee.

Generalization (Bottom-Up): Combine entities into higher-level entity.
Example: Student + Employee → Person.

Inheritance: Sub-entities inherit attributes.
Example: Instructor → Employee → Person.

ISA Relationship: Represents "is-a" relationship.
Example: Student ISA Person.

Constraints

  1. Overlapping vs Disjoint
    • Overlapping: can belong to multiple (Person = Student + Employee)
    • Disjoint: only one category (Employee ≠ Instructor & Secretary)
  2. Total vs Partial
    • Total: must belong (Every student → UG or PG)
    • Partial: optional (Not all persons are students)

Relational Schema for ISA

Method 1: Separate Tables

  • One table for higher-level entity
  • Separate tables for lower-level entities
  • Example:
    • Person(ID, Name)
    • Student(ID, Credits)
    • Employee(ID, Salary)

Pros: No redundancy, no anomalies  |  Cons: Requires joins

Method 2: Flattened Tables

  • Each sub-entity stores all attributes
  • Example:
    • Student(ID, Name, Credits)
    • Employee(ID, Name, Salary)

Pros: Faster (no joins)  |  Cons: Data redundancy, possible anomalies

Aggregation

Concept: Treat a relationship as an entity.

Purpose: Avoid redundancy when linking relationships.

Example:

  • Relationship: Project-Guide (Student, Instructor, Project)
  • Add Evaluation
  • Instead of repeating (Student, Instructor, Project), treat Project-Guide as entity

Representation: Eval_For(ProjectGuide_ID, Evaluation_ID)

  • Uses:
    • Primary key of aggregated relation
    • Primary key of new entity

Key Design Issues

Attribute vs Entity: Example: Phone Number
Single → Attribute
Multiple → Separate Entity/Table

Entity vs Relationship:

  • Decide:
    • Is it an object? → Entity
    • Is it a connection? → Relationship

Binary vs Non-Binary:

  • Some can be split: Person–Father, Person–Mother
  • Some cannot: Project–Guide (needs 3 entities together)

Modularity:

  • Use specialization/generalization
  • Benefits: cleaner design, separation of concerns
  • Example: Person → common attributes; Student → specific (credits)
