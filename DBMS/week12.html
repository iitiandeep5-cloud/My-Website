1Query Processing and Optimization / 1 — Processing

Query processing flow

The database converts an SQL query into results in three main steps:

  • Parsing & translation: SQL → relational algebra
  • Optimization: chooses the least-cost execution plan using statistics such as number of tuples and size
  • Evaluation: executes the plan and returns output

Query cost (performance measure)

  • Main goal: minimise total execution time
  • Most important factor: disk I/O (more significant than CPU or network)

Disk access includes: seek time (finding data), read time, and write time (costlier due to verification).

Cost formula: Cost = b·tT + S·tS, where b = number of block transfers, tT = transfer time per block, S = number of seeks, tS = seek time.

Note: more buffer memory ⇒ fewer disk accesses ⇒ faster queries.

Selection (σ) operation strategies

  • Without index:
    • Linear search → scan the entire file (slow).
    • If the key is unique → stop early (average half scan).
  • With index:
    • Primary index (key): very fast, tree height traversal.
    • Primary index (non-key): multiple records must be fetched.
    • Secondary index: fast for key, slower for non-key (records scattered).
  • Complex conditions:
    • AND (conjunction): use one index + filter the remaining.
    • OR (disjunction): usually a full scan; if multiple indexes exist → combine results.

Sorting techniques

  • When data fits in memory: use quicksort (fast).
  • When data is large: use external merge sort.

External merge sort phases:

  1. Run creation: break into chunks, sort each chunk, store as sorted runs.
  2. Merge: merge runs step-by-step until the final output is fully sorted.

Join operations

  • Nested loop join: compare every tuple with every tuple (very slow).
  • Block nested loop join: compare block-by-block (reduces I/O significantly).
  • Indexed nested loop join: uses an index on the join attribute (much faster).

Other operations

  • Duplicate elimination: done using sorting or hashing; optimisation — remove duplicates during merge.
  • Aggregation (GROUP BY): functions — min, max, sum, count, avg.
Trick for average: Avg = Sum / Count
Quick revision:
  • Disk I/O = biggest cost
  • Index = speed booster
  • External sorting = for big data
  • Indexed join = best join method
  • Use AND smartly, OR carefully

2Query Processing and Optimization / 2 — Optimization

Core idea

  • Goal: find the most efficient way to execute a query.
  • Achieved by converting a query into multiple equivalent forms and choosing the lowest-cost plan.

Optimization process

  1. SQL → relational algebra
  2. Generate equivalent expressions
  3. Assign algorithms to operations
  4. Estimate the cost of each plan
  5. Choose the best (cheapest) plan

Evaluation plan

  • Represented as a query tree with annotations.
  • Specifies operations (select, join, project) and the algorithms used (linear scan, index scan, merge join, hash join).

Think of it as a step-by-step execution blueprint.

Cost estimation

Based on: relation size, intermediate result size, and available indexes. It uses cost formulas to compare plans.

Key insight: smaller intermediate results ⇒ faster queries.

Equivalence rules

Two expressions are equivalent if they give the same result.

Selection rules (σ)

  • Conjunction rule: σθ1∧θ2(E) = σθ1(σθ2(E))
  • Commutativity: σθ1(σθ2(E)) = σθ2(σθ1(E))

Join rules (⋈)

  • Commutative: E₁⋈E₂ = E₂⋈E₁
  • Associative: (E₁⋈E₂)⋈E₃ = E₁⋈(E₂⋈E₃)

Distribution rules

  • Selection over join: push the condition down if it uses only one relation → reduces data before the join.
  • Projection over join: keep only needed attributes early (must keep join attributes).

Set operation rules

  • Union (∪) & intersection (∩): commutative & associative.
  • Selection distributes over: union, intersection, difference.

Key optimization strategies

  • Push selection down: apply filters early to reduce tuples.
  • Push projection down: remove unnecessary columns early to reduce data size.
  • Optimal join order: join smaller relations first; statistics guide decisions.

Note: join order greatly affects performance.

Challenges in optimization

Problem: too many possible query plans → brute force means exponential time.

Solutions:

  • Space optimization: avoid duplicate sub-expressions, share common parts of the query tree.
  • Dynamic programming: store the best cost for sub-parts, ignore worse options early.

Result: optimization becomes feasible and fast.

Quick summary:
  • Equivalent expressions = same result
  • Push selection & projection early
  • Join order matters significantly
  • Dynamic programming avoids explosion of plans
  • Goal = minimum cost, maximum efficiency

3RDBMS Performance & Architecture

Core performance factors

  • Correctness: ensured by ACID properties. Transactions must update data accurately and safely.
  • Throughput: measured as TPS (transactions per second). Higher TPS = better performance.
  • Response time: time between query request and result. Lower response time = faster system.
  • Availability: measured by MTTF (mean time to failure). Higher MTTF = more reliable system.

Levels of optimization

  • Transaction level: concurrency control, query optimization, hardware support (e.g. RAID).
  • System level: hardware components — CPU, memory, disk, network.
  • Database level: how DB processes run on the system; resource allocation & scheduling.

Performance tuning

Goal: remove bottlenecks.

  • Hardware tuning: add more disks → faster I/O; increase memory → better caching; faster CPU → improved processing.
  • Database parameter tuning: increase buffer size → fewer disk accesses; proper checkpointing → faster recovery; optimise schema & indexes.

Scalability concepts

Definition: the ability to handle more data, more users, and more workload without losing performance.

Speedup

  • Use n× resources for the same task.
  • Ideal: speedup = n.
  • Reality: less than n due to startup overhead, resource contention, uneven workload.

Scaleup

  • Increase data + system size by n×.
  • Ideal: execution time remains the same (ratio = 1).
  • Reality: slight performance drop due to overhead.

RDBMS architectures

  • Centralized system: single machine, suitable for small systems.
  • Client-server architecture: front-end (client) — UI, SQL queries, reports; back-end (server) — SQL engine executes queries. Types: transactional query server, data server.
  • Parallel systems: multiple processors + disks connected via a fast network.
    • Interconnection types: bus (simple, low scalability), mesh/toroid (moderate scalability), hypercube (best — log n communication time).
    • Configurations: shared memory, shared disk, shared nothing (best scalability), hybrid.
  • Distributed systems: data spread across multiple locations. Types: homogeneous (same DB + schema), heterogeneous (different DB/schema).

Scaling strategies

  • Vertical scaling (scale up): increase the power of a single machine — easy to implement, works with the existing system; but a single point of failure, limited scalability, expensive upgrades.
  • Horizontal scaling (scale out): add more machines — high fault tolerance, better scalability, parallel processing; but complex management, data consistency challenges.

Modern techniques

  • Replication (master-slave): master handles writes, slaves handle reads.
  • Sharding: split data across machines, each handling a subset of data; improves performance & scalability.
Quick summary:
  • ACID → ensures correctness
  • TPS ↑ and response time ↓ = good system
  • Push bottlenecks out via tuning
  • Speedup ≠ perfect due to overhead
  • Horizontal scaling > vertical scaling (modern systems)
  • Sharding + replication = real-world scaling tools

4Non-Relational DBMS: NoSQL

What is Big Data?

  • Extremely large and complex datasets.
  • Traditional DBMS tools cannot handle it efficiently.

The 5 V's of Big Data

  • Volume: massive amount of data (TBs, PBs, etc.)
  • Variety: different data types (text, images, audio, video)
  • Velocity: speed of data generation and processing (e.g. real-time streaming)
  • Variability: data is inconsistent and changing
  • Veracity: data quality and accuracy may vary

What is NoSQL?

  • Non-relational database model.
  • Data is not stored in tables.

Why NoSQL?

  • Handles big data scale.
  • Supports real-time applications.
  • Manages complex data.

Key features

  • No fixed schema (flexible).
  • Horizontal scaling (scale-out).
  • Data replication (fault tolerance).
  • High performance for simple queries.

Limitations

  • No standard query language.
  • More coding required.
  • Weak ACID guarantees.

CAP theorem

Core idea: a distributed system cannot guarantee all three together:

  • Consistency (C): same data everywhere.
  • Availability (A): every request gets a response.
  • Partition tolerance (P): works despite network failures.
Important insight: in real systems, partition tolerance is mandatory. CP systems combine consistency + partition tolerance; AP systems combine availability + partition tolerance.

ACID vs BASE

  • ACID (RDBMS): strong consistency, reliable transactions.
  • BASE (NoSQL):
    • Basically available → system always responds.
    • Soft state → data may change over time.
    • Eventual consistency → data becomes consistent later.

Gossip protocol

  • Nodes share updates randomly.
  • Data spreads like "rumours".
  • Ensures eventual consistency.

Types of NoSQL databases

  • Key-value stores: data = (key, value) pairs — very fast and scalable, not suitable for complex data.
  • Document stores: data stored as JSON/XML — supports nested structures, flexible and widely used.
  • Column stores: data stored column-wise — efficient for large datasets, uses timestamps for versions.
  • Graph databases: data as nodes and edges — best for relationships (e.g. social networks).

Quick summary:
  • Big Data = 5 V's
  • NoSQL = flexible + scalable
  • CAP theorem → pick any 2 (with partition tolerance mandatory)
  • ACID vs BASE = strong vs eventual consistency
  • Graph DB = best for relationships
  • Document DB = most commonly used

5Widely Used DBMSs and Course Summarization

Core idea

  • Data stored in tables (relations).
  • Structure: rows → tuples, columns → attributes.
  • Relationships via primary key & foreign key.
  • Uses SQL for queries.

Types of RDBMS

  • Commercial (paid): Oracle Corporation (market leader ~48.8%), IBM (Db2), Microsoft (SQL Server), SAP (Sybase), Teradata.
  • Open source (free): PostgreSQL, MySQL, SQLite.

Market trends

  • Top databases: Oracle Database, MySQL
  • Fast-growing: PostgreSQL
  • Rapid rise: Snowflake
  • Widely used in mobile: SQLite

Specialized databases

  • Object-relational DB: uses pointers for relationships, avoids expensive joins. Example: Illustra.
  • Data warehousing: designed for large-scale analytics. Examples: Apache Hive, Teradata.

Relational vs NoSQL

  • Dominance: the top 4 databases are still relational — Oracle Database, MySQL, Microsoft SQL Server, PostgreSQL.
  • NoSQL leaders: MongoDB, Redis.
