1Transactions / 1

What is a transaction?

A transaction is a single logical unit of work in a database that performs:

  • Read operations
  • Write/update operations
  • Computations

Example — bank transfer (A → B, ₹50)

  1. Read balance of A
  2. Subtract ₹50 from A
  3. Add ₹50 to B
  4. Update both accounts

Challenges

  • System failures (crash, power loss)
  • Concurrent execution (multiple users accessing the same data)

ACID properties

Atomicity (all or nothing)

  • Either the complete transaction happens or nothing happens.
  • If a failure occurs → rollback.
  • Example: ₹50 deducted from A but not added to B → rollback required.

Consistency

  • The database moves from one valid state to another valid state.
  • Rules and constraints must always hold.
  • Example: the total balance of A + B stays the same before and after the transfer.

Isolation

  • Transactions run independently without interference.
  • Example: two users updating the same account should not overwrite each other.

Durability

  • Once committed, changes are permanent and survive crashes.
  • Example: after a successful transfer, the data remains even after a system crash.

Transaction states (lifecycle)

  • Active → transaction starts execution
  • Partially committed → last operation done, waiting to save permanently
  • Committed → successfully saved
  • Failed → error occurred
  • Aborted → changes rolled back
  • Terminated → end of transaction

Concurrent execution & schedules

Why concurrency?

  • Better CPU utilisation
  • Faster response time
  • Multiple users at the same time

Schedule: an ordered sequence of operations from multiple transactions. It must include all operations, and the order within each transaction must be preserved.

Types of schedules

Serial schedule

  • Transactions execute one after another.
  • Example: T1 → T2 or T2 → T1
  • Always correct but slow performance.

Serializable schedule

  • Concurrent but equivalent to serial execution.
  • Ensures correctness and efficiency.

Non-serializable schedule

  • Leads to inconsistency.
  • Problems: lost updates, incorrect data, "vanishing money".
  • Example: two transactions update the same account → one overwrites the other.

2Transactions / 2 — Serializability

Core concepts & assumptions

Transaction: a set of operations that modify the database. Example: updating an account balance, booking tickets.

ACID properties — every transaction should follow:

  • Atomicity → all or nothing
  • Consistency → valid state maintained
  • Isolation → no interference
  • Durability → permanent changes

Consistency assumption

  • Each transaction individually keeps the database consistent.
  • Errors inside a transaction are ignored in concurrency control.

Example of a wrong transaction: A → −50, B → +40 → inconsistent (logical error).

Serial execution

Transactions executed one by one, e.g. T1 → T2 → T3. Always consistent, but slow performance.

Serializability: a concurrent schedule is correct if it is equivalent to some serial schedule. Even if operations are mixed, the final result must match serial execution.

Types: conflict serializability (most important) and view serializability (rare, complex).

Conflict in instructions

Only Read (R) and Write (W) matter. Two operations conflict if:

  • They belong to different transactions
  • They access the same data item
  • At least one is a WRITE
Types of conflicts
Operation pairConflict?Reason
Read–ReadNoNo change in data
Read–WriteYesRead may get the wrong value
Write–ReadYesOrder matters
Write–WriteYesFinal value depends on the last write
T1: R(A), W(A) T2: W(A) → Conflict: Write-Write, Write-Read

Conflict serializability

  • Conflict equivalence: two schedules are equivalent if non-conflicting operations can be swapped to make them identical.
  • Conflict serializable: a schedule that can be converted into a serial schedule using swaps.

Important points:

  • Conflict serializable ⇒ always serializable
  • Serializable ≠ always conflict serializable
Schedule S: T1: R(A), W(A) T2: R(A), W(A) → If the order can be rearranged, the schedule is serializable.

Precedence graph (testing method)

Use a graph to check if a schedule is conflict serializable.

  • Nodes → transactions (T1, T2, …)
  • Edges (Ti → Tj) → if Ti executes first and conflicts with Tj
T1: W(A) T2: R(A) → Edge: T1 → T2
Acyclic rule (golden rule): a schedule is conflict serializable if and only if the graph has no cycles.
  • Case 1 — acyclic graph: T1 → T2 → T3 — serializable, valid execution.
  • Case 2 — cycle exists: T1 → T2 → T1 — not serializable, leads to inconsistency.

Topological sorting

If the graph is acyclic, perform a topological sort — it gives the equivalent serial order.

Graph: T1 → T2 → T3 Serial order: T1 → T2 → T3

Time complexity: precedence graph check = O(n²), where n = number of transactions.

3Transactions / 3 — Recoverability

Recoverability & consistency

Problem: system failures (crash, power loss) can occur during a transaction. If a failure happens after a write but before commit → inconsistent database.

Recoverable schedule

A schedule is recoverable if: when Tj reads data written by Ti, then Ti must commit before Tj commits.

Non-recoverable example: T8: W(A) (not committed yet) T9: R(A) → COMMIT T8: FAIL → ABORT

Problem: T9 has already committed using a wrong value. It cannot be undone → inconsistency.

Cascading rollbacks

When one transaction fails, others depending on it must also roll back.

T10: W(A) T11: R(A) T12: R(A) If T10 fails → abort, then T11 and T12 must roll back.

This chain reaction is called a cascading rollback (expensive).

Cascadeless schedule

Condition: if Tj reads Ti's data, then Ti must commit before Tj reads.

Safe example: T1: W(A) → COMMIT T2: R(A) No cascading rollback → safe and efficient.

Transaction Control Language (TCL)

Controls transaction execution in SQL.

  • COMMIT → saves all changes permanently
  • ROLLBACK → undoes changes
  • SAVEPOINT → creates a checkpoint inside a transaction, allowing partial undo
  • SET TRANSACTION → sets properties
COMMIT;
ROLLBACK;
SAVEPOINT sp1;
ROLLBACK TO sp1;
SET TRANSACTION READ ONLY;

Implicit commit: by default, each SQL statement auto-commits. This can be disabled, e.g. setAutoCommit(false).

View serializability

More flexible than conflict serializability — it accepts more schedules. Two schedules are view equivalent if they produce the same reads and the same final result.

Conditions for view equivalence

  1. Initial read: if Ti reads the initial value of Q in S, the same must happen in S′.
  2. Read-from relation: if Ti reads a value written by Tj in S, it must read from the same Tj in S′.
  3. Final write: the transaction doing the last write on Q must be the same.
T1: W(A) T2: W(A) Final write = T2 → any equivalent schedule must end with T2.

Key properties

  • Relation: conflict serializable ⇒ view serializable, but the reverse is not always true.
  • Blind write: a write without reading. T1: W(A), T2: W(A) → can be view serializable but not conflict serializable.
  • Complexity: checking view serializability is NP-complete — there is no efficient algorithm like the precedence graph.

Testing view serializability

Since a direct check is hard, use the elimination method:

  1. Identify the final write transaction.
  2. Fix it at the end of the serial order.
  3. Check read relationships.
  4. Eliminate invalid orders.

Example: if the final write on A is by T3, valid serial orders must end with T3.

4Concurrency Control / 1

Objectives of concurrency control

Goal: ensure schedules are conflict serializable, recoverable (preferably cascadeless), and follow the ACID properties.

Key insight

  • Conflict serializability → efficient to test (polynomial time)
  • View serializability → hard (NP-complete)

Hence, most protocols focus on conflict serializability.

Trade-off

  • More concurrency → better performance
  • More control → more overhead

Lock-based protocol (basics)

Locking is a mechanism to control access to data items. It ensures isolation in transactions.

Lock types

  1. Shared lock (S-lock): only read allowed; multiple transactions can share. Example: T1: S(A), T2: S(A) → allowed.
  2. Exclusive lock (X-lock): read + write allowed; only one transaction allowed. Example: T1: X(A), T2: S(A) → not allowed.
Lock compatibility matrix
Lock typeS-lockX-lock
S-lock✔✘
X-lock✘✘

Working

  • Transaction requests a lock
  • Lock manager checks compatibility
  • If compatible → granted
  • Else → transaction waits

Two-phase locking (2PL)

Ensures conflict serializability.

  • Growing phase: can acquire locks, cannot release locks
  • Shrinking phase: can release locks, cannot acquire new locks

Lock conversions: upgrade (S → X) only in the growing phase; downgrade (X → S) only in the shrinking phase.

Growing: S(A) → X(A) Shrinking: unlock(A)

Problems in locking

Deadlock

  • Circular waiting condition.
  • T1: X(A) → waiting for B; T2: X(B) → waiting for A. Both stuck forever → deadlock.

Starvation (livelock)

  • A transaction waits indefinitely while others keep getting locks.

Cascading rollback

  • If locks are released early, other transactions may read uncommitted data.
  • A failure then causes multiple rollbacks.

Special locking protocols

Strict 2PL

  • Hold all X-locks until commit/abort
  • Prevents cascading rollback
  • Ensures recoverability

Rigorous 2PL

  • Hold all locks (S + X) until commit
  • Strongest protocol
  • Transactions serialized by commit order
Trade-off
ProtocolSafetyConcurrency
Basic 2PLMediumHigh
Strict 2PLHighMedium
Rigorous 2PLVery highLow

Lock manager (implementation)

Role: controls all lock operations.

Lock table

Tracks which transaction holds a lock and which transactions are waiting.

Structure: each data item → linked list of granted locks and a waiting queue.

Functions

  • Grant locks
  • Block requests
  • Release locks
  • Handle rollback

On abort, all locks of that transaction are released.

5Concurrency Control / 2

Deadlock in concurrency control

A deadlock occurs when every transaction in a set is waiting for a resource held by another transaction in the same set.

T1: holds A → waiting for B T2: holds B → waiting for A → Circular wait → Deadlock
Key point: deadlocks are unavoidable. A DBMS must handle them using prevention, detection and recovery.

Deadlock prevention

Goal: never allow a deadlock to occur.

  1. Pre-declaration: the transaction locks all resources before starting. Hard to implement and reduces concurrency.
  2. Partial ordering: define a fixed order of accessing data, e.g. always lock A before B. Prevents cycles.
  3. Timestamp-based schemes — each transaction gets a timestamp (TS):
    • Wait-die (non-preemptive): older → younger = wait; younger → older = die (rollback).
    • Wound-wait (preemptive): older → younger = wound (kill the younger); younger → older = wait.
    • Important: restarted transactions keep the same timestamp → prevents starvation.
  4. Timeout scheme: wait for a fixed time; if not granted → rollback. May cause starvation.

Deadlock detection

Used when prevention is not applied.

Wait-for graph: nodes → transactions; edge (Ti → Tj) → Ti is waiting for Tj.

Golden rule: a cycle exists ⇨ a deadlock exists.
T1 → T2 → T3 → T1 → Deadlock T1 → T2 → T3 → Safe

Deadlock recovery

  • Break the cycle: roll back one or more transactions.
  • Victim selection: choose a transaction to roll back based on cost, work done and resources used.
  • Total rollback: abort completely and restart.
  • Partial rollback: roll back only to a safe point → more efficient.
  • Starvation prevention: track the rollback count to avoid repeatedly killing the same transaction.

Timestamp-based protocol

An alternative to locking: no waiting → no deadlocks.

Each transaction gets a timestamp TS(Ti), and the execution order is determined by timestamps.

Data item Q stores:

  • W-timestamp(Q) → last write
  • R-timestamp(Q) → last read

Read rule — if Ti wants to read Q

  • If TS(Ti) < W-timestamp(Q) → reject & rollback.
  • Else → allow the read.
  • Update: R-timestamp(Q) = max(R-timestamp(Q), TS(Ti)).

Write rule — if Ti wants to write Q

  • Case 1: TS(Ti) < R-timestamp(Q) → reject (violates order).
  • Case 2: TS(Ti) < W-timestamp(Q) → reject (obsolete write).
  • Otherwise → allow the write.
  • Update: W-timestamp(Q) = TS(Ti).

Advantages

  • No deadlock
  • Ensures serializability

Disadvantages

  • May cause cascading rollback
  • May lead to non-recoverable schedules
