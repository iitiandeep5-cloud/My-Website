Lecture 1: Relational Database Design / 1

Goals of a Good Database Design

A good database is not just about storing data — it should be accurate, efficient, and future-proof.

Key Goals:

  • Real-World Reflection: Database should represent real-life entities and relationships correctly. Example: Student–Course–Instructor relationships.
  • Future Compatibility: Should handle future data easily without redesign.
  • Minimum Redundancy: Avoid storing the same data multiple times.
  • Efficiency: Queries should run fast.
  • Data Integrity: Must maintain correctness using constraints (PK, FK, etc.).
  • Clarity & Simplicity: Easy to understand and maintain.
Trade-off More redundancy → faster queries. Less redundancy → better integrity. Designer must balance both.

Redundancy & Anomalies

Redundancy: Same data stored multiple times → leads to inconsistency.

Types of Anomalies:

  1. Insertion Anomaly: Cannot insert data without unrelated info. Example: Cannot add a new department unless an instructor exists.
  2. Deletion Anomaly: Deleting one record removes useful data. Example: Deleting last instructor → department info lost.
  3. Update Anomaly: Same data must be updated in multiple places. Example: Changing department building in many rows → risk of mismatch.

Normalization & Decomposition

Normalization: Process of organizing data to reduce redundancy and remove anomalies.

Decomposition: Breaking a big table into smaller tables.

Functional Dependency (FD) If attribute A determines B → written as A → B.
Example: Department → Building, Budget — each department has one fixed building & budget.

Normalization Chain: Functional Dependency → Decomposition → Less Redundancy → No Anomalies.

Quality of Decomposition

Not all decompositions are good.

Lossless Join (Correct Design) After splitting tables: Original Table = Join(Smaller Tables)
No data lost. No extra data generated.
Lossy Join (Bad Design) After join: extra rows appear OR some data is lost → leads to wrong results.

First Normal Form (1NF)

Rule: No complex or multi-valued attributes.

Conditions for 1NF:

  • Atomic Values (Indivisible): Each field contains a single value. E.g. "Full Name" → "First Name", "Last Name".
  • Single-Valued Attributes: Multiple phone numbers in one field → store in separate rows/table.
  • Non-Atomic Examples: Name = "Rahul Sharma"; CourseID = "CS101" (if CS & 101 needed separately).

Final Summary — Quick Revision
  • Good DB = Accurate + Efficient + Scalable.
  • Redundancy causes Insertion, Deletion, Update anomalies.
  • Use Normalization + Decomposition.
  • Functional Dependency: A→B.
  • Always aim for Lossless Join, avoid Lossy Join.
  • 1NF rules: Atomic values, no multi-valued attributes.

Lecture 2: Relational Database Design / 2

Goal of Good Relational Design

Main Objective: Design schemas that minimize redundancy and avoid anomalies (insertion, deletion, update).

Decomposition: If a table is not well-structured, split it into smaller tables.

Lossless Join (Very Important) A decomposition is correct only if: Original Table = Natural Join (Decomposed Tables) — no data loss, no extra tuples.
Example Bad Design: Student(Student, Dept, Building)
Decompose into: Student(Student, Dept), Dept(Dept, Building)
Joining gives original table → Lossless.

First Normal Form (1NF)

Rules: All values must be atomic (indivisible). No multi-valued attributes.

Functional Dependencies (FDs)

Definition A functional dependency is written as α → β.
Meaning: If two rows have the same α, they must have the same β.
Example: Department → Building — one department → one building.

Important Concept: FDs are based on business rules, not just observed data.

Trivial FD: (ID, Name) → ID — always true because RHS ⊆ LHS.

Keys (Formal Understanding)

  • Superkey: A set of attributes K such that K → All attributes in table (R) — uniquely identifies rows.
  • Candidate Key: Minimal superkey (no extra attributes).
Example Table: ID | Name | Email
Superkeys: (ID), (ID, Name), (ID, Email).
Candidate Key: (ID).

Armstrong's Axioms (FD Rules)

  1. Reflexivity: If β ⊆ α, then α→β. Example: (ID, Name) → ID.
  2. Augmentation: If α→β, then αγ→βγ. Example: ID → Name ⇒ (ID, Dept) → (Name, Dept).
  3. Transitivity: If α→β and β→γ, then α→γ. Example: Dept → Building, Building → City ⇒ Dept → City.

Closure of Functional Dependencies (F⁺)

Definition Closure = all possible FDs derived from given FDs. F⁺ = set of all inferred dependencies.
Example: Given A→B, B→C, then F⁺ = {A→B, B→C, A→C}.

Properties:

  • Soundness: Only correct dependencies are generated.
  • Completeness: All possible dependencies are generated.
Final Quick Revision
  • Goal: Reduce redundancy + avoid anomalies.
  • Use: Decomposition. Must ensure: Lossless Join.
  • 1NF: Atomic + Single-valued.
  • FD: α→β.
  • Superkey → determines all attributes; Candidate key → minimal superkey.
  • Armstrong Rules: Reflexivity, Augmentation, Transitivity.
  • Closure: F⁺ = all inferred FDs.

Lecture 3: Relational Database Design / 3

Functional Dependency (FD) Theory

A functional dependency is written as α→β. If two tuples have the same α, they must have the same β. Example: Dept → Building — one department → one building.

Armstrong's Axioms (Basic Rules)

  1. Reflexivity: If β ⊆ α, then α→β.
  2. Augmentation: If α→β, then αγ→βγ.
  3. Transitivity: If α→β and β→γ, then α→γ.

Derived Rules (Shortcuts)

  • Union: If α→β and α→γ, then α→βγ.
  • Decomposition: If α→βγ, then α→β and α→γ.
  • Pseudo-Transitivity: If α→β and γβ→δ, then αγ→δ. Example: A→B, CB→D ⇒ AC→D.

Closure Sets

  • Closure of FD Set (F⁺): All possible FDs derived from F.
  • Closure of Attributes (α⁺): All attributes determined by α.
Algorithm for α⁺ (very important)
  1. Start with α⁺ = α.
  2. For each FD (β→γ): if β ⊆ α⁺, add γ to α⁺.
  3. Repeat until no change.
Example Given: A→B, B→C.
Start: A⁺ = {A}. Add B → {A,B}. Add C → {A,B,C}.
Final: A⁺ = {A,B,C}.

Applications of Attribute Closure

  1. Testing Superkey: If α⁺ = all attributes → α is superkey.
  2. Testing Candidate Key: α is superkey and no subset of α is superkey.
  3. Testing FD: To check α→β, compute α⁺. If β ⊆ α⁺, then true.

Boyce-Codd Normal Form (BCNF)

Definition A relation is in BCNF if for every non-trivial FD α→β, α must be a superkey.
Violation Example Relation: Student, Course, Instructor. FD: Course → Instructor. Course is not a superkey → violates BCNF.

BCNF Decomposition Formula: If α→β violates BCNF: R1 = (α∪β), R2 = (R−(β−α)).

Example R(Student, Course, Instructor). FD: Course → Instructor.
Decompose: R₁(Course, Instructor), R₂(Student, Course).

Decomposition Properties

Lossless Join: Join(R1,R2) = Original Table. Condition: intersection must be superkey of at least one table.

Dependency Preservation: All FDs can be checked without joining tables.

  • BCNF → Lossless guaranteed.
  • BCNF → Dependency preservation not guaranteed.

Third Normal Form (3NF)

A relation is in 3NF if FD α→β is allowed when it is trivial, or α is a superkey, or each attribute in (β−α) is part of some candidate key.

Key Idea: 3NF is less strict than BCNF and allows some redundancy to preserve dependencies.

FeatureBCNF3NF
RedundancyMinimumSlight allowed
Dependency PreservationNot guaranteedGuaranteed
StrictnessHighModerate

Design Goals & Trade-offs

  • Goal: Remove redundancy, avoid anomalies.
  • More normalization → less redundancy.
  • More decomposition → more joins (slower queries).

Higher Normal Forms: BCNF may still have issues. Use 4NF for multi-valued dependencies.

Final Quick Revision
  • FD: α→β. Armstrong Rules: Reflexivity, Augmentation, Transitivity.
  • Derived Rules: Union, Decomposition, Pseudo-transitivity.
  • Closure: α⁺ → attributes, F⁺ → all dependencies.
  • BCNF: α must be superkey. 3NF: allows non-key → key dependency if part of candidate key.
  • Always ensure Lossless join. Dependency preservation: guaranteed in 3NF, not always in BCNF.

Lecture 4: Relational Database Design / 4

Attribute Closure (α⁺) & Applications

Definition: α⁺ = set of all attributes determined by α using FDs.

Algorithm (very important)
  1. Start: α⁺ = α.
  2. For each FD (β→γ): if β ⊆ α⁺, add γ to α⁺.
  3. Repeat until no change.
Example Given: A→B, B→C. Find A⁺:
Start {A} → add B → {A,B} → add C → {A,B,C}.
Final: A⁺ = {A,B,C}.

Applications:

  1. Superkey Test: If α⁺ = all attributes → α is superkey.
  2. Candidate Key Test: α is superkey and no subset of α is superkey.
  3. Check FD: To verify α→β, compute α⁺. If β ⊆ α⁺, then true.
  4. FD Closure (F⁺): All FDs derived using rules.

Extraneous Attributes

Definition: An attribute is extraneous if it can be removed without changing meaning.

LHS Extraneous In α→β, attribute A∈α is extraneous if (α−A)⁺ contains β.
Example: Given AB→C, A→C — B is extraneous → simplified: A→C.
RHS Extraneous In α→β, attribute A∈β is extraneous if α⁺ (using modified F′) still contains A.
Example: Given A→BC, A→B — C may be extraneous depending on inference.

Equivalence of FD Sets

Definition: Two FD sets F and G are equivalent if F⁺ = G⁺.

  • Covering: F covers G → F implies all dependencies in G. G covers F → G implies all dependencies in F.
  • Equivalence Condition: F covers G AND G covers F.
  • Insight: If only one covers, that set is stronger.

Canonical Cover (Minimal Set)

Definition A canonical cover (Fc) is a minimal FD set equivalent to F.

Properties: Same meaning (Fc⁺ = F⁺); no extraneous attributes; unique LHS (no duplicates).

Rule used: Union Rule — α→β and α→γ ⇒ α→βγ.

Algorithm (Step-by-Step):

  1. Combine FDs (Union Rule).
  2. Same LHS → merge.
  3. Remove extraneous attributes (LHS and RHS).
  4. Repeat until no change.
Example Given: A→B, A→C. Step 1 (Union): A→BC. Canonical form.

Note: Multiple canonical covers may exist depending on order of simplification.

Prime vs Non-Prime Attributes

  • Prime Attribute: Attribute ∈ any Candidate Key.
  • Non-Prime Attribute: Attribute ∉ any Candidate Key.
Example Relation (A, B, C). Candidate Key = (A, B). Prime → A, B. Non-prime → C.
Final Quick Revision
  • Attribute Closure: α⁺ = all attributes derived from α.
  • Superkey: α⁺ = all attributes. Candidate Key: minimal superkey.
  • Extraneous Attributes — LHS: remove if still determines; RHS: remove if still implied.
  • Equivalence: F⁺ = G⁺. Canonical Cover: minimal, no redundancy, unique LHS.
  • Prime = part of candidate key, Non-prime = not part.

Lecture 5: Relational Database Design / 5

Lossless Join Decomposition

Definition A decomposition is lossless if R = R1 ⋈ R2. After joining decomposed tables, we get the exact original table — no data loss, no extra tuples.
Lossy Join (Bad Case) Join creates extra rows (spurious tuples); original relationships are lost.
Example Original Table: Student, Course, Instructor.
Bad Decomposition: R₁(Student, Course), R₂(Course, Instructor).
If Course is not unique, join may produce wrong combinations (extra rows).

Conditions for Lossless Join

  1. Union Rule: R1 ∪ R2 = R — all attributes must be covered.
  2. Intersection Rule: R1 ∩ R2 ≠ ∅ — must have common attributes.
  3. Key Condition (most important): (R1∩R2) → R1 OR (R1∩R2) → R2 — common attributes must be a superkey of at least one table.
Example (Lossless) R(Student, Dept, Building). FD: Dept → Building.
Decompose: R₁(Dept, Building), R₂(Student, Dept).
Common attribute = Dept. Dept is key for R₁ → Lossless join.

Dependency Preservation

Definition A decomposition is dependency preserving if all FDs can be checked without joining tables.

Why important? Joins are time-consuming; efficient systems avoid unnecessary joins.

Formal Condition: (F1∪F2∪…∪Fn)⁺ = F⁺ — combined dependencies of decomposed tables equal the original dependencies.

Example Original FD: A→B, B→C.
Decomposition: R₁(A, B), R₂(B, C). Both FDs preserved separately → Dependency preserving.

Note: Some dependencies may not appear directly but are preserved using transitivity. Example: A→B, B→C ⇒ A→C.

Checking Dependency Preservation

Naive Method: Compute full closure F⁺ — very slow (exponential time).

Efficient Method — Attribute Closure To check α→β:
  1. Initialize: Result = α.
  2. Iterate — for each table Rᵢ: find Result ∩ Rᵢ, compute closure using FDs, intersect with Rᵢ, add new attributes to Result.
  3. Verify: if β ⊆ Result → Dependency preserved.
Intuition: Gradually collect attributes using decomposed tables, check if RHS can still be derived.

Key Practice Strategies

For Lossless Join: Check if common attributes = key. If yes → Lossless.

For Dependency Preservation: Use attribute closure and transitivity.

PropertyImportance
Lossless JoinMUST (no data loss)
Dependency PreservationPreferred (for efficiency)
Final Quick Revision
  • Lossless Join: R = R1 ⋈ R2
  • Conditions: Union = full attributes; Intersection ≠ ∅; Common attribute = superkey.
  • Dependency Preservation: (F1∪F2∪…)⁺ = F⁺ — no need for joins to check FDs.
  • Algorithms: Naive → F⁺ (slow). Attribute Closure → fast.
  • Key Idea: Always ensure Lossless join (mandatory) and Dependency preservation (preferred).
