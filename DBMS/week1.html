Lecture 1: Course Overview

What is DBMS?

A Database Management System (DBMS) is software used to store, manage, and retrieve data efficiently for an organization.

Key Requirements

  • Collection of interrelated data
  • Programs to process and manage data

Characteristics

  • Easy to use
  • Efficient
  • Reliable

Career Scope

  • Database Developer
  • Database Designer
  • Database Administrator (DBA)

Real-World Applications of DBMS

  • Banking & Finance: Net banking, UPI, Paytm, Google Pay
  • Reservation Systems: Railway & airline booking (e.g., IRCTC)
  • Education: ERP systems (admissions, marks, timetable)
  • E-commerce: Amazon, eBay, Snapdeal
  • Daily Apps: Email (Gmail, Yahoo), Social Media (Instagram, WhatsApp, Facebook)
  • Other Areas: HR, manufacturing, travel industry

File System vs DBMS

File-Based Storage (Old System): Data stored in files (CSV, text files).

Problems in File Systems

  • Data Redundancy: Same data repeated → waste of space
  • Data Inconsistency: Different files have different values
  • Data Access Difficulty: Hard to search and automate tasks
  • Data Isolation: Data scattered in multiple files
  • Integrity Issues: Rules (e.g., minimum balance) hard to enforce
  • Atomicity Problem: Transactions may fail midway (e.g., money deducted but not credited)
  • Concurrency Issues: Multiple users accessing same data → conflicts
  • Security Problems: Weak protection → risk of data theft

Why DBMS is Better?

  • Reduces redundancy
  • Ensures consistency
  • Provides security
  • Handles multiple users
  • Supports transactions (ACID properties)

Prerequisites for DBMS

Mathematics

  • Set Theory (union, intersection)
  • Relations & Functions
  • Propositional Logic (AND, OR, NOT)
  • Predicate Logic (∀, ∃)

Computer Science

  • Data Structures: Arrays, Linked Lists, Trees (BST, B-Trees), Hashing
  • Python Programming: For database connectivity & applications

Good to Know

  • Algorithms (sorting, searching)
  • C Programming
  • OOP Concepts (Java/C++)

Course Structure

Duration: 12 Weeks (60 Modules)

Breakdown:

  • Weeks 1–8: Application Programming (most important for placements)
  • Weeks 9–12: Database Design & Administration

Recommended Book: Database System Concepts by Silberschatz, Korth & Sudarshan (6th Edition)

Quick Summary

  • DBMS = Efficient data management system
  • Replaces file systems (fixes redundancy, security, consistency issues)
  • Used in banking, e-commerce, social media, etc.
  • Requires basics of math + data structures + programming
  • Course focuses first on applications, then advanced DB topics

Lecture 2: Why DBMS? / 1

Pervasiveness of Databases: Databases are everywhere in daily life, often unnoticed.

Everyday Examples

  • Mobile Communication: Stores call logs, locations, and network data via towers
  • Health Apps: Aarogya Setu tracks infection proximity
  • Vaccination Systems: COWIN stores vaccination status, dates, locations, and identity verification (Aadhaar/passport)

Key Idea: Databases silently power most digital services around us.

Basic Needs of Data Management

Every system (physical or digital) must fulfill these needs:

  • Storage: Store data permanently (e.g., bank records, employee data)
  • Retrieval: Quickly access stored data when needed
  • Transactions: Handle data changes safely (e.g., money transfer, ownership change)
  • Audit: Verify correctness of operations, detect fraud or errors
  • Archival: Store old data for future reference

Key Parameters of Modern Data Systems

  • Durability: Data should not be lost, even after failures
  • Scalability: Handle growth from hundreds to billions of users
  • Security: Protect against unauthorized access; level depends on application (normal vs military)
  • Retrieval Speed: Fast access, ranging from seconds to nanoseconds
  • Consistency: Database must always remain correct (e.g., no money should disappear in transfer)
  • Efficiency: Time efficiency, storage optimization, cost-effectiveness

Evolution of Data Management

A. Physical Era (Bookkeeping)

  • Data stored in registers and ledgers
  • Contributions:
    • Henry Brown → File cabinet invention
    • Herman Hollerith → Punch cards for computation
  • Problems: Easily damaged (fire, humidity), hard to scale, slow retrieval, poor security

B. Electronic Era

  • 1950s–60s: Punch cards, magnetic tapes
  • 1970s: Magnetic disks, COBOL language, CODASYL model, VisiCalc (first spreadsheet)
  • 1980s: Relational DBMS (RDBMS) introduced, SQL becomes standard, shift to distributed systems
  • 1990s: Internet enables global data access
  • 2000s–Present:
    • NoSQL databases handle unstructured data (images, videos)
    • Big Data & Data Science systems (Google Bigtable, Amazon)
    • Applications: Data Warehousing, Data Mining

Limitations of Flat File Systems (CSV/Spreadsheets)

  • Scalability Problem: Limited rows and size
  • Consistency Issues: Hard to maintain rules (constraints), requires manual coding
  • Limited Permissions: Basic password protection only, no proper multi-user roles

Quick Revision

  • Databases are used everywhere (mobile, health, payments)
  • Core needs: storage, retrieval, transactions, audit, archival
  • Key features: durability, scalability, security, consistency
  • Evolution: Physical → Electronic → RDBMS → NoSQL & Big Data
  • Flat files are limited in scalability, consistency, and security

Lecture 3: Why DBMS? / 2

Overview: A simple banking system is used to compare File-Based Systems and DBMS.

Main Operations

  • Open Account
  • Transfer Money
  • View Transaction History

Important Conditions

  • Balance Check: No transfer if balance is insufficient
  • Validation: Wrong account → transaction fails
  • Confirmation: Success message after transaction

File-Based (Python) vs DBMS (SQL)

Data Storage

  • File-Based System:
    • Uses accounts.csv (account details)
    • Uses ledger.csv (transactions)
  • DBMS:
    • Uses accounts table
    • Uses ledger table
    • Managed using SQL

A. Initialization & Setup

  • File-Based (Python):
    • Manual work required
    • Open files, read/write operations every time
    • More coding effort
  • DBMS (SQL):
    • Automatic handling
    • System already initialized
    • Less repetitive code

B. Transactions & Consistency

  • DBMS (SQL):
    • Commit Mechanism: Saves changes permanently
    • Rollback Mechanism: Cancels incomplete transactions, keeps data consistent
    • Example: If debit happens but credit fails → rollback restores balance
  • File-Based System:
    • No built-in safety
    • System crash → inconsistent data
    • Example: Money debited but not credited
    • Needs extra coding to handle this

Comparison Table

FeatureFile-Based (Python/CSV)DBMS (SQL)
ScalabilityHard to manage large dataEasily scalable
Execution TimeSlow (seconds/minutes)Fast (ms/µs)
PersistenceManual save → risk of lossAutomatic & reliable
RobustnessHard to recover corrupted filesBackup & recovery available
SecurityBasic OS-level securityAdvanced multi-level security
ProductivityMore coding effortEasier to manage
ArithmeticFlexible (Python libraries)Limited compared to Python
CostLow costHigher setup & maintenance cost

Conclusion: When to Use What?

  • Use DBMS When:
    • Large-scale applications
    • Multi-user systems
    • Need high speed, data consistency, security, reliability
  • Use File-Based System When:
    • Small projects (100–200 records)
    • Simple applications
    • Budget is low
    • No need for complex features

Quick Revision

  • Banking system = real-life DBMS example
  • File-based uses CSV, DBMS uses tables + SQL
  • DBMS supports Commit and Rollback
  • DBMS is faster, more secure, scalable
  • File system is cheaper, simpler, but less reliable

Lecture 4: Introduction to DBMS / 1

Levels of Abstraction: DBMS uses three levels to hide complexity and simplify usage.

Physical Level (Lowest)

  • Describes how data is stored
  • Stored as bits, bytes, files
  • Deals with storage structures and memory layout
  • Used by: System-level engineers

Logical Level (Middle)

  • Describes what data is stored
  • Defines tables (records), attributes (columns), relationships
  • Example: Customer(ID, Name, Balance)
  • Used by: Programmers & DB designers

View Level (Highest)

  • What the user actually sees
  • Shows only relevant data
  • Can hide sensitive information (e.g., salary)
  • Can show derived data (e.g., age from DOB)
  • Used by: End users

Schema vs Instance

Schema (Structure)

  • Blueprint/design of database
  • Like the "type" of a variable
  • Changes rarely
  • Types:
    • Physical Schema → storage level
    • Logical Schema → table structure

Instance (Data)

  • Actual data stored
  • Like the "value" of a variable
  • Changes frequently

Physical Data Independence

  • Changes in physical storage do not affect logical schema
  • Example: Changing disk type doesn't affect table structure

Data Models

Tools to describe data, relationships, and constraints.

Types

  • Relational Model (Most Important):
    • Data in tables
    • Rows = records, Columns = attributes
  • ER Model: Used for database design, shows entities & relationships
  • Other Models: Hierarchical, Network, Object-based, Graph (social networks), NoSQL (images, videos, unstructured data)

Database Languages

DDL (Data Definition Language)

  • Defines structure
  • Examples: CREATE TABLE, ALTER, DROP

Data Dictionary

  • Stores metadata
  • Contains table names, attributes, data types

DML (Data Manipulation Language)

  • Used to modify data
  • Examples: SELECT, INSERT, UPDATE, DELETE

SQL (Structured Query Language)

  • Combines DDL + DML
  • Most widely used language
  • Limitation: SQL is not Turing complete (cannot handle very complex logic alone)

Host Languages

  • SQL is used with Python, Java, C++
  • Reason: Handle complex logic outside DB

Database Design

Logical Design

  • Decide what data to store and how tables are structured
  • Balance business needs and efficiency

Physical Design

  • Decide storage methods and indexing (e.g., B-Trees)

Quick Revision

  • Three Levels: Physical → Logical → View
  • Schema = structure, Instance = data
  • Data Models: Relational (most important), ER, NoSQL
  • Languages: DDL → structure, DML → data operations
  • SQL is powerful but not fully programmable
  • Design = Logical (what) + Physical (how)

Lecture 5: Introduction to DBMS / 2

Database Design Parts: Database design has two main parts:

Physical Design

  • How data is actually stored
  • Includes: files, pages, indexing (e.g., B-Trees)

Logical Design

  • What data is stored and how it is structured
  • Includes: tables (schemas), attributes (columns), relationships

Logical Design Decisions

  • Based on business needs (what data is required)
  • Algorithmic efficiency (easy queries, performance)

Physical Data Independence

  • Changes in storage do not affect logical schema
  • Example: Changing storage disk → tables remain the same

Redundancy & Normalization

Redundancy

  • Same data stored multiple times
  • Example: Department budget repeated for every faculty

Problems (Anomalies)

  • Update anomaly → inconsistent data
  • Insert/Delete issues
  • Wasted storage

Normalization

Process of splitting tables into smaller related tables

Benefits:

  • Removes redundancy
  • Prevents anomalies
  • Improves consistency

Example: Separate faculty table and department table

Data Models

Relational Model

  • Data in tables
  • Atomic values (numbers, strings)

Object-Relational Model

  • Extension of relational model
  • Supports complex data types

XML (Extensible Markup Language)

  • Used for data exchange and hierarchical data
  • Example format: <name>John</name>

Database Engine

The core system that runs DBMS.

Storage Manager

  • Manages storage, retrieval, updates
  • Uses indexing and hashing

Query Processor

  • Converts SQL into execution plan
  • Tasks: query optimization, performance evaluation

Transaction Manager

  • Ensures transactions work as a single unit
  • Handles concurrency (multiple users) and consistency

Database Users & Roles

  • Naive Users: Use applications without DB knowledge (e.g., shopping apps)
  • Application Programmers: Build applications and interfaces
  • Analysts: Handle complex queries, build tools
  • Database Administrator (DBA): Controls entire database
    • Responsibilities: storage management, security, backup & recovery

Database Architecture Evolution

Centralized Systems

  • Single system
  • File-based (e.g., COBOL)

Client-Server RDBMS

  • Database = server, applications = clients
  • Examples: MySQL, Oracle

Parallel & Distributed Systems

  • Spread across multiple machines
  • Used in internet and cloud systems

NoSQL Systems

  • For unstructured data (images, videos)
  • Used in Big Data and Data Science

Quick Revision

  • Design = Logical (what) + Physical (how)
  • Redundancy causes anomalies → fixed by normalization
  • Models: Relational, Object-Relational, XML
  • Engine = Storage + Query + Transaction Manager
  • Users: Naive → Programmers → Analysts → DBA
  • Architecture: Centralized → Client-Server → Distributed → NoSQL
