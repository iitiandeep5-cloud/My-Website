Lecture 1: Access Control

Security Overview: Security ensures safe access, data privacy, and monitoring in applications.

Key Areas:

  • Access Control – Who can do what
  • Session Management – Keep user sessions safe
  • HTTPS – Secure connection
  • Logging & Analysis – Track actions & detect anomalies

Access Control

Definition: Mechanism to decide who can read, write, or modify data.

Why Needed: Protect sensitive info from unauthorized users.

Examples:

  • E-commerce: Protect personal data (phone, address, payment info)
  • Banking: Users cannot view each other's accounts
  • Education: Students see only their own grades

Levels of Access:

LevelDescription
Read-onlyView only
Read-WriteCRUD operations (Create, Read, Update, Delete)
Fine-grainedRestrict specific actions (e.g., modify but cannot delete)

Access Control Models

a) Discretionary Access Control (DAC)

  • Owner decides who can access their files/data.
  • Permissions: read, write, delete
  • Example: File sharing in Google Drive

b) Mandatory Access Control (MAC)

  • Central authority assigns strict permissions.
  • Users cannot share access.
  • Used in: Military, high-security systems

c) Role-Based Access Control (RBAC)

  • Access based on roles, not individual users.
  • Users can have multiple roles.
  • Supports hierarchies: higher role inherits permissions of lower roles.
  • Example:
    • Teacher → can grade students
    • HOD → Teacher permissions + department management
  • Benefit: Easy management when people change positions

d) Attribute-Based Access Control (ABAC)

  • Access based on user attributes (extra info).
  • Example: Only allow access during work hours or weekdays

Key Concepts in Implementation

Permissions vs Policies

TermDescription
PermissionsSimple allow/deny rules (single bit)
PoliciesComplex conditions (e.g., user must be bank employee AND access after 8 AM)

Principle of Least Privilege

  • Give only the minimal access needed for a task.
  • Benefits:
    • Higher security
    • Prevent accidental errors
    • Easier deployment

Privilege Escalation

  • Temporarily gaining higher privileges.
Linux Examples:
sudo apt update   # perform one action with higher privileges
su root            # switch user to root

Best Practices:

  • Use as last resort
  • Limit scope
  • Log every escalation

Enforcement Layers

LayerHow Access is ControlledExample
HardwarePhysical tokens, NFC, keysUSB token access
OSFile system permissions, memory protectionchmod in Linux
ApplicationRestrict access in DB or app modulesFlask decorators

MVC Enforcement: Controller is best for access checks

Flask Example:
from flask import Flask, redirect, url_for
from functools import wraps

app = Flask(__name__)

# Decorator to check login
def login_required(f):
    @wraps(f)
    def decorated_function(*args, **kwargs):
        if not user_logged_in:
            return redirect(url_for('login'))
        return f(*args, **kwargs)
    return decorated_function

@app.route('/dashboard')
@login_required
def dashboard():
    return "Welcome to Dashboard!"
Quick Recap
  • Access Control = Who can do what
  • Models: DAC, MAC, RBAC, ABAC
  • Key Principles: Least Privilege, Permissions vs Policies
  • Enforcement: Hardware, OS, Application
  • Best Practices: Limit escalations, use logging

Lecture 2: Security Mechanisms

Basic Security Approaches

ApproachDescriptionExample / Risk
Security by ObscurityHiding the app on a non-standard porte.g., port 1356 instead of 80. Bad idea — ports can be discovered easily
Host-based Access ControlRestrict access based on IP whitelistCommon in SSH. Risk: If a trusted machine is hacked, attacker gains access

Login & Password Management

Username/Password Authentication: Server prompts users for credentials.

Password Storage Best Practices:

  • Never store plain text — if server is hacked, passwords are exposed.
  • Use hashing → store a cryptographic hash (irreversible).
Example: Python password hashing
import hashlib

password = "MySecret123"
hashed = hashlib.sha256(password.encode()).hexdigest()
print(hashed)  # Store this hash, not the plain password

HTTP Authentication Mechanisms

HTTP Status Codes:

  • 401 Unauthorized → can try login
  • 403 Forbidden → access denied regardless
  • 404 Not Found → resource missing

a) Basic HTTP Authentication

  • Server sends: WWW-Authenticate header (with realm)
  • Client sends: Authorization header (username:password Base64 encoded)

Problems:

  • Base64 is reversible
  • Password sent in clear text
  • Logout requires closing browser

Example: Browser pop-up login

b) Digest Authentication

  • Secure variant using one-way hash functions (e.g., MD5)
  • Uses a nonce (number used once) to prevent replay attacks
  • Client sends a hash of (username + realm + password + nonce)

Benefit: Safer because token changes every request

Tokens & Certificates

MethodDescriptionExample
Token-based AuthenticationFor machine-to-machine; uses long, unguessable stringAPI calls between services
Client CertificatesDigital certificate proves client identityLike HTTPS server certificates, used in secure networks

Form-based Security

GET vs POST:

  • GET → data in URL, unsafe for passwords
  • POST → data in request body, safer

HTTPS required: Encrypts form data in transit

Example: Login form
<form action="/login" method="POST">
  Username: <input type="text" name="username">
  Password: <input type="password" name="password">
  <input type="submit" value="Login">
</form>

Cookies & Session Management

HTTP is stateless → server doesn't remember users automatically

Cookies:

  • Server sends Set-Cookie header
  • Client returns cookie on every request → session maintained

Server Controls:

  • Set timeout, delete cookies to log out users
  • Clients can use incognito mode to avoid saving cookies
Example (Flask session):
from flask import Flask, session

app = Flask(__name__)
app.secret_key = "secret_key"

@app.route('/login')
def login():
    session['user'] = 'Alice'
    return "Logged in!"

@app.route('/dashboard')
def dashboard():
    if 'user' in session:
        return f"Welcome {session['user']}"
    return "Please log in"

API Level Security

  • API Keys → for automated clients (no interactive login)
  • Each client gets a unique token
  • Token sent in every request header
  • Server can invalidate/expire keys if compromised
Example: Using API Key in a request
curl -H "Authorization: ApiKey abc123xyz" https://api.example.com/data
Quick Recap
  • Security Basics: Obscurity (bad), IP whitelist (risk)
  • Passwords: Store hashes, not plain text
  • HTTP Auth: Basic (unsafe), Digest (secure)
  • Tokens & Certificates: Machine auth / digital identity
  • Forms: POST + HTTPS
  • Sessions: Cookies maintain state
  • API Security: Use API keys, manage expiry

Lecture 3: Sessions

Session Management in Web Security

Definition & Purpose

Why needed: HTTP is stateless → server doesn't remember clients between requests.

Purpose:

  • Track client status (logged in or not)
  • Maintain shopping cart, preferences, or other client-specific info
  • Customize responses per client

Types of Sessions

TypeStorageNotes / Example
Client-sideCookie stores all session infoQuick, but insecure if cookie is tampered
Server-sideCookie stores only session ID; data on serverSafer, can store in database, file, or Redis
Redis backendIn-memory key-value storeLightweight, fast; good for temporary session storage

Cookies & Security

Cookies:

  • Sent by server using Set-Cookie header
  • Client sends it back on every request

Risks:

  • Users can tamper with cookies (e.g., change username to admin)

Protection:

  • Encrypt or sign cookies using a secret key
  • Store keys securely (not in source code, use config.py or environment variables)
Flask Example: Signing Cookies
from flask import Flask, session

app = Flask(__name__)
app.secret_key = "super_secret_key"  # Never commit this to source control

Implementation in Flask: Sessions are like Python dictionaries

Login Example
from flask import session

# Store username in session after login
session['username'] = 'Alice'
Logout Example
# Remove user info to log out
session.pop('username', None)
Decorator for Authentication
from functools import wraps
from flask import redirect, url_for

def login_required(f):
    @wraps(f)
    def decorated(*args, **kwargs):
        if 'username' not in session:
            return redirect(url_for('login'))
        return f(*args, **kwargs)
    return decorated

@app.route('/dashboard')
@login_required
def dashboard():
    return f"Welcome {session['username']}"

Decorators can chain checks, e.g., for roles:

  • @login_required @role_required('admin')

Major Security Risks

RiskDescriptionMitigation
Public ComputersUser forgets to log out → next user can access sessionAlways log out; use short session expiry
CSRFMalicious site triggers requests on another site using logged-in sessionUse CSRF tokens in sensitive forms (most frameworks handle this)
Wire SecurityData intercepted during transmissionAlways use HTTPS to encrypt client-server traffic
Quick Recap
  • Sessions: Solve HTTP statelessness, track user activity
  • Types: Client-side (cookie only), Server-side (cookie + server storage)
  • Security: Sign cookies, secure secret keys, use HTTPS
  • Flask Implementation: session dict, login_required decorator
  • Risks: Public machines, CSRF, intercepted traffic

Lecture 3: HTTPS

HTTP vs HTTPS

ProtocolPortData TransmissionSecurity
HTTP80Readable (plain text)Not secure
HTTPS443Encrypted using SSL/TLSSecure channel between client & server

Key Point: HTTPS prevents eavesdropping and tampering.

The Need for Security: The "Wire"

Wire Concept: Data travels over multiple links (WiFi, Ethernet, fiber optics).

Threat: Attackers can tap these links at coffee shops, office networks, or via splitters.

Risks of Tapping:

  • Information theft – passwords, personal data, credit cards
  • Data alteration – e.g., modifying a GET request to POST to change account info

Encryption and Shared Secrets

Goal: Convert readable data into a code only client and server understand.

Shared Secret / Key: A long binary number known only to the client & server.

Process: Even if attacker listens, complex math (like Diffie-Hellman) allows secure key sharing.

Simple XOR Example (illustrative only):
# Very basic example, not for real use
data = 0b1101
key  = 0b1011
encrypted = data ^ key
decrypted = encrypted ^ key
print(bin(decrypted))  # Outputs original data: 0b1101

Authentication & Chain of Trust

Server Authentication: Confirm you're talking to the real server (e.g., Gmail).

Trust via Certificate Authorities (CA): Root CA → Intermediate CA → Server certificate

Browser/OS Integration: Preloaded trusted root certificates.

Chain of Trust Verification: Browser implicitly trusts server if root is trusted.

Example: mail.google.com → Certificate from GTS CA → Root CA trusted by Chrome/OS

Specialized Certificates & Failure Points

Type / IssueDescription
Wildcard CertificatesCover multiple subdomains (*.iitm.ac.in → www.iitm.ac.in, academic.iitm.ac.in)
Stolen Root CertificatesAttackers can issue fake certificates browsers trust
DNS HacksBrowser usually blocks certificate mismatch
Old BrowsersMay not recognize newer root certificates

HTTPS: Impact & Trade-offs

Benefits:

  • Prevents wiretapping on public networks
  • Ensures data integrity and confidentiality

Negatives:

  • Slight performance overhead due to encryption
  • Encrypted data prevents caching by intermediate proxies → may affect load speed
Quick Recap
  • HTTP = plain text, HTTPS = encrypted
  • Wire threat: attackers can steal/modify data
  • Encryption: shared secret, converts readable data into secure bits
  • Authentication: chain of trust via CA certificates
  • Wildcard & potential failures: stolen roots, DNS hacks, old browsers
  • Trade-offs: security vs performance/caching

Lecture 4: Logging

Definition & Purpose

Logging: Recording all accesses and actions in an application.

Purpose:

  • Identify bugs, server errors, crashes
  • Gather usage statistics (site visits, popular pages, peak hours)
  • Optimize site performance based on patterns
  • Security monitoring → detect attacks or anomalies

Levels of Logging

LevelDescriptionNotes
Application-LevelBuilt into app; logs user actions, POST data, errorsCan feed data to analysis pipeline for insights
Server-LevelBuilt into web server (Apache, Nginx)Logs URLs, IPs, but limited detail (no POST body)

Security Applications of Logs

  • Detect attacks: SQL injection, brute force, malformed requests
  • Spot anomalous patterns: high traffic spikes, repeated 404s
  • Track server crashes and stack traces for fixing vulnerabilities

Technical Components of a Log

ComponentExample / Explanation
IP AddressSource of the request
TimestampExact date & time of access
HTTP Verb & URLGET / POST and resource accessed
Status Code200 (OK), 3xx (redirect), 4xx (client error), 404 (Not Found)
ReferrerPrevious URL (internal link)
Flask Example of Logging Requests
from flask import Flask, request
import logging

app = Flask(__name__)

logging.basicConfig(filename='app.log', level=logging.INFO)

@app.route('/login', methods=['GET','POST'])
def login():
    logging.info(f"IP: {request.remote_addr} | Method: {request.method} | URL: {request.url}")
    return "Login page accessed"

Log Management & Maintenance

  • Volume Control: High traffic → logs can fill disks
  • Log Rotation: Keep fixed number of files (e.g., last 10 logs), delete oldest
  • Cloud Facilities: Platforms like Google App Engine offer automated analysis & reporting

Data Analysis & Tools

  • Time-Series Analysis: Logs are timestamped → analyze performance during events (like exam openings)
  • Databases for Logs: RRDTool, InfluxDB → efficient storage & analysis
  • Use Cases: Detect traffic spikes, response times, error frequency

Core Security Principles

  • Knowledge Needed: Cryptography, SQL, OS vulnerabilities
  • Frameworks: Using well-tested frameworks is safer than building custom security
  • Continuous Monitoring: Security is ongoing → analyze logs regularly to fix emerging problems
Quick Recap
  • Logging = record accesses & actions for debugging, stats, optimization, and security
  • Levels: App-level (detailed), Server-level (basic)
  • Components: IP, timestamp, HTTP verb, status code, referrer
  • Security: Detect attacks & anomalies
  • Management: Log rotation, cloud analysis tools
  • Analysis: Time-series, specialized DBs
  • Principles: Use frameworks, monitor continuously
