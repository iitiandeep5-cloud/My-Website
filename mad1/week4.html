Lecture 1: Persistent Storage

Role of the Model

  • Handles data and business logic of the application.
  • Ensures persistent storage so data survives crashes/restarts.
  • Allows users to resume where they left off.

Structured Data Basics

  • Table → Collection of related data (like a sheet).
  • Row → One complete record (e.g., one student).
  • Column/Cell → Specific data field (e.g., name, marks).

Unique Identifiers (IDs)

  • Every record must have a unique ID.
  • Examples: Roll number, Student ID.

Importance:

  • Avoids confusion (same names possible).
  • Enables efficient data retrieval & linking.
  • Supports validation (correct format checking).

Data Redundancy

  • Repetition of the same data (e.g., address multiple times) is:
    • Inefficient
    • Unrealistic

Solution: Store data once and use references (IDs).

Relationships & Joins

  • Data across tables is connected using IDs.
  • A join table links records.

Example: Student ID + Course ID → shows enrollment.

Data Identification Patterns

  • IDs often follow fixed formats:
    • Student ID → MAD001
    • Course ID → EE1001

Best Practice:

  • Use simple integer keys (1, 2, 3...).
  • Faster and more efficient.

Example: Student Gradebook

Students Table

  • ID: MAD001, MAD002 (Unique)
  • Name: Can repeat
  • Other info: Address, hostel, room

Courses Table

  • Course ID: EE1001, AM1100
  • Course Name: Usually unique
  • Extra: Department, year

Student–Course Table (Join Table)

Student IDCourse IDMarks
MAD001BT101078

Meaning: Student MAD001 scored 78 in BT1010.

Tools for Data Modeling

  • Spreadsheets: Google Sheets, Microsoft Excel, LibreOffice Calc.
  • Used for:
    • Visualizing data
    • Designing tables before databases

Quick Revision Summary

Model = data + logic
Use tables (rows + columns) to organize data
Always use unique IDs
Avoid data repetition
Use joins to connect tables
Prefer integer keys for efficiency

Lecture 2: Mechanisms For Persistent Storage and Relational Databases

Data Representation in Python

Lists & Tuples

  • Lists → Store entities (students, courses).
  • Tuples → Store relationships (student–course mapping).

Problem with Strings

  • Typos and case issues.
  • Cannot distinguish same names.
  • Not scalable.

Solution → Keys (IDs)

  • Assign unique IDs (numeric/string).
  • Ensures uniqueness and compact storage.
  • Reduces errors.

Class-Based Modeling (OOP)

  • Classes in Python: Store structured data using variables (e.g., self.name).
  • ID Handling:
    • Can use class variable (idnext).
    • Better: let database assign IDs (handles concurrency safely).

Advantages:

  • Add custom functions (e.g., full name generator).
  • Easily extend fields (hostel, address, etc.).
  • More organized and flexible than lists.

Persistent Storage Methods

  • Problem: Memory data is lost after program/server stops.
  • Serialization
    • Using Python's pickle.
    • Saves objects to disk and reloads them later.
    • Preserves exact structure.
  • Tabular Files
    • Formats: CSV, TSV.
    • Simple and widely used.
  • Limitations: CSV struggles with special characters (commas). Limited flexibility.
  • Spreadsheets
    • Tools: Excel, Google Sheets.
    • Easy for visualization.
  • Drawbacks: Hard to manage relationships across sheets. Not powerful like databases.

Relational Databases (SQL)

  • Structure: Tables → Rows + Columns.
  • Strong mathematical foundation.

Stored Procedures

  • Predefined database operations.
  • Simplify complex tasks.

Atomic Operations

  • "All or nothing" execution.
  • Prevents partial data errors.

SQL vs NoSQL Databases

Structured Databases (SQL)

  • Fixed schema (same columns in every row).
  • Strong validation.
  • Faster and reliable.

Unstructured / Semi-structured (NoSQL)

  • Flexible schema (different fields allowed).
  • Examples: MongoDB, CouchDB.

When to Use NoSQL:

  • When data varies across entries.
  • Example:
    • Hosteller → needs mess info.
    • Day scholar → needs local address.
  • Add fields without affecting whole database.

Quick Revision Summary

Use IDs (keys) instead of names.
Classes → better structure than lists.
Memory data is temporary → use storage methods.
CSV/Sheets → simple but limited.
SQL → structured, reliable, atomic.
NoSQL → flexible, real-world adaptable.

Lecture 3: Relations And ER Diagram

Core Purpose of Databases

Beyond Storage

  • Databases are not just for storage.
  • They store data and represent relationships.

Tabular Structure

  • Tables → Overall data.
  • Rows → Individual records.
  • Columns → Attributes (fields).

Database Structure & Identifiers

Unique Identifiers: Every record must be uniquely identifiable.

  • Humans prefer patterns (e.g., roll numbers).
  • Computers only require uniqueness.

Primary Key (PK): Unique ID for each row (usually integer).

  • Ensures:
    • No duplicates.
    • Fast retrieval.
    • Easy indexing.

Foreign Key (FK): A field that links to another table's Primary Key.

  • Used to connect tables.

Types of Relationships

One-to-One (1:1)

  • One record ↔ one record.
  • Examples:
    • Student ↔ Roll Number.
    • Email ↔ Message ID.
  • Often can be merged into one table.

One-to-Many (1:M)

  • One record ↔ many records.
  • Examples:
    • One hostel → many students.
    • One folder → many emails.

Many-to-Many (M:N)

  • Many records ↔ many records.
  • Examples:
    • Students ↔ Courses.
    • Emails ↔ Labels.
  • Requires a joint table.

Entity-Relationship (ER) Diagrams

Used to visually represent database structure.

Components:

  • Entities: Objects (Student, Course, Customer).
  • Notation: Crow's Foot Notation.

Crow's Foot Symbols

  • | → One.
  • ≡ (three lines) → Many.
  • ○ → Zero (optional).

Constraints

  • Mandatory: Must exist (exactly one).
  • Optional: May or may not exist (zero or more).

Practical Example (E-commerce)

  • Customer ↔ Order
    • Each order → exactly one customer.
    • A customer → zero or many orders.
  • Order ↔ Shipment
    • Each shipment → one order.
    • One order → zero or many shipments.

Implementation & Tools

  • ER diagrams can be converted into:
    • Database schemas.
    • Code structures.
  • Tools: app.diagrams.net (draw.io). PowerPoint / presentation tools.

Quick Revision Summary

Database = data + relationships.
Use Primary Keys for uniqueness.
Use Foreign Keys to connect tables.
Three relationship types: 1:1, 1:M, M:N.
ER diagrams help visualize structure.
Crow's Foot notation shows relationships clearly.

Lecture 4: SQL

Introduction to Relational Databases

Origin

  • Developed at IBM in the 1970s.

Basic Structure (Tabular)

  • Table → Complete dataset.
  • Columns (Fields) → Attributes (e.g., name, ID).
  • Rows (Records) → Individual entries (e.g., one student).

Database Keys & Indexing

Primary Key (PK)

  • Unique identifier for each row.
  • Usually an integer (fast access).
  • Faster than searching by names.

Foreign Key (FK)

  • Connects one table to another.
  • Refers to the Primary Key of another table.

Indexing

  • Improves search speed on non-PK fields.
  • Example: roll number, course ID.
  • Makes queries faster.

Structured Query Language (SQL)

  • Definition: Language used to query and manage databases.
  • Features:
    • English-like syntax.
    • Strict rules (syntax-sensitive).
    • Can be verbose.
    • Based on mathematical logic.

Data Joining Techniques

Inner Join: Combines rows from two tables based on matching condition.

student.hostelId = hostel.ID

Cartesian Product: All combinations of two tables.

  • Size = N × M.
  • Problem: Can become huge and slow.

Performance Note

  • Complex joins → slower queries.
  • Must be used carefully.

Constructing Complex Queries

Aliasing

  • Short names for tables.
  • Example: students → s.
  • Reduces typing.

Multi-Step Queries

  • Combine multiple operations into one query.
  • Example: Find names of students in a course using:
    • Student table.
    • Course table.
    • Enrollment table.
  • SQL handles it in one statement.

The "Model" in Applications (MVC)

Persistence: Data stored permanently on disk. Survives server restart.

Storage Options

  • CSV files.
  • Spreadsheets.
  • SQL databases.
  • NoSQL databases.

Separation of Concerns

  • Model ≠ View.
  • Model → handles data.
  • View → handles UI.
  • Model does not deal with HTML/UI.

Flexibility: Can change database (e.g., MySQL → SQLite). No need to change rest of application.

Quick Summary

Relational DB = tables (rows + columns).
Use Primary Keys for uniqueness.
Use Foreign Keys for relationships.
Indexing improves speed.
SQL = query language (strict but powerful).
Joins combine data (watch performance).
Model = data layer, independent of UI.
