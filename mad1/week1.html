Lecture 1: What is an App?

What is an Application?

An application (app) is a software program designed to perform a specific task.

  • Earlier usage: The term "app" referred to any software (desktop or mobile).
  • After smartphones (e.g., Apple iPhone): The term evolved to mean small, downloadable programs.
  • Today: An app is a focused tool solving a specific problem (e.g., chatting, editing, browsing).

Common Types of Applications

Browsers

  • Used to access web applications.
  • Examples: Google Chrome, Mozilla Firefox, Microsoft Edge, Safari.
  • Very important for web development.

Productivity & Social Apps

  • Help in daily tasks and communication.
  • Examples: Microsoft Word (document editing), Instagram, X (social interaction).

Text Editors vs Word Processors

  • Text Editors
    • Handle plain text.
    • Used for coding.
    • Examples: Visual Studio Code, Sublime Text, Vim.
    • Features: Syntax highlighting, auto indentation.
  • Word Processors
    • Used for formatted documents.
    • Example: Microsoft Word.
    • Features: Bold, italics, highlights, rich formatting.

Terminal / Command Line

  • Used to run programs and manage systems.
  • Important for developers.

Desktop Applications

  • Run on computers (Windows, Mac, Linux).
  • Usually work offline.
  • Use local storage (files, data).

Development

  • Built using SDKs (Software Development Kits) and APIs (Application Programming Interfaces).
  • Often OS-specific (e.g., Windows app may not work on Linux).
Key idea: Full-featured and powerful applications.

Mobile Applications

  • Platforms: Smartphones & tablets.
  • Interaction: Touch, voice/audio, camera gestures.
  • Constraints: Less RAM, lower processing power, battery limitations.

Ecosystem

  • Apple: Uses Swift, strong ecosystem integration.
  • Android: Larger market share, supports cross-platform frameworks.

Connectivity

  • Most apps are internet-based.
  • Connect to servers for real-time data.

Web Applications

  • Run inside a browser.
  • No installation needed.

Key Features

  • Platform-independent (works on any OS).
  • Uses browsers as interface.
  • Processing can happen on server or client (browser).

Examples: Gmail, online editors.

Why Web Apps Matter

  • Work across Windows, Linux, Mac.
  • No OS dependency.
  • Easy to deploy and access.
  • Web development is the main focus of most courses.

Final Summary

TypeRuns OnKey Feature
DesktopComputerOffline, powerful
MobilePhoneTouch-based, battery constraints
WebBrowserPlatform-independent

Lecture 2: Components of an App

Core Components of an Application

Every application is built using three main layers:

Storage (Where data is stored)

  • Cloud Storage
    • Data stored on remote servers.
    • Accessible from anywhere.
    • Example: Gmail stores emails on cloud servers.
    • Features: Hidden internal structure, optimized for fast search and retrieval.
  • Local Storage
    • Data stored on user's device.
    • Works even without internet.
    • Examples: Microsoft Outlook (proprietary files), Mozilla Thunderbird (formats like maildir/mbox).

Computation (Processing / Logic)

  • Also called business logic.
  • Defines how data is processed and used.
  • Example (Email app): Search emails by sender, date, or keywords.
  • Key idea: Happens on-the-fly (real-time processing).

Presentation (User Interface)

  • How data is shown to users.
  • Includes formatting text/images and organizing views (e.g., inbox, unread emails).
  • Goal: Make data easy to read and interact with.

Application Platforms & Paradigms

A paradigm is a way of thinking or designing how applications work.

Desktop Paradigm

  • Uses KVM (Keyboard, Video, Mouse).
  • Based on desktop metaphor: files, folders.
  • Features: Large screens, full control, traditional interface.

Mobile Paradigm

  • Uses touchscreen instead of mouse/keyboard.
  • Features: Small screen, app-based design, sensors (voice, camera, gyroscope, tilt).
  • Focus: Small, focused apps.

Web-Based Paradigm

  • Runs via browser and internet.
  • Data stored in cloud (data centers).
  • Key advantage: Access from any device, anywhere.
  • Example: Gmail works seamlessly on phone and laptop.

Embedded Platforms

  • Designed for specific tasks only.
  • Examples: Digital cameras, smartwatches, smart appliances (fridge, microwave).
  • Features: Limited interface, single-purpose.
  • Note: Some modern embedded platforms are becoming smarter.

Course Focus

  • Main focus: Web-based applications.
  • Reasons:
    • Platform-independent.
    • Accessible anywhere.
    • Widely used in real-world systems.

Final Quick Revision

3 Core Layers

  • Storage → Data
  • Computation → Logic
  • Presentation → UI
PlatformKey Feature
DesktopKVM, powerful
MobileTouch + sensors
WebCloud + browser
EmbeddedSingle-purpose
One-Line Summary: Every application = Data (Storage) + Logic (Computation) + UI (Presentation) running on a specific platform.

Lecture 3: Client-Server and Peer-to-Peer Architecture

Client–Server Architecture: A widely used model where roles are clearly separated.

Core Components

  • Server
    • Stores data.
    • Handles requests.
    • May perform computations.
    • Example: Gmail servers store emails.
  • Client
    • Requests data from server.
    • Usually represents end-user actions.
    • Example: Browser requesting a webpage.
  • Network
    • Acts as a communication channel.
    • Transfers requests (client → server) and responses (server → client).
    • Important: Does not modify data, only transfers it.

Key Characteristics

  • Separation of roles: client and server are conceptually separate, even if running on the same machine.
  • Machine clients: clients are not always humans (e.g., antivirus checking updates automatically).

Examples

  • Email: Server stores emails; client reads/manages emails.
  • Databases: Application acts as client; server stores and returns data.
  • Messaging: Example: WhatsApp. Server collects messages and sends them to receiver.
  • Web Browsing: Client = browser; server = website server; uses URL to fetch data.

Advanced Architecture

  • Multiple servers used for database, web hosting, caching.
  • Also uses load balancing to distribute traffic.

Peer-to-Peer (P2P) Architecture: No fixed client/server roles; all devices are equal peers.

Core Concept: Every node acts as both client and server.

Key Characteristics

  • Symmetry: You download and upload simultaneously.
  • Decentralization: No central authority; network runs collectively.
  • Fault Tolerance: System continues even if some nodes fail; new leader can be elected if needed.

Examples

  • File Sharing: BitTorrent, where users both download and share files.
  • Blockchain: Decentralized trust system used in Bitcoin.
  • Distributed Storage: Examples include IPFS, where data is stored across multiple devices and encrypted for security.

Client–Server vs Peer-to-Peer (Comparison)

FeatureClient–ServerPeer-to-Peer
ControlCentralizedDecentralized
RolesFixed (client/server)Equal peers
ReliabilityDepends on serverHigh fault tolerance
SecurityEasier to manageMore complex

Suitability

  • Client–Server: Best for sensitive data. Example: Email (users trust central servers).
  • P2P: Best for sharing large distributed data. Example: File sharing.

Node Hierarchy in P2P

  • Not all nodes are equal in practice.
  • Some nodes have higher bandwidth and act as major data providers.

Final Summary

  • Client–Server = centralized, controlled, structured.
  • P2P = decentralized, distributed, resilient.
One-Line Revision: Client–Server = request–response model. P2P = everyone shares everything.

Lecture 4: Software Architecture

Introduction to Design Patterns

What is a Design Pattern?

  • A design pattern is a reusable solution to common software design problems. It is not code, but a strategy or blueprint.
  • Purpose
    • Represents "best practices" used by experienced developers.
    • Saves time by avoiding reinventing solutions.
    • Helps in better planning and structured thinking.
Key Idea: Not the only solution, but a proven and reliable one.

Model–View–Controller (MVC) Paradigm

A very popular software architecture pattern. It divides an application into three main parts:

Model (Data Layer)

  • Represents data and metadata.
  • Handles storage, retrieval, and indexing.
  • Example (Email app): Emails, sender, receiver, timestamp, attachments.
  • Can use databases (MySQL, SQLite), NoSQL, or even simple files.

View (User Interface)

  • What the user sees and interacts with.
  • Not just visual: includes GUI, keyboard interface, voice/audio systems.
  • Example: Inbox UI showing emails.

Controller (Logic Layer)

  • Handles user actions.
  • Controls how data is modified.
  • Example: Delete email, archive message, move to folder.

MVC Workflow

Flow: User interacts → Controller → Model → View → User.

Important Rule:

  • View cannot directly modify Model.
  • Everything goes through Controller.

Closed Feedback Loop: Continuous cycle: User → Controller → Model → View → User.

Benefits

  • Separation of concerns.
  • Cleaner and organized code.
  • Easier debugging and maintenance.
  • Scalable applications.

Origin: Introduced in 1979 with Smalltalk.

Alternatives to MVC

Other similar patterns include:

  • MVP (Model–View–Presenter).
  • MVA (Model–View–Adapter).
  • HMVC (Hierarchical MVC).

Choosing a Pattern: Depends on programming language, platform (web/mobile/desktop), and developer preference.

Modern Perspective

  • Some consider MVC outdated in certain cases.
  • Still very useful for understanding and structuring applications.

Course-Specific Focus

  • Platform: Focus on web applications.
  • Architecture: Uses client–server model.
  • Design Pattern: Uses MVC architecture.
  • Technologies: Central servers; web technologies like Hypertext (HTML) for display.

Final Quick Revision

MVC Components

  • Model → Data.
  • View → UI.
  • Controller → Logic.

Workflow: User → Controller → Model → View → User.

Key Benefit: Separation of concerns = clean design.

One-Line Summary: MVC = Divide application into Data + UI + Logic for better structure.

Lecture 5: Introduction To The Web

Web as a Platform

Why Web is Important

  • The web is the primary platform for modern applications.
  • Works across Windows, Mac, Linux, phones, tablets, and PCs.
  • Platform-independent: no need to worry about device type.

Web as a "Universal OS"

  • Acts like a cross-platform operating system.
  • Hides hardware differences (keyboard, touchscreen, sensors).
  • Developers build once → works everywhere.

Development Considerations

  • Some tasks are easy on the web, others are hard or impossible.
  • Trade-offs include storage cost, network usage, and data center cost.

Evolution of Networking

Circuit-Switched Networks (Old)

  • Used in early telephone systems (1890s).
  • Requires dedicated connection.
  • Problem: Bandwidth is wasted even when no data is sent.

Packet-Switched Networks (Modern)

  • Data is broken into small packets.
  • Sent only when needed.
  • Benefits: Efficient use of network, multiple users share same connection.

Data Neutrality

  • Network does not care about data type (text, video, audio, images).
  • All treated equally.

Foundations of the Internet

Early Networks

  • ARPANET (1960s, US Defense).
  • Private networks by IBM, Xerox, DEC.
  • Problem: Networks could not communicate easily.

Protocols (Solution): Rules for formatting data, addressing, and error handling.

Internet Protocol (IP)

  • Standardized in 1983.
  • Enables communication between different networks.
  • Core idea: "Connect all networks together."

Transmission Control Protocol (TCP)

  • Works on top of IP.
  • Ensures reliable data delivery.
  • Retries if data is lost.
  • Adjusts speed automatically.

Addressing System

  • IP Address: Unique number for each machine (e.g., 192.168.1.1).
  • Domain Name System (DNS): Converts names into IP addresses.
    • Example: apple.com → IP address.
    • Easier for humans to remember.

World Wide Web (WWW)

Origin: Invented in 1989 by Tim Berners-Lee at CERN.

Key Concepts

  • Hypertext: Text with formatting and embedded instructions.
  • Hyperlinks: Links to other documents/pages.

Internet vs Web

  • Internet = Network of computers.
  • Web = System of linked documents.

Evolution: Web 1.0 → Web 2.0

Web 1.0 (Early Web)

  • Static web pages.
  • Simple text, limited styling.
  • Problems: No interactivity, browser conflicts (e.g., Netscape vs Internet Explorer).

Web 2.0 (Modern Web)

  • Dynamic content (after ~2004).
  • Pages generated in real-time.
  • Example: Personalized feeds, user-specific data.

HTTP Evolution

  • Originally for text transfer.
  • Now supports images, videos, PDFs.
  • Became a general data transport protocol.

Client-Side Power

  • Modern browsers are powerful.
  • Use JavaScript for interactivity.
  • Enables smooth UI and real-time updates.

Final Quick Revision

Networking: Circuit-switched → inefficient. Packet-switched → efficient.

Internet Basics: IP → addressing. TCP → reliability. DNS → name conversion.

Web Evolution: Web 1.0 → static. Web 2.0 → dynamic.

One-Line Summary: The web is a universal platform built on packet-switched networks using IP, TCP, DNS, and HTTP to deliver dynamic applications.

Lecture 6: How does the Web work?

What is a Web Server?

  • Any computer connected to a network can act as a web server, provided it has proper server software.
  • Examples: Apache HTTP Server, Nginx.

Functions of a Web Server

  • Listens for incoming requests.
  • Finds requested data (file/page).
  • Sends response back to client.

Performance Factors

  • Network speed.
  • CPU and memory.
  • Storage capacity.
  • Client-side computation.

Networking Mechanics: Ports & Packets

Ports

  • A port is a communication channel.
  • Range: 0 to 65,535.
  • Common example: Port 80 → Web (HTTP).

Listening

  • Server software listens on a fixed port.
  • Waits for incoming requests.

OS vs Web Server

  • Operating System (OS)
    • Handles network connections, packet receiving, and port management.
    • Receives packets and sends them to the correct application.
  • Web Server
    • Works at a higher level.
    • Understands what the request means.
    • Example: "Send index.html."

Communication Protocols

What is a Protocol? A set of rules for communication between devices.

HTTP (Hypertext Transfer Protocol)

  • Main protocol of the web.
  • Features: Text-based, easy to read/debug, defines request and response format.

HTTP Headers

Contain information such as:

  • Requested file.
  • Language preferences.
  • Supported formats.

Hypertext & Links

Hypertext

  • Text with embedded instructions (HTML).
  • Example: Formatting (bold, color), links.

Links (Hyperlinks)

  • Connect one document to another.
  • When clicked: Browser sends new request to server.

Request–Response Cycle

Core Working of the Web — Step-by-step flow:

  • 1. Client Request: Browser sends request (data + headers + port).
  • 2. OS Processing: Receives packet, identifies port, sends to correct server application.
  • 3. Server Processing: Finds requested resource, prepares response.
  • 4. Server Response: Sends back HTML page, image, video, etc.

Final Quick Revision

Key Concepts: Server = listens + responds. Port = communication channel. HTTP = communication protocol.

Flow: Client → OS → Server → Response → Client.

One-Line Summary: The web works through a request–response cycle using HTTP over ports, where servers listen and send data back to clients.

Lecture 7: Simple Web Server

Core Tools & Commands

Shell Scripting (Bash)

  • Servers can be written using Bash (Bourne Again Shell).
  • Used to interact with Unix/Linux systems via the command line.

echo Command

  • Prints output to STDOUT (screen/output stream).
  • In servers: used to send HTTP response (headers + data).

Netcat (nc)

Acts as a simple server tool.

nc -l 1500
  • -l → listen mode.
  • Listens for incoming connections on a port.

Piping (|)

Connects output of one command to another.

echo "Hello" | nc -l 1500
  • Output of echo goes into nc.

curl

  • Tool to send HTTP requests manually.
  • Used for testing servers without a browser.
curl http://localhost:1500

Server Logic & Structure

Infinite Loop: while true keeps the server running continuously.

Dynamic Content: $(date) generates real-time data, making the server dynamic.

Port Usage

  • Uses port 1500 instead of 80.
  • Reason: avoids conflicts and simplifies testing.

Shebang Line

  • #!/bin/bash
  • Meaning: tells the OS to use the Bash interpreter.

HTTP Protocol Basics

URL (Uniform Resource Locator)

  • Structure: protocol://server/path.
  • Example: http://localhost:1500/.

HTTP Status Codes

CodeMeaning
200OK (success)
301Moved permanently
404Not found

HTTP Versions

  • HTTP/1.1: Most widely used, requires Host header.
  • HTTP/2: Faster, supports multiple requests.
  • HTTP/3: Newer, still evolving.

Request–Response Cycle

Client Request: Includes:

  • Method: GET → fetch data.
  • Path: / → root.
  • Headers: Extra info like User-Agent, Accept.

MIME Types: Define data format:

  • text/html
  • image/png
  • application/json

Blank Line Rule

  • Headers and body must be separated by \n\n.
  • Without this, client cannot understand the response.

Server Response: Includes status line (e.g., 200 OK), headers, and body (actual data).

Localhost

  • Special address: 127.0.0.1 (IPv4), ::1 (IPv6).
  • Refers to your own computer.

Final Quick Revision

Tools: Bash → scripting. echo → output. nc → server. curl → client.

Key Rules: Port = communication channel. HTTP = protocol. \n\n separates headers and body.

Flow: curl → request → nc server → response.

One-Line Summary: A simple web server can be built using Bash + Netcat, where HTTP requests are handled via a continuous loop and responses are sent using standard output.

Lecture 8: What is a Protocol?

Definition & Role of a Protocol

  • Protocol = set of rules for communication between two systems.
  • Simple idea: an agreement on how to talk.
  • Human analogy: just like greetings or handshakes, computers also need rules to understand each other.
  • Why needed: Without protocols, systems cannot interpret messages even if connected.
  • Protocols define: Request format, Response format, Supported data types, Communication behavior.

HTTP (Hypertext Transfer Protocol)

Key characteristics:

  • Text-based → easy to read and debug.
  • Uses headers (metadata) for details like accepted language, encoding formats, response types, caching rules.

Status codes:

  • 200 → OK (success)
  • 404 → Not Found
  • 500 → Server Error
  • 300s → Redirection/warnings

HTTP Methods

  • GET → retrieve data (e.g., opening a webpage).
  • POST → send large or complex data (e.g., forms, emails in Gmail).
  • PUT → update data.
  • DELETE → remove data.
  • Common in APIs and CRUD operations.

Server Behavior & Conventions

Simple server (Python):

python -m http.server
  • Starts a server on port 8000.
  • Directory convention: If a folder is requested, server looks for index.html.

Debugging tool:

curl -v http://localhost:8000
  • Shows request headers, response headers, and full communication.

Data Identification (MIME Types)

  • Content-Type: tells browser how to interpret data.
    • Examples: text/html → webpage, application/pdf → PDF.
  • MIME Types: identify type of file/data.
    • Example: application/x-sh → shell script.
  • Content-Length: size of response in bytes.
  • Last-Modified: timestamp of last update.
    • Benefit: avoids reloading unchanged data, improves efficiency.

Final Quick Revision

  • Protocol → rules for communication.
  • HTTP basics → text-based, uses headers + status codes.
  • Methods → GET (fetch), POST (send), PUT (update), DELETE (remove).
  • Important headers → Content-Type, Content-Length, Last-Modified.
One-Line Summary: Protocols define communication rules, and HTTP uses methods, headers, and status codes to enable structured data exchange between client and server.

Lecture 9: Performance of a Website

Latency (Delay in Communication)

  • Definition: Latency = time between sending a request and receiving a response.
  • Physical limits:
    • Speed of light in vacuum ≈ 3×10⁸ m/s.
    • Speed in cables ≈ 2×10⁸ m/s.
  • Examples:
    • 1000 km → ~5 ms.
    • Chennai ↔ Delhi (~2000 km) → ~20 ms round trip.
  • Impact:
    • If each request waits for response: max ≈ 50 requests/sec.
    • Latency limits speed even with fast computers.

Bandwidth & Response Size

  • What server sends: Not just file, but also HTTP headers, CSS, JavaScript.
  • Bandwidth example:
    • 100 Mbps ≈ 10 MB/s.
    • If 1 KB per request → max ≈ 10,000 requests/sec.
  • Real-world case:
    • Even simple pages (e.g., Google homepage) ≈ 100 KB per request.
    • Due to scripts, tracking, dynamic content.

Scaling for High Traffic

  • Massive traffic: Large services handle ~60,000 requests/sec.
  • Bandwidth need: Requires ~80 Gbps → impossible for a single server.
  • Solution: Distribution.
    • Use multiple data centers worldwide.
    • Load distributed geographically.

Memory (RAM) & Concurrent Users

  • Problem: Each connection uses memory.
    • Example: 1 connection → 6 MB.
    • 2 million users → 12 TB RAM (impossible).
  • Solution: Horizontal scaling.
    • Use many smaller servers.
    • Example: 1000 servers × 12 GB RAM.
  • Key idea: Don't build one big machine; build many small machines.

Storage Requirements

  • Massive data scale: Search engines store hundreds of billions of pages.
  • Storage needed: ~100 petabytes.
  • Hardware requirement: Hundreds of thousands of disks.
  • Efficient retrieval systems required.

Summary of Web Foundations

  • Platform: Web is OS-independent, universal platform.
  • Protocols: HTTP → communication, HTML → presentation.
  • Real challenge: Easy: build a basic server. Hard: build a scalable system.
  • Key insight: Scaling is not just hardware; requires better algorithms, protocols, and smart system design.

Final Quick Revision

Constraints:

  • Latency → delay.
  • Bandwidth → capacity.
  • Memory → concurrent users.
  • Storage → data size.

Scaling solution: Distributed systems + multiple servers.

One-Line Summary: Web scalability is limited by latency, bandwidth, memory, and storage, and solved using distributed systems instead of single powerful machines.
