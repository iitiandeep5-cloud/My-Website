Lecture 1: Application Testing

Core Concept of Testing

Definition: Testing is the process of checking whether a system behaves according to its requirements or specifications.

Purpose:

  • Verify functionality (meets design intent)
  • Handle corner cases and invalid inputs
  • Check performance (e.g., response < 100 ms)
  • Ensure proper installation/setup
  • Evaluate usability (user-friendly)

Requirements: Predefined goals are set by the user or designer, and tests are built to satisfy these goals.

Types of Testing

Static Testing (No execution):

  • Code is not run.
  • Examples: Code reviews, proof checking, equivalence checking.
  • Used to find logical errors, poor design, missing initialization.

Dynamic Testing (Execution-based):

  • Code is executed with inputs.
  • Most common type.
  • Includes input-output testing, handling invalid inputs, crash recovery testing.

Testing Approaches ("Box" Methods)

White Box Testing:

  • Full knowledge of internal code.
  • Pros: Deep and detailed testing.
  • Cons: Focus on unnecessary details, breaks abstraction.

Black Box Testing:

  • Only inputs/outputs (APIs) visible.
  • Pros: Real-world testing, clean abstraction.
  • Cons: Hard debugging, misses internal corner cases (e.g., overflow).

Grey Box Testing:

  • Hybrid approach.
  • Tester starts as black-box, then uses internal info for debugging.
  • Requires developer–tester collaboration.

Regression Testing

Definition: Ensures new changes do not break existing features.

Key Terms:

  • Regression: Old feature stops working after change.
  • Test Suite: Set of automated tests run after updates.
  • Versioning (V1 vs V2): Breaking changes → release new version, maintain old version for users.

Code Coverage Metrics

Definition: Measures how much code is executed by tests.

Types:

  • Function Coverage: Every function is called at least once.
  • Statement Coverage: Every line of code executed.
  • Branch Coverage: Every decision path (if/else) tested.
  • Condition Coverage: Every boolean condition tested (true & false).

Important Rule: 100% Coverage ≠ Bug-Free Code.

Coverage measures execution, not correctness. Bugs can still exist in logic.

Examples

Car Analogy:

  • Specs: Petrol, X people, Y speed.
  • Test: What happens if diesel is used?
  • Checks correctness and failure handling.

Exam Software:

  • Must respond to clicks quickly.
  • Example: Move to next question in <100 ms.
  • Tests performance and usability.

Function Example (foo):

  • Case 1: foo(1,1) → 100% Statement Coverage (not sufficient).
  • Case 2: foo(1,1) + foo(1,0) → 100% Branch Coverage.
  • Case 3: foo(0,1) + foo(1,0) → 100% Condition Coverage (may not execute all branches).

Key Insight:

  • Condition coverage ≠ Branch coverage.
  • Branch coverage ≠ Full correctness.
Final Revision Summary
  • Testing ensures correctness, performance, and usability.
  • Two main types: Static & Dynamic.
  • Three approaches: White, Black, Grey Box.
  • Regression testing prevents breaking old features.
  • Coverage metrics: Function, Statement, Branch, Condition.
  • 100% coverage does not guarantee bug-free code.

Lecture 2: Levels Of Testing

Requirements Gathering (Design Phase)

Definition: Before coding, define what the system should do and its scope.

Stakeholders: Users of the system include:

  • Students
  • Teachers
  • Administrators

Types of Requirements:

Functional Requirements (What the system does): Specific actions and features.

  • Examples:
    • Student registers for a course
    • Administrator updates database
  • In code:
    • Controllers = logic
    • Views = user interface

Non-Functional Requirements (How the system behaves): Focus on experience and quality.

  • Examples:
    • Page color, font, logo
    • Performance and scalability

Language Ambiguity: Natural language can be unclear.

Example: "update registration" → Does this mean add, delete, or modify?

Solution – Use Cases: Real-world scenarios clarify behavior.

Example: Student logs in → selects course → clicks register → confirmation shown.

Unit Testing

Definition: Testing small individual components (such as a function or controller).

Key Concepts:

Isolation: Test each unit separately using dummy data or a fake database.

  • Example: To test "add course," the student must exist in a dummy database.

Test-Driven Development (TDD):

  • Process:
    1. Write test → fails
    2. Write code → passes
    3. Test passes successfully

Regression Testing: Unit tests become part of a test suite and are re-run after every change.

Example Code (Python-like):
def test_add_course():
    student = DummyStudent(id=1)
    result = add_course(student, "ML")
    assert result == "Course Added"

Integration Testing

Definition: Testing the interaction between modules.

Example Modules:

  • Student system
  • Payment gateway
  • Admin panel

Common Problems: Modules may work alone but fail together due to:

  • Dependency conflicts
  • Poor communication

Continuous Integration (CI): Every code commit runs tests automatically to detect issues early.

Tools:

  • GitHub Actions
  • GitLab CI

System Level Testing

Definition: Testing the complete system in a real environment.

Key Areas:

  • Black Box Testing: Test from the user perspective without internal code knowledge.
  • Non-Functional Testing: Performance under load and scalability.

Example: 1000 users log in simultaneously → check response time.

Browser Automation: Tools simulate real user actions:

  • Click buttons
  • Fill forms
  • Verify HTML

Example Checks:

  • Login button exists
  • Input fields present
Example (Selenium-like):
driver.get("http://app.com/login")
assert driver.find_element("name", "username")

User Acceptance Testing (UAT)

Definition: Final testing by real users before release.

Types:

  • Beta / Pilot Testing: Limited release to selected users.
  • Intelligent Feedback: Detailed bug reports.

Example:

  • Bad: "App crashed"
  • Good: "App crashed when clicking submit after empty form"

Concepts & Code Summary

Key Concepts:

  • Requirements → Controllers + Views
  • HTTP Methods:
    • GET → Fetch data/page
    • POST → Submit data

Validation: Check invalid inputs

  • Example: Empty form → error message
  • HTML Verification: Ensure required elements exist

Key Methodology – Test-Driven Development (TDD): Flow: Write Test → Fail → Write Code → Pass

Important Notes

  • Testing happens at multiple levels: Unit → Integration → System → UAT
  • Dummy data is crucial for isolation
  • Continuous Integration ensures early bug detection
  • Real users validate final usability
Final Quick Revision
  • Requirements = Functional + Non-functional
  • Unit Testing = Small components
  • Integration Testing = Module interaction
  • System Testing = Full application testing
  • UAT = Real user validation
  • TDD = Test first, then code

Lecture 3: Test Generation

API-Based Testing

Definition: Testing using the API (Application Programming Interface) instead of the user interface.

Focus:

  • Endpoints
  • Requests and responses

Single Source of Truth: Use OpenAPI (Swagger) specifications. The same file can generate:

  • Stub code
  • Test cases

Key Capabilities: Define query parameters, authentication, and request body. Tests can be automatically generated.

Use Cases:

  • Import API definitions → auto-generate tests
  • Record API traffic → inject error cases
  • Help beginners using pre-defined testing patterns
Example (Python – requests):
import requests

response = requests.get("http://api.com/hello")
assert response.status_code == 200
assert "Hello" in response.text

Abstract vs Executable Tests

Abstract Test: Human-readable test description, not code.

Example: "Send request to / and check if response contains 'Hello world'"

Executable Test: Actual coded test.

Example (PyTest):
def test_homepage(client):
    response = client.get("/")
    assert "Hello world" in response.data.decode()

Key Idea:

  • Abstract → Easy to understand
  • Executable → Runs automatically

Model-Based Testing

Definition: System is modeled as a Finite State Machine (FSM).

State-Based Testing: Example states:

  • Not logged in
  • Logged in
  • Password reset

Test all transitions:

  • Login → Logout
  • Reset → Login

Advantages:

  • Automatic test generation
  • Covers all system flows

Generic Nature: Same abstract tests can work across frameworks such as Flask, Django, and Laravel.

UI / GUI Testing

Definition: Testing the user interface (frontend).

What to Test:

  • HTML structure (semantics)
  • CSS styling
  • User interaction

Challenges:

  • CAPTCHA blocks automation
  • Dynamic UI behavior

Tools:

  • Selenium: Automates real browser, simulates clicks, typing, navigation
  • Requests library: Simple API calls (no browser)
Example (Selenium):
from selenium import webdriver

driver = webdriver.Chrome()
driver.get("http://app.com")
assert "Login" in driver.page_source

Security Testing

Goal: Prevent crashes (DoS attacks) and data corruption.

Testing Approaches:

  • Black Box: No knowledge of system, simulates real attacker
  • White Box: Full code knowledge, more powerful testing

Common Attacks:

  • SQL Injection: Inject malicious SQL queries. Example: ' OR '1'='1. Can bypass login if not handled properly.
  • Fuzz Testing (Fuzzing): Send random inputs to crash system, break validation, and find hidden bugs.
Example (Simple fuzzing idea):
import random
import string

random_input = ''.join(random.choices(string.ascii_letters, k=100))
response = requests.post("http://api.com/login", data={"username": random_input})

Summary of Concepts

TopicKey Idea

Executable TestCode-based

Important Points

  • API testing is faster than UI testing.
  • Abstract tests improve clarity.
  • FSM ensures full coverage of states.
  • Selenium enables real browser testing.
  • Always test for SQL Injection and fuzzing.
Final Quick Revision
  • API testing uses OpenAPI specifications.
  • Abstract → description, Executable → code.
  • Model-based testing = state transitions.
  • UI testing uses Selenium.
  • Security testing includes SQL Injection and fuzzing.

Lecture 4: Pytest

Introduction to Pytest

Definition: Pytest is a testing framework in Python, serving as an alternative to unittest.

Philosophy:

  • Opinionated → follows fixed conventions.
  • Automatically handles test discovery and execution.

Benefits:

  • Less boilerplate code.
  • Easy test writing.
  • Reduces developer confusion.
  • Advanced features: fixtures, monkeypatching.

Basic Mechanics & Assertions

assert Statement: Core of Pytest.

assert 2 + 2 == 4   # Pass
assert 2 + 2 == 5   # Fail

If condition is false → AssertionError.

Test Discovery Rules:

ElementNaming Rule
Filetest_*.py or *_test.py
Functionstarts with test_
Classstarts with Test

Output Symbols:

SymbolMeaning
.Pass
FFail

Pytest also shows expected vs actual values.

Testing Exceptions & Environment

pytest.raises: Used to check exceptions.

import pytest

def test_error():
    with pytest.raises(ZeroDivisionError):
        x = 1 / 0

Temporary Directory (tmpdir): Creates a temporary folder, auto-deleted after test.

def test_file(tmpdir):
    file = tmpdir.join("test.txt")
    file.write("Hello")
    assert file.read() == "Hello"

Test Fixtures

Definition: Reusable setup for tests.

Example:
import pytest

@pytest.fixture
def sample_data():
    return {"name": "John"}

def test_name(sample_data):
    assert sample_data["name"] == "John"

Key Points:

  • Fixture runs before test.
  • Cannot be called directly.
  • Passed as parameter.

Testing Flask Applications

client Fixture: Simulates browser behavior.

Setup & Teardown using yield:
import pytest
from app import create_app

@pytest.fixture
def client():
    app = create_app()
    with app.test_client() as client:
        yield client  # setup before, cleanup after

Testing Endpoints:

GET Request:
def test_home(client):
    response = client.get("/")
    assert b"Welcome" in response.data
POST Request:
def test_login(client):
    response = client.post("/login", data={
        "username": "admin",
        "password": "123"
    }, follow_redirects=True)

    assert b"Dashboard" in response.data
Helper Functions:
def login(client):
    return client.post("/login", data={
        "username": "admin",
        "password": "123"
    })

Not treated as a test (no test_ prefix).

Importance of Automated Testing

Benefits:

  • Confidence in system design.
  • Detects regressions.
  • Useful in grading systems.

Limitation: 100% coverage ≠ Bug-free code.

Tests may miss edge cases. Continuous testing is necessary.
