Lecture 1: Application Frontends

Introduction

The frontend is the user-facing part of an application – what the user sees and interacts with.

  • Usually accessed via a web browser.
  • Can also be:
    • Native apps (direct hardware access)
    • Embedded interfaces (e.g., Google Assistant using HTTP without a screen)

Core Design Concepts

  • UI (User Interface): Actual buttons, forms, menus, and controls.
  • UX (User Experience): Overall ease, flow, and feel of using the application. Critical for retention.

Web Standards:

Most web frontends rely on three pillars:

  1. HTML: Structure and content
  2. CSS: Styling & layout (frameworks like Bootstrap, Tailwind)
  3. JavaScript: Interactivity; originally optional, now essential for dynamic apps

Frontend Implementation Approaches

(1) Fully Static Web Pages

  • How it works: Pages are precompiled; server just serves files.
  • Pros: Very fast, high performance; great caching.
  • Cons: Hard to personalize or adapt at runtime; minor changes may require rebuilding the site.
  • Tools/Examples: Jekyll, Hugo, Next.js

(2) Runtime (Server-Side) Generation

  • How it works: Server generates pages dynamically per request (e.g., using Flask, WordPress).
  • Pros: Flexible, easy to implement dynamic content/templates.
  • Cons: Heavy server load; database bottlenecks possible; performance drop (~100× fewer requests per second vs static pages).
Example Code (Python Flask):
from flask import Flask, render_template
app = Flask(__name__)

@app.route('/')
def home():
    user = {"name": "John"}
    return render_template('index.html', user=user)

if __name__ == "__main__":
    app.run(debug=True)

index.html can use {{ user.name }} to personalize content.

(3) Client-Side Computation

  • How it works: Browser executes JavaScript; server only provides data updates.
  • Pros: Reduces server load; reusable components/widgets (navigation bars, modals).
  • Cons: Requires more client resources; security risks (data exposure, XSS).
  • Examples: Single Page Applications (SPAs) like React, Vue.js, Angular.
React Example:
function Greeting({ name }) {
  return <h1>Hello, {name}!</h1>;
}

Evolution: Led to Node.js, allowing JavaScript to run on backend.

Server Performance & Security

Performance:

  • Static pages: Apache/Nginx can handle 10,000–20,000 requests/sec.
  • Dynamic pages: Drops to ~100 requests/sec.

Security Considerations:

  • Always validate client inputs.
  • Protect against JavaScript vulnerabilities (XSS, data leaks).

ApproachProsConsExamples
StaticFast, cacheableNo runtime personalizationJekyll, Hugo, Next.js
Server-SideFlexible, dynamicHeavy server loadFlask, WordPress

Final Insight

Frontend development balances performance, flexibility, and security.

  • Static sites → best for speed and caching.
  • Server-side rendering → best for dynamic personalization.
  • Client-side computation → best for interactive, modern applications.

Lecture 2: Asynchronous Updates

Traditional Web Model (Late 80s/Early 90s)

  • Every user action required a full page request to the server.
  • The server sent a complete HTML page back.
  • Browser had to parse and render the entire page even if only a small part changed.

Issues:

  • Network/Server Load: Headers, footers, and menus were resent unnecessarily.
  • Poor UX: Full-page refreshes felt slow and disruptive.

Asynchronous Updates

  • Only part of the page is updated, while the rest stays as is.
  • Happens in the background, so it doesn't block the initial page rendering.

Key Concept: Asynchronous = updates happen outside the critical path of page display.

AJAX (Asynchronous JavaScript and XML)

Definition: Early way to update pages dynamically without full reloads.

Purpose: Servers send structured data, not entire HTML pages.

Note: "XML" in AJAX is just a structured format; JSON is commonly used today.

Example – Animal Form:

  • Traditional: Clicking "Cat" reloads entire page (menus + content).
  • AJAX: Clicking "Cat" fetches only cat data, updates a specific section of the page.
Modern Example (fetch + JSON):
fetch('/api/animal/cat')
  .then(response => response.json())
  .then(data => {
    document.getElementById('animal-info').innerText =
      `Name: ${data.name}, Habitat: ${data.habitat}`;
  });

Document Object Model (DOM)

Definition: A tree-like representation of the webpage stored in memory.

Allows programmatic manipulation of elements.

JavaScript is the primary language for DOM manipulation in browsers.

Key Capabilities:

  • Retrieve Elements:
const paragraphs = document.querySelectorAll('p');
paragraphs.forEach(p => alert(p.nodeName));
  • Dynamically Update Content:
window.onload = function() {
  const h1 = document.createElement('h1');
  const text = document.createTextNode('Big Head');
  h1.appendChild(text);
  document.body.appendChild(h1);
};

No page reload needed.

Implications for Development

Advantages:

  • Flexibility: Use loops, iterators, and object composition directly in browser.
  • Better UX: Updates happen smoothly without page reloads.

Cautions:

  • Increased Complexity: Can make frontend logic harder to understand and maintain.
  • Developers must balance power vs. maintainability.

The shift from traditional full-page reloads to asynchronous updates (AJAX + DOM manipulation) transformed web applications, enabling smoother user experiences and more efficient data handling.

Lecture 3: Browser/Client Operations

Browser Fundamentals

1. HTML Rendering

  • Purpose: Display web content for the end user.
  • Behavior: Browsers usually follow conventions (e.g., <h1> is large), but HTML specifications only require semantic meaning, not exact visuals.

2. Cookies and Sessions

  • Function: Browsers must store and send cookies to servers for session management and authentication.
  • Example: Logging into Gmail keeps you signed in via cookies.

3. Text-Mode Browsers

  • Definition: Browsers without a GUI, operating in command-line mode.
  • Limitations:
    • Cannot render images, complex JavaScript, or advanced styling.
    • Only display raw HTML.
  • Examples: Lynx, w3m.

4. Design Principles & Accessibility

  • W3C Guidelines:
    • Avoid using only color or font size to convey meaning.
    • Ensures content is usable on minimal browsers or screen readers.
  • Separation of Concerns:
    • HTML: Structure and semantic meaning.
    • CSS: Styling and visual presentation.
    • Benefits: Improves accessibility and flexibility.
  • CSS Accessibility:
    • Proper CSS usage allows browser choice on styling.
    • Better readability for users with visual impairments.

5. JavaScript & Client-Side Execution

  • Core Points:
    • Standard language for interactivity and dynamic content.
    • Works with the DOM to create/manipulate content not originally in HTML.
  • Scripting Engines:
    • V8 (Chrome) – fast and memory-efficient.
    • Other engines: Firefox, Safari.
    • Mostly API-compatible.
  • Resource Impact:
    • JavaScript runs on client CPU and sometimes GPU.
    • Heavy scripts may block browser or hang tabs.
    • Modern browsers sandbox tabs to prevent full crashes.
Example – DOM Update:
document.getElementById('title').innerText = "Hello, World!";

Updates content without a page reload.

6. Machine Clients and APIs

  • Non-human users: IoT devices, sensors, robots.
  • Interaction: Use standard HTTP APIs instead of custom protocols.
  • Limitation: Usually cannot execute JavaScript; just send/receive structured data.

Example: Temperature sensor posts JSON to /api/temperature:

{
  "device_id": "sensor_01",
  "temperature": 28.5
}

7. Advanced & Emerging Technologies

  • Transpilation: Convert code from other languages into JavaScript to run in browsers.
  • Brython: Run Python 3 in the browser; JS engine interprets Python code.
  • WebAssembly (WASM): Binary instruction format for high-performance web apps.
    • Can run C/C++/Rust code in browsers.
    • Use cases: 3D editing, online office suites.
Example (Emscripten converts C++ → WASM):
#include <iostream>
int main() { std::cout << "Hello WebAssembly!"; }

8. Native Mode Applications

  • Definition: Web apps behave like desktop/mobile apps.
  • Access: File systems, cameras, messaging APIs (requires permissions).
  • Security: Standard JavaScript is sandboxed; permissions needed for native features.
  • Example: Visual Studio Code
    • Runs in a Chromium shell.
    • Uses HTML, CSS, JS for UI.
    • Can access filesystem and extensions.

Lecture 4: Client Side Computations and Security Implications

Client-Side Validation

Purpose:

  • Catch basic errors before sending data to the server.
  • Reduces server load and network traffic.
  • Improves user experience.

Limitations:

  • Cannot stop malicious users who bypass the browser.

Tools & Methods:

  • HTML5 Built-in Controls:
<input type="text" required minlength="3" maxlength="20">
<input type="number" min="1" max="100">
  • Regular Expressions: Validate patterns like email or phone.
const emailPattern = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
if(!emailPattern.test(emailInput.value)){
  alert("Invalid email");
}
  • JavaScript Custom Validation: Use the Constraint Validation API and attach event listeners for live feedback.
const input = document.querySelector('#username');
input.addEventListener('input', () => {
  if(input.value.length < 3) input.setCustomValidity("Too short!");
  else input.setCustomValidity("");
});

Server-Side Role

  • Mandatory Validation: Every request must be validated server-side.
  • Zero Trust Principle: Assume every request could be malicious.

Backward Compatibility

  • Older browsers may not support HTML5/JS features.
  • Use frameworks like jQuery, Angular, React for compatibility.
  • Trade-off: Extra code may slow down applications.

Proof of Humanity (CAPTCHA)

Purpose: Stop bots from automated actions (e.g., ticket bookings, vaccine appointments).

  • Google reCAPTCHA:
    • Tracks mouse movement, clicks, keystrokes.
    • Determines if user is human.
  • Privacy Concern: Detailed tracking may raise privacy issues.

High-Performance Computation

  • Modern JavaScript engines are fast, near CPU speed.
  • Scripts can access GPU for video/image rendering.
  • Can make asynchronous background calls to servers.

Warning: Some sites abuse this for crypto mining (malicious, discouraged).

Security and Sandboxing

  • Sandboxing: JavaScript is restricted from accessing sensitive local files or networks directly.
  • DoS Attacks: Malicious JS can coordinate millions of requests to a server.
  • Resource Exhaustion: Scripts can consume client CPU/memory, but modern browsers can terminate them.

Native Resource Access

  • Hardware Access: Cameras, GPS, magnetometers, tilt sensors (only if user allows).
  • Native-like Experience:
    • Apps can use OS APIs or compile to native resources.
    • Reduces browser overhead and improves smoothness.
Example – WebRTC for camera access:
navigator.mediaDevices.getUserMedia({ video: true })
  .then(stream => {
    document.querySelector('video').srcObject = stream;
  });
