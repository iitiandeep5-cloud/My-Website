Lecture 1: API Design

What is an API?

  • API = Application Programming Interface
  • Bridge between client & server
  • Flow: Client → API → Database → Response

What is REST?

  • REST = Representational State Transfer
  • Introduced by Roy Fielding (2000)
  • Type: Architectural style (guidelines)
  • Not strict rules / not code pattern

Web as Distributed System

  • Client–Server Model: Client (browser/app), Server (backend)
  • Run on different machines

Challenges:

  • Distance → latency
  • Network issues → slow/mobile
  • Authentication → added later
  • State problem → server & client unaware of each other's state

Six REST Constraints

1. Client–Server Separation

  • Client = UI, Server = Data
  • Example: Mobile app ↔ Backend API

2. Statelessness

  • Each request independent
  • Example: Login required for secure requests

3. Layered Architecture

  • Multiple hidden layers (load balancer, middleware, backend)
  • Client doesn't know structure

4. Cacheability

  • Server defines cache rules
  • Example: Static data cached → faster

5. Uniform Interface

  • Standard communication
  • Resource-based: /users, /orders/1
  • Self-discovery: links in responses

6. Code on Demand (Optional)

  • Server sends executable code
  • Example: JavaScript for frontend

REST + HTTP Methods

MethodActionExample
GETReadGet user
POSTCreateAdd user
PUT/PATCHUpdateEdit user
DELETERemoveDelete user

REST Flow: Client → HTTP Request → API → Server → Response → Client

Memory Tricks

  • API = Bridge
  • REST = Rules for web
  • Resource = Everything is an object
  • Stateless = No memory

Final Takeaways

REST = best practice for web architecture
Designed for scalability, flexibility, performance
Works well with HTTP, APIs, distributed systems

Lecture 2: REST

Definition

  • REST = Representational State Transfer
  • Architecture: state transferred between client & server via standardized representations
  • Example: Shopping cart → state moves back & forth, server doesn't store "current view"

Statelessness

  • Server does not remember client status between requests
  • Each request = independent & complete
  • Example: Refresh page → server responds correctly based on submitted data

Resources & Identifiers

URI vs URL

  • URI = identifies any resource
  • URL = browser address
  • Example:
    • URL: https://example.com/users/1
    • URI: https://example.com/users/1?id=1&format=json

Resource Operations

  • Identifier → which resource
  • Action → what to do (CRUD)

HTTP Verbs (REST Actions)

VerbFunctionExample
GETRead / retrieveGet user info
POSTCreate / submitAdd new user
PUTCreate / UpdateUpdate user 1
DELETERemoveDelete user 1

Idempotency

  • Idempotent: same result if repeated → GET, PUT, DELETE
    • Example: Delete same user twice → no extra effect
  • Non-Idempotent: changes each time → POST
  • Example: Submit twice → duplicate entries

REST vs CRUD

ConceptFocusExample
CRUDDatabase operationsAdd/Read/Update/Delete student
RESTWeb architectureUse HTTP verbs to implement CRUD

Key: REST implements CRUD but ≠ database

Data Encoding in REST

  • Machine-Readable Formats: JSON / XML / YAML
  • JSON (Most Common): key-value pairs & arrays (like Python dicts/lists)
{
  "id": 1,
  "name": "Alice",
  "courses": ["Math", "Physics"]
}
  • Serialization: convert complex data → string for transfer
  • YAML: compact alternative, used for config & OpenAPI Spec

Memory Tricks

  • REST = Rules for Web Communication
  • Stateless = No memory
  • Resource = Object / Entity
  • Idempotent = Safe to repeat
  • JSON/YAML = Machine-friendly data

Key Takeaways

REST = Web architectural style
CRUD = Database operations
REST uses HTTP + resource identifiers + machine-readable data
Idempotency prevents unintended side effects
Serialization ensures smooth data transfer

Lecture 3: REST APIs - Examples I

What is a REST API?

  • REST = Representational State Transfer
  • Architecture to transfer data between model ↔ controller
  • Commonly used for CRUD (Create, Read, Update, Delete), but not limited to databases
  • Examples:
    • Google Cloud → create/reboot VMs
    • Smart City → control street lights

Purpose of an API

  • Formalizes system functionality → developers interact programmatically
  • Example: Wikipedia API → search terms, get revision history, without direct DB access

Wikipedia REST API Case Study

FeatureDetailsExample
Access URLAPI endpointhttps://en.wikipedia.org/w/rest.
Data FormatMachine-readableJSON (not HTML)
VersioningPrevents breaking appsv1 in URL
Endpoints & ParamsRoutes + query info/search/page?q=Python&limit=

Interacting with APIs

  • Tools: curl (command-line utility)
  • Request: typically HTTP GET
  • Response: JSON blob → dictionary/array in Python

Example JSON Response

{
  "pageid": 12345,
  "title": "Python",
  "description": "Programming language",
  "extract": "<p>Python is  ... </p>",
  "thumbnail": "https://example.com/python.png"
}

JSON easily parsed into Python dict for processing

API Documentation & Schema

ConceptPurposeExample
SchemaDescribes data types"title" = string, "key" = URL
Route & MethodURL + HTTP verb/search/page → GET
Response CodesIndicate result200 → success, 400 → bad request, 500 → server error

Best Practices

  • Public Service Etiquette: use responsibly
  • Rate Limiting: avoid too many requests in short time
  • Abuse Prevention: overloading → IP block/blacklist
  • Example: Query Wikipedia API → 1 request/sec, not 100/sec

Memory Tricks

  • REST API = Bridge → Client ↔ Server
  • JSON = Machine-friendly data
  • Endpoints = URL routes
  • Versioning = backward compatibility
  • HTTP codes = result signals

Key Takeaways

REST APIs transfer state between client & server
CRUD can be implemented via REST
JSON = standard for data exchange
Documentation + schema ensure correct usage
Respect rate limits & server resources

Lecture 4: REST APIs - Examples II

CoWin REST API

Overview

  • CoWin app (India) uses RESTful API architecture
  • Backend data separated from frontend app
  • Scales to manage 60–70% of India's population
  • Docs include: production servers, user authentication (OTP), metadata & schemas

API Types & Schemas

TypePurposeExample
UnauthenticatedSearch infoFind vaccination centers
AuthenticatedSensitive actionsBook slot, download certificate
  • Schemas: define data structure (e.g., vaccination center → name, address, pincode)
  • Versioning: e.g., V2 → avoids breaking changes

Technical Implementation (curl)

  • Endpoints & Routes: URL paths → access functions
    • Example: find sessions by pincode
  • HTTP Methods: default GET, optional POST (-X POST)
  • Parameters: required query strings → pincode, date
  • Headers (-H):
HeaderPurpose

Lecture 5: OpenAPI

1. What is an API?

API (Application Programming Interface) = A bridge that allows different software systems to communicate.

Examples:

  • A weather app calling a server to get temperature data.
  • Payment apps connecting to bank servers.

Core Concepts of APIs

Information Hiding

  • API hides internal implementation details.
  • Client doesn't need to know database type or internal logic.

Example:

  • Call /getUser → returns user data.
  • Storage/fetching details remain hidden.

Separation of Concerns

  • Backend (server) and frontend (client) work independently.
  • Server doesn't care if client is mobile or web.
  • Client doesn't care how backend works.

Unbreakable Contract

  • API = agreement between provider & user.
  • Should not change frequently → prevents breaking apps/scripts.

Standardization & Versioning

APIs use version numbers.

Example:

  • /api/v1/users
  • /api/v2/users

Problems with Traditional Documentation

  • Subjectivity → Docs vary by developer.
  • Incomplete Info → Missing parameters, unclear logic.
  • Outdated Docs → Code changes but docs don't.
  • Language Barriers → Hard for non-native speakers.

Machine-Readable Description Files

Solution: Structured files describing APIs.

Formats: JSON, XML.

Benefits:

  • Structured format.
  • Automation (scaffolding).
  • CRUD auto-generation.

Example (JSON-like)

{
  "endpoint": "/users",
  "method": "GET",
  "response": "List of users"
}

Tools can auto-generate functions like getUsers(), createUser().

OpenAPI Specification (OAS)

Definition: Standard format to describe REST APIs.

Key Features:

  • Vendor-neutral.
  • Focused on web APIs (HTTP-based).
  • Not for local APIs (Java, C).
  • Originated from Swagger (~2015).
  • Current version: OAS 3 (still called Swagger Docs).

Example of OpenAPI (YAML)

openapi: 3.0.0
info:
  title: User API
  version: 1.0.0

paths:
  /users:
    get:
      summary: Get all users
      responses:
        '200':
          description: Successful response

Defines:

  • Endpoint: /users
  • Method: GET
  • Response: 200 OK

Real-World Examples

Web APIs

  • Wikipedia API → fetch articles.
  • CoWIN API → vaccine registration data.

Automation APIs: Create VM on cloud (Google Cloud, AWS).

Example (pseudo-code):

create_vm(name="test-vm", region="asia-south1")

Markup Language Example (XML):

<user>
  <name>John</name>
  <age>25</age>
</user>

Why OAS is Important

  • Standard documentation.
  • Enables automation.
  • Keeps API consistent.
  • Easy for developers to understand.
  • Helps testing tools (Swagger UI, Postman).

Quick Revision (1-Min Summary)

API = Communication bridge between systems.
Key ideas: Information hiding, separation of concerns, unbreakable contract, versioning.
Problem: Human docs are unreliable.
Solution: Machine-readable files.
OAS: Standard API description format.
Swagger: Origin of OAS.
Uses: Documentation, automation, testing.

One-Line Summary: APIs connect systems; OAS standardizes their description, enabling automation, consistency, and feature-rich documentation.

Lecture 6: Important Concepts of an API

What is OpenAPI Specification (OAS)?

  • OAS = Structured file that describes an API
  • It is: Human-readable & Machine-readable

Purpose: Clearly define how an API works before coding.

Format of OAS

YAML (Most Common): Key–value format (like dictionary).

name: User API
version: 1.0

JSON (Alternative)

{
  "name": "User API",
  "version": "1.0"
}

Single Source of Truth

  • OAS file acts as the only reference.

From this one file, we can generate: Documentation & Code

Benefit: No mismatch between code & docs.

Design-First Approach

  • First design API → then write code.

Why important?

  • Reduces bugs.
  • Saves debugging time.
  • Improves structure.
Real idea: "Think before coding".

Basic Structure of OpenAPI Document

A minimal OAS file must have:

  1. openapi → Defines version
openapi: 3.1.0
  1. info → API details
info:
  title: My API
  version: 1.0.0
  1. paths → Defines endpoints
paths: {}

Minimal Example:

openapi: 3.1.0
info:
  title: Minimal API
  version: 1.0.0
paths: {}

Valid but not useful (no endpoints).

Endpoints & Operations

Endpoint = URL + HTTP method

Example: GET /users

Path Item Object → Defines operations allowed on a path.

Operation Object → Contains request details.

paths:
  /users:
    get:
      summary: Get all users

Parameters (Dynamic values in URL):

/users/{id}
parameters:
  - name: id
    in: path
    required: true

Responses & Content Handling

HTTP Status Codes:

CodeMeaning
200Success
400Bad Request
404Not Found

Example Response:

responses:
  '200':
    description: Success

Content Types:

  • application/json → JSON data
  • text/html → Web page

Controller Logic:

  • Model → raw data
  • Controller → chooses format
  • View → JSON / HTML output

Schema (Data Structure)

Defines structure of request/response.

schema:
  type: object
  properties:
    product_name:
      type: string
    product_price:
      type: number

Example: Tic Tac Toe API

API Responsibilities:

  • Create game
  • Place X or O
  • Get board state

Not Responsible:

  • UI (display, buttons, etc.)

Example Paths:

paths:
  /board:
    get:
      summary: Get current board

    put:
      summary: Initialize game
Key Idea: API handles logic, UI handles display.

Tools & Maintenance

Swagger: Documentation, testing, code generation.

Version Control (Git): Track changes, features, contributors.

Automation:

  • YAML is error-prone → use tools.
  • Tools help validate syntax & generate APIs.

Public APIs

Examples: Wikipedia API, GitHub API

Benefits:

  • Others can build apps on your API.
  • Encourages innovation.

Quick Revision (1-Min Summary)

OAS = API description file (YAML/JSON).
Key concepts: Single source of truth, design-first approach.
Structure: openapi, info, paths.
Includes: Endpoints, parameters, responses, schema.
Tools: Swagger, Git.
API ≠ UI → separation of concerns.

One-Line Summary: OpenAPI Specification = standardized blueprint for APIs, enabling documentation, automation, testing, and consistency across systems.
