Lecture 1: Memory Hierarchy

What is Storage Hierarchy?

A system that organizes memory based on:

  • Speed, Cost, Capacity

Key Idea:

  • Faster memory = smaller & expensive.
  • Slower memory = larger & cheaper.

Types of Storage (Hierarchy Order)

Registers (Fastest)

  • Located inside CPU.
  • Used for temporary calculations.
  • Capacity: ~10–30 values.
  • Speed: ⚡ Extremely fast (nanoseconds).
Example:
int a = 10; // may be stored in register

Cache Memory (L1 / L2)

  • Built using SRAM.
  • Acts as buffer between CPU & RAM.
  • Capacity: KB → ~1 MB.
  • Faster than RAM.

Main Memory (RAM)

  • Built using DRAM.
  • Stores programs currently running.
  • Capacity: 4GB – 16GB (typical).
  • Volatile (data lost on power off).

Solid State Drive (SSD)

  • Uses flash memory.
  • Non-volatile (data saved permanently).
  • Capacity: 256GB – 1TB+.
  • Faster than HDD.

Hard Disk Drive (HDD)

  • Uses magnetic storage.
  • Slower but cheaper.
  • Capacity: 2TB – 10TB.

Archival / Cold Storage

  • Used for long-term backup.
  • Very slow access.

Example: Cloud backups (AWS Glacier, Google Cloud).

Key Performance Parameters

Latency (Access Time)

  • Time to read data.
  • Lower = better.

Latency Comparison:

StorageLatency
Registers~Nanoseconds
Cache10–100 ns
RAMMicroseconds
SSD100s of µs
HDDMilliseconds

Throughput

  • Data read per second (bytes/sec).
  • Important for RAM, SSD, HDD.

Cost & Density

  • Storage efficiency (cost per bit).

Order (best → worst): HDD > SSD > DRAM > SRAM > Registers

Important Scales & Formula Concepts

Data Scale: 1 Petabyte (PB) = 1015 bytes

Used in Google data centers, large cloud systems.

Latency Gap:

  • Registers (1 ns) vs HDD (1 ms).
  • Difference = 106 (1 million times).

Meaning: HDD is 1,000,000 times slower than registers.

Why This Matters for Developers 💻

Performance Bottlenecks:

  • Problem: Storing everything on disk (HDD/SSD).
  • Result: Slow server, low requests/sec.

Speed vs Cost Trade-off:

OptionAdvantageDisadvantage
RAMFastExpensive + volatile
DiskCheap + permanentSlow

Use-Case Based Decisions:

  • Log File Analysis: Needs fast writing → Use SSD, sequential storage.
  • Social Media / Student Records: Needs large storage + long-term safety → Use HDD + Cloud backup.
Example (Simple Code Concept):
# Bad approach (slow)
with open("data.txt") as f:
    data = f.read()  # disk read every time

# Better approach (fast)
data = load_into_memory()  # RAM
process(data)
Quick Revision
  • Memory hierarchy: Registers > Cache > RAM > SSD > HDD > Cold Storage.
  • Key points: Speed ↓ → Capacity ↑, Cost ↓ → Storage ↑.
  • Latency: Registers → ns, HDD → ms.
  • Important scale: 1 PB = 1015 bytes.
  • Speed gap: 106.
  • Developer focus: Avoid disk bottlenecks, balance cost vs speed.

One-Line Summary: Storage hierarchy balances speed, cost, and capacity: fast but small registers at the top, massive but slow archival storage at the bottom.

Lecture 2: Data Search

Big O Notation (O())

  • Definition: Represents the order of complexity of an algorithm.
  • Purpose: Shows how execution time grows with input size N.

Common Notations (Best → Worst):

NotationNameDescriptionExample
O(1)ConstantTime does not change with input sizeAccessing array index arr[5]
O(log N)LogarithmicTime grows slowly as N increasesBinary search in sorted array
O(N)LinearTime grows proportional to NSearching in unsorted list
O(N²), O(N³)PolynomialTime grows fast with NNested loops for N² operations
O(k^N)ExponentialDoubles/triples work per extra elementRecursive Fibonacci
O(N!)FactorialVery inefficientTraveling Salesman problem (brute force)

Practical Goal: Keep algorithms ≤ O(log N) or O(N).

Search Algorithms & Data Structures

1️⃣ Linked Lists

  • Structure: Node → Node → Node (A → B → C).
  • Search Complexity: O(N).
  • Average Steps: N/2 → Still O(N).
Example (Sequential Search):
current = head
while current:
    if current.value == target:

2️⃣ Arrays

  • Unsorted Array: Search O(N). Must check all elements.
  • Sorted Array: Binary Search O(log N).

Binary Search Formula: K = ⌈log₂N⌉

Example (Binary Search):
def binary_search(arr, target):
    low, high = 0, len(arr)-1
    while low <= high:
        mid = (low + high) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1

Limitation: Resizing arrays (insertion/deletion) is inefficient.

3️⃣ Binary Search Tree (BST)

  • Structure: Left < Root < Right.
  • Average Search: O(log N).
  • Unbalanced Trees: Performance drops → use AVL / Red-Black Trees.
Example (BST Search):
def bst_search(root, key):
    if not root or root.val == key:
        return root
    if key < root.val:
        return bst_search(root.left, key)
    return bst_search(root.right, key)

4️⃣ B-Trees

  • Designed for disk-based storage.
  • Optimized to retrieve data in large chunks.
  • Used in databases & file systems.

5️⃣ Hash Tables

  • Compute index using hash function.
  • Search Complexity: O(1).
Example (Python dict):
data = {'Alice': 25, 'Bob': 30}
print(data['Alice'])  # O(1)

Comparison Table

Search TypeData StructureComplexity
Sequential SearchLinked List / Unsorted ArrayO(N)
Binary SearchSorted Array / Balanced BSTO(log N)
Hash LookupHash TableO(1)

Quick Formula Recap

Binary Search Steps: N→N/2→N/4→⋯→1

Number of Steps: K = ⌈log₂N⌉

Big O Goal: Minimize time complexity → Faster algorithms.

Tips for Developers

  • Use hash tables for fast lookup.
  • Use binary search / BST for sorted data.
  • Avoid nested loops / exponential algorithms for large datasets.
Quick Revision
  • Big O: Measures algorithm efficiency.
  • Best cases: O(1), O(log N).
  • Search complexities: Linked List / Unsorted Array → O(N); Sorted Array / BST → O(log N); Hash Table → O(1).
  • Formula: Binary search steps = ⌈log₂N⌉.
  • Developer focus: Choose efficient data structures, avoid exponential growth.

One-Line Summary: Big O notation helps evaluate algorithm efficiency; hash tables (O(1)) and binary search (O(log N)) are optimal for fast lookups, while nested loops and factorial algorithms should be avoided for large datasets.

Lecture 3: Database Search

Tabular Structure

  • Databases = tables with rows & columns.
  • Each row = one record.
  • Each column = one attribute.

Relationships: Linking tables enables useful applications.

  • Example: Student Table + Course Table → Student-Course link table.

Unique Identifiers: Columns like roll numbers or IDs ensure reliable searching.

Problem with Unsorted Data:

  • Data often stored in insertion order.
  • Searching = linear scan → O(N).
  • Inefficient as database grows.

Database Indexing

What is an Index?

  • A sorted copy of data from one or more columns.
  • Includes links back to the original row.

🔹 B-Tree Index

  • Variant of binary tree.
  • Effective for:
    • Prefix searches (e.g., Patrick%).
    • Narrowing subtrees → skips irrelevant branches.

◆ Hash Index

  • Optimized for exact equality searches.
  • Very fast, but cannot do ranges or partial matches.
  • Example: Searching for Name = 'Nina'.

Multi-column / Compound Indexes

Index created on multiple columns.

  • Example: [DateOfBirth, City, Name].
  • Sorting: First by Date, then City, then Name.

Usage Rules:

  • Effective: Query using first column, or first + second in order.
  • Ineffective: Skipping first column, or using OR queries.

Search Formulae & Efficiency

Binary Search Complexity: O(log N)

Database SizeLinear SearchIndexed Search
N = 10001,000 stepslog₂(1000) ≈ 10 steps

100x faster even for small datasets.

Engineering Trade-offs

  • Space vs Speed: Index = faster search but uses extra space.
  • Over-indexing: Too many indexes → wasted space & confusion.
  • Developer Responsibility: ORMs help build queries but do not auto-optimize indexes.

Real-world Examples

Table Example:

Roll NoNameDept
101PatrickCS
102NinaEE
Effective Query:
SELECT * FROM student
WHERE name LIKE 'Patrick%';

Uses B-Tree index → fast.

Ineffective Query:
SELECT * FROM student
WHERE name LIKE '%Pat%';

Cannot use B-Tree → full scan needed.

Compound Index Example:

  • Index: [DateOfBirth, City, Name].
  • Good for: WHERE DateOfBirth='2005-01-01'.
  • Bad for: WHERE Name='Patrick' (without date & city).

Key Takeaways

  • Index = sorted copy → faster search.
  • B-Tree = range & prefix searches.
  • Hash = exact matches only.
  • Compound index = order matters.
  • Binary search → O(log N) vs linear → O(N).
Quick Revision
  • Databases = tables with rows & columns.
  • Indexing = sorted copy of data for faster search.
  • B-Tree → prefix & range queries.
  • Hash → exact matches only.
  • Compound indexes → column order matters.
  • Binary search O(log N) vs linear O(N).
  • Trade-off: speed vs space.

One-Line Summary: Database indexing transforms slow linear scans into efficient O(log N) searches, with B-Trees for ranges, Hashes for exact matches, and compound indexes for multi-column queries.

Lecture 4: SQL vs. NoSQL

SQL / Relational Database (RDBMS)

  • Concept: Data stored in tables (rows & columns), with relationships between tables.
  • Every row = same set of columns.

Advantages:

  • Prior knowledge of data size → predictable structure.
  • Efficient indexing → faster searches.

Limitations:

  • Null Problem: Rigid table structure forces unnecessary columns.
StudentMess FeesGate Pass
Hosteller2000NULL
Day ScholarNULL1

Wastes space when many fields are irrelevant.

NoSQL – "Not Only SQL"

  • Flexible, not limited to traditional SQL queries.
  • Can store data differently: document, key-value, graph, column, time series.

A. Document Databases

  • Stores structured but flexible documents (often JSON).
  • Indexing: Specific keys (e.g., document.info.rating).
  • Examples: MongoDB, Amazon DocumentDB.

Use Case: Students database.

{
  "name": "Patrick",
  "hosteller": {"mess": "A"}
}

B. Key-Value Stores

  • Stores key → value pairs like a dictionary or hash table.
  • Fast exact lookups, poor for ranges.
  • Examples: Redis, Memcached, BerkeleyDB.

Use Case: Instantaneous checks (enrollment status).

students = {"101": "Patrick", "102": "Nina"}
print(students["101"])  # O(1)

C. Columnar / Wide Column Stores

  • Stores data by column instead of row.
  • Efficient for queries on specific attributes.
  • Use Case: Find all students born on a given date.

D. Graph Databases

  • Stores nodes (entities) & edges (relationships).
  • Use Case: Social networks, shortest path, LinkedIn connections.
  • Example: Neo4J.

E. Time Series Databases (TSDB)

  • Optimized for time-based metrics.
  • Stores aggregates to save space.
  • Examples: InfluxDB, Prometheus, RRD tool.
  • Use Case: Monitoring requests per second, log analysis.

Core Database Principles

ACID (Traditional SQL):

  • Atomicity: All or nothing.
  • Consistency: Database always valid.
  • Isolation: Transactions don't interfere.
  • Durability: Committed data saved permanently.

Example: Bank transfer – money deducted from A only if credited to B.

Eventual Consistency (NoSQL):

  • Immediate consistency sacrificed for scaling & performance.
  • Guarantees: If no new updates, all reads eventually return latest value.

Example: Facebook friend request may take seconds to show for everyone.

Counter Example: Financial transactions must be ACID.

Storage Considerations

TypeSpeedScalabilityNotes
In-MemoryExtremely fastLimited across machinesRedis, Memcached
Disk-BasedSlower (latency)Scales wellUse B-Trees, indexes for efficiency

Quick Example Code Snippets

SQL Query Example:
-- Get students from CS department
SELECT * FROM students WHERE department='CS';
NoSQL Query Example (MongoDB):
// Find hostellers with mess A
db.students.find({"hosteller.mess": "A"})
Key-Value Example (Redis / Python):
redis.set("101", "Patrick")  # O(1)
name = redis.get("101")

Key Takeaways

  • RDBMS: Structured, ACID-compliant, great for predictable schemas.
  • NoSQL: Flexible, scalable, eventual consistency, suited for JSON, key-value, graph, column, time-series data.
  • Indexes & Storage: Use in-memory for speed, disk-based for scale.
  • Choice: Depends on use case — Financial → SQL, Social apps → NoSQL.
Quick Revision
  • SQL → Tables, ACID, predictable structure.
  • NoSQL → Flexible, scalable, eventual consistency.
  • Types: Document, Key-Value, Columnar, Graph, Time-Series.
  • Storage: In-memory (fast), disk-based (scalable).
  • Use case decides choice.

One-Line Summary: SQL ensures structure & reliability, while NoSQL provides flexibility & scalability — developers choose based on use case (finance → SQL, social apps → NoSQL).

Lecture 5: Scaling

Core Concepts of Data Duplication

Redundancy

  • Purpose: Keep multiple copies of data for backup and disaster recovery.
  • Focus: Ensure data survival, not speed.
  • Example: Laptop + external backup of photos/documents.

Replication

  • Purpose: Improve performance and availability rather than backup.
  • Example: Two identical database servers in the same data center handling read queries.
  • Limitation: If both servers are destroyed (same location), data is lost.
  • Requirement: Careful design for live replication to maintain data integrity.

Scaling Strategies

Scale Up (Vertical Scaling)

  • Idea: Make a single machine more powerful.
  • Example: Add more RAM, faster CPU, better network.
  • Implementation:
    • May require infrastructure changes.
    • Sometimes requires restart, though "hot swapping" can allow upgrades while running.
  • Best For: Traditional RDBMS like Oracle.

Scale Out (Horizontal Scaling)

  • Idea: Add more machines to the pool rather than making one stronger.
  • Example: Cloud platforms like Google App Engine or AWS.
  • Implementation:
    • New VM added to handle increasing traffic.
    • Can happen automatically at runtime.
  • Best For: Distributed, high-traffic systems.

Consistency Models

ACID

  • Used by: Traditional RDBMS.
  • Guarantees: Atomicity, Consistency, Isolation, Durability.
  • Use Case: Financial transactions.

BASE

  • Used by: NoSQL databases.
  • Stands for:
    • Basically Available
    • Soft state
    • Eventually consistent
  • Eventual Consistency: Replicas may lag, but system remains highly available.

Constraints: Real-time replication across geographically distributed servers is difficult due to latency.

Application-Specific Use Cases & Trade-offs

Application TypeConsistency NeedsStrategyExample
Financial TransactionsCannot tolerate inconsistenciesACID, Scale UpBank transactions
Web & Social MediaMinor delays acceptableEventual Consistency, Scale OutFacebook, Twitter feeds
E-Commerce (Hybrid)Mix of bothScale Out for search/catalog, ACID for paymentsAmazon, Flipkart

Example – Amazon Payment Flow:

  • Item Search: Stored in NoSQL, scaled horizontally for high traffic.
  • Payment Processing: Uses ACID, scaled vertically to ensure transaction correctness.
Key Takeaways
  • Redundancy ≠ Replication: Redundancy is for survival, replication is for performance.
  • Scale Up = Vertical, Scale Out = Horizontal: Know when to use each.
  • ACID = Strict Consistency, BASE = High Availability & Eventual Consistency.
  • Hybrid Strategies: Common in modern applications – critical parts (payments) use ACID, non-critical parts (catalog/search) use BASE.

Lecture 6: Security Of Databases

Query Placement

  • MVC Framework:
    • Model: Only place for SQL queries.
    • Controller: Constructs queries and sends them to the Model.
  • Non-MVC Risk: Queries scattered in scripts (e.g., PHP) → higher security risk.

SQL Injection (SQLi)

Definition: Malicious input is inserted into SQL queries to manipulate database behavior.

Common Causes: Direct concatenation of user input into query strings without sanitization.

Example Vulnerable Query (Python):
user_input = "' OR '1'='1"
query = "SELECT * FROM users WHERE username = '" + user_input + "';"

Attack Methods:

  • Bypass Authentication: ' OR '1'='1 returns all rows.
  • Data Destruction: ; DROP TABLE users; deletes tables.
  • Client Manipulation: Attackers skip forms and send crafted HTTP requests using tools like curl.

Input Validation Strategies

Timing: Validate just before hitting the database.

Core Checks:

  • Character Filtering: Remove special characters like ;, ', ".
  • Escaping: If special characters are needed, escape them.
  • Format Validation: Check emails, dates, phone numbers.
  • Framework Use: Use tested frameworks for built-in security and patches.
Example (Parameterized Query in Python with SQLite):
import sqlite3

conn = sqlite3.connect("users.db")
cursor = conn.cursor()
cursor.execute("SELECT * FROM users WHERE username = ?", (user_input,))

This avoids SQL injection by separating data from query logic.

HTTPS and Network Security

  • SSL / HTTPS: Encrypts communication between client and server.
  • Server Certificates: Verified by trusted authorities; hard to spoof.

Limitations:

  • Only secures the link, not the data itself.
  • Can impact performance and cacheability.

Additional Security Concepts

  • Buffer/Input Overflows: Maliciously long URLs or queries can crash servers/clients.
  • Character Encodings: Using visually similar but different characters to crash systems.
  • Full Stack Awareness: Security is required at every layer: OS, language, hardware.
  • Managed Services: Platforms like Google App Engine handle:
    • Security patches.
    • Buffer overflow protection.
    • Developers can focus on application-level validation.
