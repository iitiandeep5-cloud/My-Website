Lecture 1: MVC Origins

Introduction

  • MVC = Model–View–Controller
  • Separates application into:
    • Model → Data + Business Logic
    • View → User Interface
    • Controller → Input & Flow Control
  • Idea: Divide responsibilities → clean, maintainable code
Analogy: Restaurant → User (You), Waiter (Controller), Kitchen (Model), Food served (View)

Origins

  • Introduced ~1980 by Trygve Reenskaug at Xerox PARC
  • First used in Smalltalk-80 GUI systems
  • Based on Object-Oriented Programming

Components

ComponentRoleExampleMnemonic
ModelData + LogicStudent DB (Name, Marks)Brain
ViewPresentation (UI)Web page showing marksFace
ControllerHandles input & flowForm handler, Submit btnManager

Principles

  1. Separation of Concerns
    • User → Controller → Model → View → User
  2. No Direct Access to Model
    • Must go via Controller
  3. View Independence
    • Only displays data
  4. Controller Boundaries
    • Chooses views, doesn't design UI

Modern Web Development

  • Challenge: State management (client vs server)
  • Flexibility: MVC adapted, not strict
  • Frameworks:
    • ASP.NET → Strong typing, clear MVC
    • Flask → Loosely applied MVC
  • Debate: Purity less important than using MVC concepts

MVC Flow

  1. User interacts with View
  2. Controller receives input
  3. Controller updates Model
  4. Model sends data to View
  5. View updates UI

Key Points

MVC = clean architecture
Improves Maintainability, Scalability, Reusability
Used in Web, Mobile, Desktop apps

Lecture 2: Requests and Responses

Evolution of Web

  • Traditional Web: Static HTML, full page reloads (old sites).
  • Modern Web: Dynamic, interactive (Instagram feed, live search).
  • Key Idea: Web moved from pages → interactions.

Page Layout (View)

  • Structure: Header (title/navbar), Sidebar (navigation), Main Body (content).
  • Responsive Design: Adapts to screen size (hamburger menu ☰).
  • Example: Same site on phone vs laptop.

URL & Server Communication

  • Domain Name → IP Address (e.g., nptel.ac.in).
  • Data in URL: Encoded info → /course/CS101/assessment.
  • Logical Naming: Human-friendly paths (e.g., "assessment").

MVC in Web Apps

  • Flow: User → Controller → Model → View → User.
  • Example: "View Marks" → Controller fetches (Model) → shows page (View).
  • Multi-View: Same data, different views (desktop vs mobile).

HTTP Methods

Application Design & Data

  • Common Logic: Users, Items, Relationships.
    • Ex: Student ↔ Course, Customer ↔ Product.
  • Data Storage: Tables in DB, linked via relationships.

Lecture 3: CRUD

Definition

  • CRUD = Create, Read, Update, Delete
  • 4 basic operations → manage data lifecycle
  • Idea: Every app = Data + CRUD actions

Purpose

  • Simplifies data handling
  • Works across Databases, Web apps, APIs
  • Examples: Student system, e-commerce, social media

Core Operations

OperationMeaningExamples
CreateAdd new recordAdd student, Register user
ReadFetch/view dataView marks, Count students
UpdateModify recordEdit marks, Change phone
DeleteRemove recordDelete user, Remove old data

Memory Trick: CRUD = Data Life Cycle → Create → Read → Update → Delete

Data Management

  • Delete: Permanent removal
  • Archive: Backup storage (faster system, preserve old data)

Performance Types

  • Read-heavy: Analytics dashboards
  • Write-heavy: Logs, transactions

CRUD & APIs

  • API = Communication interface
  • Defines request/response format
  • Abstracts database details

Flow: User → API → Database → Response → User

Final Takeaways

CRUD = foundation of all apps
APIs = way to perform CRUD remotely
Archiving = performance + preservation
Every system = CRUD + API + Database

Lecture 4: Group Actions by Controller

Actions & Controllers

Actions

  • Definition: Tasks requested by the user.
  • Types:
    • CRUD Actions: Create, Read, Update, Delete
    • Side Actions: Extra tasks

Examples:

  • Save user data → Create
  • Fetch marks → Read
  • Send email / WhatsApp alert → Side action
  • Check quiz answers → Side action

Controllers

  • Definition: Group of related actions, usually tied to a model (resource).
  • Example: StudentController handles: Add student, View student, Update student
Note: "Controller" & "Action" are often used interchangeably.

Resource Controller Pattern

Standard Actions

ActionPurposeExample
IndexList all itemsShow all students
CreateShow formDisplay add form
StoreSave dataSave new student
ShowShow one itemView student (id=1)
EditShow edit formEdit student
UpdateModify dataUpdate marks
DeleteRemove itemDelete student

Create vs Store

  • Create (GET): Show form
  • Store (POST): Save data

Example Flow: User clicks "Add Student" → Form opens (Create) → Submits → Data saved (Store)

APIs & HTTP Verbs

API

  • Interface to communicate with server.

HTTP Methods

MethodPurposeExample
GETFetch dataView page
POSTCreate dataSubmit form
PUT/PATCHUpdate dataEdit data
DELETERemove dataDelete record
Note: HTTP doesn't strictly enforce rules. Client & server must agree on meaning.

Example (Flask Routes)

from flask import Flask, request

app = Flask(__name__)

@app.route('/students', methods=['GET'])
def index():
    return "List of students"

@app.route('/students', methods=['POST'])
def store():
    return "Student created"

@app.route('/students/<int:id>', methods=['GET'])
def show(id):
    return f"Student {id}"

@app.route('/students/<int:id>', methods=['PUT'])
def update(id):
    return f"Student {id} updated"

@app.route('/students/<int:id>', methods=['DELETE'])
def delete(id):
    return f"Student {id} deleted"

MVC Rules of Thumb

  • Model–View Independence
    • Model doesn't care about UI.
    • Same data → mobile & desktop views.
  • Storage Abstraction
    • Change DB without changing UI.
    • Use ORM like SQLAlchemy.
  • Separation of Concerns
    • Controller ≠ Database access.
    • Only Model handles DB.
    • ❌ Bad: SQL inside controller
    • ✅ Good: Controller → Model → DB
  • Controller–View Link
    • Controller decides which view to show.
    • Example: Success → success page, Error → error page.

Memory Tricks

  • Action = Task
  • Controller = Manager
  • Route = Entry point (URL)
  • API = Communication bridge

Full Flow (Important)

User → Route → Controller → Model → DB → Controller → View → User

Final Takeaways

Controllers manage actions
Routes map URL → action
Resource pattern = standard structure
Clean MVC = no mixing responsibilities

Lecture 5: Routes and Controllers

Core Concept: Statelessness

  • Web apps = stateless client–server model
  • Server does not remember previous requests
  • Each request = independent
  • If connection breaks → user must request again

Example: Refresh page → form data lost (unless saved)

Design Goal: Recover smoothly, avoid losing form inputs & user progress

Communication via HTTP

  • HTTP = text-based protocol
  • Ports: 80 (HTTP), 443 (HTTPS)

Request Structure

  • Verb (Action) → WHAT
  • URL (Location) → WHERE

Example: GET /students/1 → fetch student ID 1

Routing: URL + Method → Function mapping

Python Decorators in Flask

  • Decorator = function adding extra behavior
@app.route('/')
def home():
    return "Hello"
  • Flask builds mapping table at runtime

Examples:

  • / → home()
  • /students → students()

Flask Routing Implementation

  • Explicit methods:
@app.route('/data', methods=['GET'])
  • Wrong method → ❌ error

Handling Data

  • POST → send/store data (e.g., form → DB)

Dynamic Routes

@app.route('/user/<int:id>')
  • /user/5 → id = 5

Multiple Methods (Same URL)

  • GET → show data
  • DELETE → remove data

MVC Philosophy in Flask

  • Flask ≠ strict MVC, but supports it
  • Separation of Concerns:
    • Model → Data
    • View → UI
    • Controller → Logic
  • Rule: Model ↔ View via Controller only
  • MVC = design mindset, not strict rule

Security Best Practices

Destructive actions (UPDATE/DELETE) should not be simple URLs

❌ Bad: GET /delete/1
✅ Secure: Use authentication, tokens, permissions

Example: Only logged-in user can delete account

Full Flow

User → HTTP Request → Route → Controller → Model → Response → View

Memory Tricks

  • Stateless = No Memory
  • Route = Path → Function
  • Decorator = Connector
  • HTTP = Communication
  • MVC = Structure

Final Takeaways

Web = stateless system
Routing = core of Flask
Decorators map URL → function
MVC = clean design principle
Security = essential for destructive actions
