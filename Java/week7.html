Lecture 1: Dealing With Errors

Why Do We Need Exception Handling?

  • Prevent program crashes
  • Keep the application running
  • Handle unexpected situations gracefully
  • Help developers identify the exact problem

Types of Errors

  • User Input Errors → Wrong filename, invalid URL, incorrect password
  • External Environmental Errors → Internet lost, printer paper finished, server unavailable
  • Resource Limitation Errors → Disk full, memory exhausted
  • Internal Coding Errors → Array index out of bounds, null pointer, divide by zero

How Programs Report Errors

  • Return Values (old method) → -1, null, false
  • Exception Handling (modern method) → Throws an Exception object

Analogy: Referee raises a flag when a foul occurs → Java throws an Exception when an error occurs.

Exception Object

Every Exception object stores:

  • Type → e.g., ArithmeticException, IOException
  • Message → e.g., "Divide by zero"
  • State/Data → e.g., Input = -7

Java Throwable Hierarchy

Throwable / \ Error Exception | RuntimeException
  • Throwable → Root class
  • Error → Serious JVM problems (OutOfMemoryError, StackOverflowError)
  • Exception → Recoverable problems (File not found, invalid input)

Checked vs Unchecked Exceptions

ConceptChecked ExceptionUnchecked Exception
CompilerForces handlingDoes not force handling
CauseExpected situationsProgrammer mistakes
ExamplesIOException, SQLExceptionNullPointerException, ArithmeticException

Runtime Exceptions

  • Programmer mistakes → e.g., 10/0, array[10], obj.method() when obj is null.
  • Best solution: Fix the code.

Custom Exceptions

  • Create meaningful exceptions for application rules.
  • Example: NegativeIntegerException when Order ID < 0.

Exception Propagation

Error in Function C → moves to B → A → main().

If unhandled → program crashes.

throws Keyword

  • Declares that a method may throw an exception.
void readFile() throws IOException

Lecture 2: Exceptions in Java

Throwable Hierarchy (Architecture of Failure)

Java treats every error as an object. All errors and exceptions come under one parent class called Throwable.

Throwable / \ Error Exception | RuntimeException

Error vs Exception

  • Error → Serious JVM/system problems (OutOfMemoryError, StackOverflowError). Not programmer's fault, unrecoverable.
  • Exception → Recoverable problems (File not found, invalid input, database error). Programmers are expected to handle these.

Checked vs Unchecked Exceptions

FeatureChecked ExceptionUnchecked Exception (Runtime)
CauseBusiness logic, I/OCoding mistakes
CompilerForces handlingDoes not force handling
SolutionHandle or declareFix the code
ExamplesIOException, FileNotFoundExceptionNullPointerException, ArrayIndexOutOfBoundsException

Defensive Coding

  • Validate input before use.
  • Check array index before accessing.
  • Ensure object is not null.
  • Check file existence before reading.

Goal → Prevent runtime exceptions, build reliable software.

try-catch Block

  • try → Contains risky code.
  • catch → Handles exceptions.

Flow:

  • No exception → continue normally.
  • Exception → catch executes → program continues.

Exception Matching

Java checks catch blocks in order.

try { /* risky code */ }
catch(FileNotFoundException e) { }
catch(IOException e) { }
  • FileNotFoundException → first catch executes.
  • Other IOExceptions → second catch executes.

Specific to Generic Rule

Always catch specific exceptions first, then generic ones.

Correct order: FileNotFoundException → UnknownHostException → IOException

Exception Propagation

If not handled, exception moves upward through method calls (C → B → A → main).

If unhandled → program crashes.

Call Stack

Exception follows the call stack: Last called method → previous caller → main().

If nobody catches → program terminates.

throw Keyword

Used to manually throw exceptions.

throw new EOFException();

throws Keyword

Declares possible exceptions in method header.

void readFile() throws IOException

Difference Between throw and throws

throwthrows
Used inside method bodyUsed in method header
Actually throws exceptionDeclares possible exceptions
Action keywordDeclaration keyword

Exception Message

Custom messages can be added:

throw new IOException("File is empty");

Retrieve with e.getMessage().

Compiler Rule

For checked exceptions, compiler enforces handling: Must use try-catch OR throws.

  • Otherwise → compilation error.

Custom Exception

User-defined exceptions for application-specific rules.

Example: NegativeException when only positive numbers are allowed.

Structure of Custom Exception

  • Private Data → stores invalid value.
  • Constructor → initializes exception, uses super(message).
  • Methods → provide extra info (e.g., reportErrorValue()).

Exception Chaining

  • One exception causes another.
  • Use initCause() and getCause().
  • Preserves original error for debugging.

Flow: Database error → SQLException → wrapped in ServletException → handler retrieves original cause.

finally Block

Always executes, regardless of exception.

  • Case 1: No exception → try → finally → next statement.
  • Case 2: Exception handled → try → catch → finally → next statement.
  • Case 3: Exception re-thrown → try → catch → throw → finally → propagates.

Why finally is Important

Used for resource cleanup:

  • Close files
  • Close database connections
  • Release memory/resources

Prevents resource leaks.

Best Practices

  1. Catch order → specific first, then generic.
  2. Handle or declare rule → checked exceptions must be caught or declared.
  3. Don't ignore runtime exceptions → fix logic instead.
  4. Use meaningful custom exceptions → NegativeException, InvalidAgeException.
  5. Always use finally → close resources safely.

Lecture 3: Packages

What is a Package?

A Package is a collection of related Java classes and interfaces.

It is used to:

  • Organize code
  • Avoid class name conflicts
  • Make projects easier to manage
  • Improve code reusability

Think of a package like a folder that stores related Java files.

Why Do We Need Packages?

  • Prevents class name conflicts in large projects.
  • Example:
    • com.analytics.DataProcessor
    • com.reporting.DataProcessor
    • Both classes have the same name but belong to different packages, so Java treats them as distinct.

Fully Qualified Name (FQN)

A Fully Qualified Name = Package Name + Class Name.

Example: java.math.BigDecimal

  • java → Parent package
  • math → Sub-package
  • BigDecimal → Class

Package Hierarchy

Packages are arranged in a hierarchy using dot (.) notation.

Example: java → math → BigDecimal

Import Statement

The import keyword allows use of classes without writing the full package name.

import java.util.Scanner;
Scanner sc;

Wildcard (*) Import

Imports all classes from one package.

import java.util.*;

Examples: Scanner, ArrayList, HashMap, Random.

Limitation: Does not import sub-packages.

import java.*; // Invalid

Directory-to-Package Mapping

Java package structure matches folder structure.

Root → java → math → BigDecimal.java

Creating a Package

Declared using the package keyword (first statement in file).

package in.ac.iitm.onlinedegree;

public class StudentRecord { }

Java Package Naming Convention

Uses reverse domain naming.

Website: iitm.ac.in → Package: in.ac.iitm

Anonymous Package (Default Package)

If no package statement is written, the class belongs to the Anonymous Package.

  • Classes in the same folder belong to the same default package.
  • Mainly used for small programs.

Access Modifiers

Control visibility of classes, variables, and methods.

  • Public → Accessible everywhere
  • Private → Accessible only inside the same class
  • Default → Accessible only within the same package
  • Protected → Accessible within the same package and by subclasses

Public Modifier

Accessible from any class. Used for APIs, library classes, and widely available methods.

public class Student { }

Private Modifier

Accessible only inside the same class. Used for data hiding and encapsulation.

private int marks;

Default Access Modifier

If no modifier is written → Default access. Accessible only within the same package.

Risk: Important variables may be unintentionally exposed.

Protected Modifier

Accessible by:

  • Same package
  • Subclasses (even in different packages)

Example:

class Animal {
    protected void sound() { }
}
class Dog extends Animal { }

Visibility Ranking

Most restrictive → Least restrictive:

Private → Default → Protected → Public

Increasing Visibility

Allowed during method overriding.

protected void display() { }
public void display() { } // Allowed

Example: Object.clone() — clone() in Object class is protected. A subclass may override it and make it public.

Best Practices

  • Organize large projects into packages.
  • Use reverse domain naming.
  • Use private for data members.
  • Use protected for subclass access.
  • Use public only when necessary.
  • Avoid default access unless package-level sharing is intended.
  • Keep package and folder structure identical.

Lecture 4: Assertions

What is an Assertion?

An Assertion is a debugging tool used to verify that a condition is true while the program is running.

  • Mainly used during development and testing.
  • If the condition is false → Java throws an AssertionError.

Why Do We Need Assertions?

  • Programmers used to write assumptions as comments (not checked by Java).
  • Assertions make assumptions executable.
assert x >= 0;

Assertions vs Comments

FeatureCommentsAssertions
PurposeDocumentation onlyExecutable documentation
Checked by JavaNoYes (when enabled)
ReliabilityCan become outdatedAlways verifies condition

Why Not Use Exceptions Everywhere?

  • Exceptions → Inform caller of invalid input (public APIs).
  • Assertions → Internal checks, can be disabled in production for performance.

Assertion Syntax

Basic:

assert condition;

With message:

assert x >= 0 : "x cannot be negative";

Predicate

The condition inside an assertion is called a Predicate.

Examples: x > 0, age >= 18, name != null.

AssertionError

If assertion fails → Java throws AssertionError.

Hierarchy:

Throwable ├── Error │ └── AssertionError └── Exception

Should We Catch AssertionError?

  • No.
  • AssertionError = programming mistake.
  • Correct approach → Fix the code, not catch the error.

Assertions vs Exceptions

FeatureAssertionException
PurposeInternal assumptionsRuntime problems
Used ForDeveloper mistakesUser/external errors
RecoveryNoYes
ProductionUsually disabledAlways active
HandlingShould not be caughtUsually caught

When to Use

  • Assertions → Internal calculations, algorithm validation, debugging logic.
  • Exceptions → Invalid input, file not found, database/network errors.

Assertion Lifecycle

Development → Testing → Disabled in Production.

Assertion Execution Flow

Condition → True → Continue Condition → False → AssertionError → Program stops

Stack Trace: When assertion fails → Java prints a Stack Trace showing:

  • Error location
  • Method calls
  • Line numbers

Enabling & Disabling Assertions

  • Enable: java -ea MyProgram
  • Disable: java -da MyProgram
  • Enable for one class: java -ea:com.mycompany.MyClass Main
  • Enable for package: java -ea:com.mycompany...
  • Enable system assertions: java -esa

Life Jacket Analogy

  • Development → Assertions enabled (safety).
  • Production → Assertions disabled (performance).

Decision Rules

  • Use Exception → Public API, user mistakes, recoverable errors.
  • Use Assertion → Internal conditions, programmer mistakes, expensive checks.

Best Practices

  • Use assertions only for internal assumptions.
  • Never validate user input with assertions.
  • Never catch AssertionError.
  • Keep assertions enabled during development/testing.
  • Disable in production.
  • Use meaningful messages.
  • Use exceptions for public APIs.

Lecture 5: Logging

What is Logging?

Logging is the process of recording important information about a program while it is running.

It helps developers:

  • Find bugs
  • Monitor applications
  • Audit user activities
  • Analyze failures later

Why Do We Need Logging?

In real-world systems (banking, reservations, hospitals, e-commerce), logging answers:

  • What happened?
  • When did it happen?
  • Where did it happen?
  • Why did it happen?

Output vs Logging

  • System.out.println() → Temporary, lost after program ends.
  • Logging → Permanent record with metadata (time, date, method, class, log level).

Problems with Print Statements

  • Manual work (add/remove statements).
  • Code clutter.
  • No metadata (date, time, class).
  • Cannot control easily in production.

Advantages of Logging

  • Permanent records
  • Better debugging
  • Automatic timestamps
  • Function information
  • Error tracking
  • Performance monitoring
  • Auditing

What is a Logger?

A Logger is an object that records log messages.

Logger logger = Logger.getGlobal();
logger.info("Program Started");

Types of Loggers

  • Global Logger → Logger.getGlobal() (small apps).
  • Named Logger → Logger.getLogger("Bank") (large apps, modular).

Metadata Advantage

Logs automatically include:

  • Date
  • Time
  • Class name
  • Method name
  • Message

Logger Hierarchy

Loggers follow package hierarchy:

in → in.ac → in.ac.iitm → in.ac.iitm.onlinedegree

Parent loggers control child loggers.

Cascading Property

Settings applied to parent logger are inherited by child loggers.

Logging Handlers

Handlers process log messages and send them to destinations:

  • Console
  • File
  • Database
  • Network

Logging Levels (highest → lowest)

  • SEVERE → Serious errors
  • WARNING → Possible problems
  • INFO → General info
  • CONFIG → Configuration details
  • FINE → Basic debugging
  • FINER → Detailed debugging
  • FINEST → Complete debugging

Special levels: ALL (everything), OFF (nothing).

Default Logging Level

By default → SEVERE, WARNING, INFO.

setLevel()

Changes logging level.

logger.setLevel(Level.FINE);

Useful for switching between production (important logs only) and development (detailed logs).

External Configuration: Professional projects use configuration files for logging.

Advantages:

  • No code changes
  • No recompilation
  • Easy maintenance

Logging vs Print Statements

Logging vs Assertions

LoggingAssertions
Records eventsChecks assumptions

Best Practices

  • Use logging instead of System.out.println().
  • Write meaningful log messages.
  • Use appropriate log levels.
  • SEVERE → critical failures only.
  • FINE/FINER/FINEST → debugging.
  • Organize loggers by package hierarchy.
  • Use external configuration files.
  • Never remove logging statements → adjust level instead.
