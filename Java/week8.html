Lecture 1: Cloning

Aliasing

  • Definition: When two reference variables point to the same object.
  • Effect: Any change made through one reference is visible through the other.
Employee e1 = new Employee();
Employee e2 = e1; // aliasing

Example:

e2.setName("Alice"); // e1 also sees "Alice"

Primitive variables: Independent copies.

int x = 10;
int y = x; // changing y does not affect x
  • Object references: Only the reference (memory address) is copied.
  • Problem: Unintended side effects.
  • Solution: Use cloning or copy constructors.

Shallow Copy – Object.clone()

  • Provided by: Object class.
  • Mechanism: Bit-by-bit copy into new memory location.

Field behavior

Field TypeResult in Shallow Copy
Primitive fieldsIndependent copy
Immutable objects (String, Double)Safe to share
Mutable objects (Date, ArrayList)Reference is shared

Example:

Employee e2 = (Employee) e1.clone();

Limitation: Nested mutable objects are shared.

e2.birthday.setYear(...); // also modifies e1.birthday

Deep Copy

  • Definition: Independent copies of all mutable nested objects.
  • Goal: No shared mutable references.

Steps:

  1. Call super.clone() → shallow copy.
  2. Clone every mutable field.
  3. Assign cloned objects to fields.

Example:

public Employee clone() {
    Employee copy = (Employee) super.clone();
    copy.birthday = (Date) birthday.clone();
    return copy;
}

Result: Modifying clone's birthday does not affect original.

Covariant Return Type

Normally:

Object clone()

Allowed:

public Employee clone()
  • Benefit: Caller gets Employee directly, no cast required.
  • Inside method: super.clone() still returns Object.

Inheritance Paradox

Example hierarchy: Employee → Manager

  • Employee deep copies birthday.
  • Manager adds promotionDate.
  • If Manager does not override clone(), promotionDate is shallowly copied.
  • Result: Partial deep copy → dangerous.

Rule: Subclasses with mutable fields must override clone().

Java Cloning Safeguards

  • Cloneable interface: Marker interface, signals cloning allowed.
  • Without it: CloneNotSupportedException.

Protected clone():

protected Object clone();

To allow external cloning:

public Employee clone()

Checked exception:

try {
    Employee e2 = e1.clone();
} catch (CloneNotSupportedException e) {
    e.printStackTrace();
}

Shallow vs Deep Copy

FeatureShallow CopyDeep Copy
Top-level objectCopiedCopied
Nested mutable objectsSharedIndependently cloned
SpeedFastSlower
Side effectsPossibleNone
Default behaviorObject.clone()Manual implementation

Final Architect's Verdict

  1. e2 = e1 → aliasing
  2. Object.clone() → shallow copy
  3. Deep copy → clone all mutable fields
  4. Subclasses must override clone() if they add mutable fields
  5. Cloneable + public clone() + exception handling = safety mechanisms

Real-World Note & Summary

Many developers prefer copy constructors or other techniques because clone() is fragile and error-prone.

One-Line Summary: Aliasing causes shared references, shallow copy duplicates only top-level objects, deep copy ensures independence of nested mutable fields, and Java's cloning safeguards enforce careful design to avoid corruption.

Lecture 2: Type Inference

Introduction

  • Java is strongly and statically typed.
  • Earlier: explicit type declarations.
String name = "Rohit";

Modern Java: type inference with var.

var name = "Rohit"; // compiler infers String

Main idea:

  • Less code for programmer
  • Compiler identifies type
  • Type safety remains intact

Type Declaration vs Type Inference

Type DeclarationType Inference
Programmer writes typeCompiler finds type
Explicit declarationAutomatic deduction
Checked at compile timeChecked at compile time

Example:

String s = "Hello"; // declaration
var t = "Hello";     // inference

Both are treated as String.

How Type Inference Works

  • Compiler acts like a detective.

Looks at RHS value → deduces type.

var s = "Hello" + "World"; // s is String

Type obligation: Once inferred, type is fixed.

var x = 10;    // int
x = 20;        // OK
x = "Hello";   // Error

No backtracking → conflicts cause compilation failure.

Type Propagation

  • Compiler carries type forward.
var s = "Hello";
var t = s + 5; // t is String

Type information flows through expressions.

Why Java Limits Type Inference

  • Conservative approach.

Example:

x.bonus(); // compiler won't infer Manager

Reasons:

  • Algorithmic complexity
  • Object hierarchy ambiguity
  • Performance predictability

The var Keyword

  • Not dynamic typing.
  • Python: type can change.
  • Java: type fixed at compile time.
var x = 10; // always int

Rules of var

  • Rule 1: Local variables only.
public void test() { var x = 10; } // allowed
class Test { var x = 10; }         // error
  • Rule 2: Initialization mandatory.
var x = 10; // OK
var y;      // Error

Constant Literals and Inference

CodeInferred Type
var d = 2.0;double
var f = 2.0f;float
var n = 10L;long
var flag = true;boolean

Use suffixes (f, L) for specific types.

var with Inheritance

class Employee {}
class Manager extends Employee {}

var e = new Manager(); // e is Manager
  • Compiler chooses most specific subtype.

var and Polymorphism

Using var:

var e = new Manager();
e = new Employee(); // Error

Explicit type:

Employee e = new Manager();
e = new Employee(); // OK

Best practice: Use explicit types for polymorphism.

Best Practices

  • Use var when type is obvious.
var list = new ArrayList<String>();
var name = "Rohit";

Avoid var when type is unclear or polymorphism is needed.

Employee emp = new Manager();

Final Checklist

  1. var performs compile-time type inference
  2. Java remains statically typed
  3. Inferred type becomes fixed
  4. Compiler does not backtrack
  5. var works only for local variables
  6. Initialization is mandatory
  7. Use suffixes (f, L) for correct inference
  8. var chooses most specific subtype
  9. Use explicit types for polymorphism
  10. Use var mainly to remove redundant declarations

Lecture 3: Higher Order Functions

Definition of HOF

  • Higher Order Function (HOF): A function that takes another function as an argument.
  • Purpose:
    • Callbacks
    • Event handling
    • Asynchronous programming
    • Parallel computation
    • Reusable logic

Example: A Timer receives a function to run when it finishes → callback.

Difficulty in Old Java

  • Java originally followed strict OOP.
  • Functions could not be passed directly.
  • Developers had to:
    1. Create an interface
    2. Implement the interface
    3. Create an object
    4. Pass the object
  • Result: Boilerplate code.

Interfaces as Solution

  • Interfaces used to pass behavior.
interface TimerOwner {
    void timerDone();
}
  • Examples: Comparator, Runnable, Callable.
  • Interface = contract → guarantees required method exists.

Arrays.sort() Example

Sorting TargetMechanism
PrimitivesMethod overloading
ObjectsComparator interface

Box-in-a-Box Problem

  • Passing small logic required creating a whole class.
class MyComparator implements Comparator<String> {
    public int compare(String a, String b) {
        return a.length() - b.length();
    }
}
Arrays.sort(arr, new MyComparator());

Verbose and inefficient.

Python vs Java

Python: Functions are first-class citizens.

map(square, numbers)
  • Old Java: Functions must be wrapped in objects.
  • Solution: Lambda expressions.

Lambda Expressions

  • Anonymous function.
  • Syntax: (parameters) -> expression.
(s1, s2) -> s1.length() - s2.length();

Used in:

Arrays.sort(arr, (s1, s2) -> s1.length() - s2.length());

Structure of a Lambda

  • Normal function: name, parameters, return type, body.
  • Lambda: removes name.
(String s1, String s2) -> s1.length() - s2.length();

Components: parameters → arrow → body.

Type Inference in Lambdas

  • Compiler infers parameter types.
(s1, s2) -> s1.length() - s2.length();

Return Rule

  • Single expression → implicit return.
(a, b) -> a + b
  • Multiple statements → explicit return.
(a, b) -> {
    if (a > b) return a;
    else return b;
}

Lambda Calculus History

  • Origin: Alonzo Church.
  • Turing model: machine-oriented, execution steps.
  • Lambda calculus: function-oriented, transformations.
  • Java adopted functional style with lambdas.

Functional Interfaces

  • Interface with exactly one abstract method.
interface Calculator {
    int add(int a, int b);
}
Calculator c = (x, y) -> x + y;
  • May contain default/static methods.
  • Only one abstract method allowed.

Caller vs Consumer

  • Caller: provides lambda.
  • Consumer: receives it (e.g., Arrays.sort).
  • Backward compatibility preserved.

Method References

  • Shorthand for lambdas calling existing methods.
LambdaMethod Reference
(a, b) -> Integer.sum(a, b)Integer::sum
x -> obj.process(x)obj::process
s -> s.toLowerCase()String::toLowerCase
() -> new ArrayList<>()ArrayList::new

Limitations of Method References

  • Only valid when lambda is a single method call.
  • Invalid if extra logic is present → use lambda instead.

Final Checklist

  1. HOF = function that accepts another function
  2. Old Java used interfaces for behavior passing
  3. Comparator = classic example
  4. Lambdas = anonymous functions (params) -> body
  5. Parameter types often inferred
  6. Braces → explicit return
  7. Lambdas require functional interface (one abstract method)
  8. Method references use ::
  9. Method references only for single method calls
  10. Lambdas reduced boilerplate, added functional programming
Shortcut memory: Interface = contract · Lambda = anonymous implementation · Method reference = shortest form of lambda

Lecture 4: Streams in Java

Introduction

  • Earlier: Iterators required manual loops, counters, and state.
Iterator<Integer> it = list.iterator();
while (it.hasNext()) {
    System.out.println(it.next());
}
  • Stream API: Declarative, functional way to process data.
  • Concept: A stream is a flow of data → like a ticker, feed, or conveyor belt.

Iterator vs Stream

IteratorStream
Pull modelFlow/push model
Manual iterationAutomatic pipeline
Focus on loop mechanicsFocus on transformation logic
Mutable stateFunctional transformations

Imperative vs Declarative

Imperative: Explicit loops.

int count = 0;
for (String s : list) {
    if (s.length() > 3) count++;
}

Declarative: Express desired result.

long count = list.stream()
    .filter(s -> s.length() > 3)
    .count();

Advantages of Streams

  • Parallel processing: list.parallelStream() uses multiple cores.
  • Lazy evaluation: Work only executes at terminal operation.
  • Benefits: performance, reduced memory, early termination.

Stream Lifecycle

Stages:

  1. Source
  2. Intermediate operations
  3. Terminal operation
list.stream().filter(...).map(...).count();

Creating Streams

  • From collection: list.stream()
  • From array: Stream.of(arr)
  • Generate infinite: Stream.generate(Math::random)
  • Iterate sequence: Stream.iterate(0, n -> n + 1)
  • Bounded iterate:
Stream.iterate(0, n -> n < 100, n -> n + 1);

Non-Destructive Nature

  • Streams never modify source.
List<Integer> result = nums.stream()
    .map(n -> n * 2)
    .toList();

Original list unchanged.

Intermediate Operations

  • Lazy: return another stream.
  • Examples:
    • filter(x -> x > 10)
    • takeWhile(condition) → stops permanently when false
    • dropWhile(condition) → skips until false, then keeps all
    • limit(n) → essential for infinite streams
    • skip(n) → ignores first n elements

map() Operation

  • Transforms each element.
words.stream().map(String::length);

Result: lengths of words.

flatMap() Operation

  • Flattens nested streams.
Stream<Stream<Character>> → Stream<Character>

Example: "cat","dog" → [c,a,t,d,o,g].

Terminal Operations

  • Execute pipeline, stream finished.
  • Examples:
    • count()
    • max()
    • min()
    • findFirst()

Empty Streams & Optional

  • If no element exists → Optional<T> instead of null.
Optional<Integer> result = stream.max(Integer::compare);

Methods: isPresent(), get(), orElse(default).

Lazy Evaluation Example

list.stream().filter(x -> x > 10).map(x -> x * 2);

No work yet. Execution only at .count().

Memory Efficiency

  • Analogy: Passport office → each applicant moves desk-to-desk.
  • Streams process one element at a time → reduced memory usage.

Final Checklist

  1. Stream = flow of data
  2. Iterator = pull, Stream = pipeline flow
  3. Declarative programming focus
  4. Intermediate ops are lazy
  5. Terminal ops trigger execution
  6. Stream creation: collection.stream(), Stream.of(), generate(), iterate()
  7. Streams are non-destructive
  8. filter(), takeWhile(), dropWhile(), limit(), skip()
  9. map() transforms, flatMap() flattens
  10. Terminal ops: count(), max(), min(), findFirst()
  11. Optional handles empty safely
  12. Streams are memory-efficient and parallelizable
Shortcut memory: Source → Intermediate (lazy) → Terminal (execution)
