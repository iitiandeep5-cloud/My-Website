Lecture 1: Concurrency: Threads and Processes

What is Concurrency?

  • Concurrency = multiple tasks making progress at the same time.
  • Needed for responsiveness and multitasking.
  • Example: Browser downloading a file while opening another tab.
  • Illusion of parallelism on single-core CPUs via time slicing.
  • On multi-core CPUs, tasks can actually run in parallel.

Concurrency Levels

  • Between Applications: OS manages Chrome, VS Code, Email, Music Player.
  • Inside One Application: Browser downloads, loads pages, responds to clicks concurrently.

Process vs Thread

FeatureProcessThread
MemorySeparate spaceShared process memory
IsolationHighLower
CommunicationExpensiveEasier
Context switchingHeavierLighter
Resource usageHigherLower
RelationshipIndependentExists inside process
Easy analogy: Process = separate house, Thread = people inside the same house.

Shared State

  • Threads communicate via shared variables.
  • Example: terminate = true → UI thread cancels download.

Race Condition

  • Occurs when multiple threads update shared data simultaneously.
  • Example: Two users booking the last seat → incorrect result.

Synchronization

  • Needed to maintain consistency in shared data.
  • Java provides synchronization & locks.

Creating Threads in Java

Method 1: Extending Thread

class MyThread extends Thread {
    public void run() {
        System.out.println("Thread is running");
    }
}

MyThread t = new MyThread();
t.start();
  • run() = normal method call.
  • start() = creates new thread.

Method 2: Implementing Runnable

class MyTask implements Runnable {
    public void run() {
        System.out.println("Task is running");
    }
}

Thread t = new Thread(new MyTask());
t.start();
  • Useful with single inheritance.

Thread.sleep()

  • Pauses current thread.
  • Example: Thread.sleep(1000); → 1 second.
  • Requires handling InterruptedException.

Non-Determinism

  • Thread execution order is unpredictable.
  • Scheduler decides execution order.

Thread Interleaving

  • Threads can interleave steps in different orders.
  • Output may vary across runs.

Logical vs Actual Concurrency

  • Logical: Programmer designs concurrent tasks.
  • Actual: OS/JVM scheduler decides execution order.

Revision (Important Points)

  • Concurrency → overlapping progress of tasks.
  • Time slicing → illusion of parallelism.
  • Process → independent, heavier.
  • Thread → lightweight, shares memory.
  • Shared state → easy communication, risk of race condition.
  • Race condition → incorrect results due to uncontrolled access.
  • run() vs start() → normal call vs new thread.
  • Runnable → alternative to Thread inheritance.
  • Thread.sleep() → pauses thread, needs exception handling.
  • Non-determinism → unpredictable execution order.

Lecture 2: Race Conditions

Shared State

  • Shared state = data accessible by multiple threads.
  • Threads share same memory space.
  • Useful for communication between threads.
  • Example: Browser download with terminate flag.
  • Polling = repeatedly checking a variable's value.

Race Condition

  • Occurs when multiple threads access/update shared data concurrently.
  • Result depends on unpredictable execution order.
  • Characteristics:
    • Concurrent updates.
    • Reading changing data.
    • Non-deterministic interleaving.
  • Not always reproducible → timing dependent.

Case Study: Bank Account Example

  • 100 accounts, total balance must remain constant (Invariant).
  • Transfer Thread: subtract + add.
  • Audit Thread: checks total.
  • Without synchronization:
    • Audit may see ₹500 less (intermediate state).
    • Audit may see ₹500 more (double counting).
Lesson: A logically single operation may consist of multiple steps → needs synchronization.

Case Study: Shared Integer n++

  • n++ is not atomic.
  • Steps: Read → Modify → Write.
  • Two threads incrementing can cause Lost Update.
  • Example:
    • Expected: 7 → 8 → 9.
    • Actual: 7 → 8 (update lost).

Critical Section

  • Code accessing shared state.
  • Needs protection from conflicting concurrent access.
  • Includes:
    • Reading shared data.
    • Updating shared data.
    • Complex operations (Read → Calculate → Update).

Mutual Exclusion

  • Only one thread at a time enters critical section.
  • Prevents inconsistent state.
Analogy: bathroom with one key → one thread at a time.

Identifying Critical Sections

Ask three questions:

  1. Is the data shared?
  2. Is the data being modified?
  3. Is the data being read while modified?

If YES → synchronization needed.

Critical Section vs Mutual Exclusion

  • Critical Section = dangerous region of code accessing shared data.
  • Mutual Exclusion = mechanism ensuring only one thread enters at a time.

Complete Concept Flow

Multiple Threads → Shared Memory → Shared Variables → Concurrent Access → Race Condition → Incorrect State → Identify Critical Section → Apply Mutual Exclusion → Consistent Result.

Revision

  • Shared State → data accessible by multiple threads.
  • Polling → repeatedly checking variable.
  • Race Condition → unpredictable result due to concurrent access.
  • Bank Example → audit may show less/more balance.
  • n++ → not atomic, can cause lost update.
  • Critical Section → code accessing shared data.
  • Mutual Exclusion → only one thread at a time.

Lecture 3: Mutual Exclusion

Race Condition

  • Happens when multiple threads access/update shared data simultaneously.
  • Final result depends on execution order.
  • Example: count = 10, Thread 1 adds 5, Thread 2 adds 10 → inconsistent result.
  • Main problem: uncontrolled concurrent access → inconsistent result.

Critical Section

  • Code region where shared data is accessed/modified.
  • Needs mutual exclusion to ensure sequential appearance.
  • Requirements of good solution:
    • Mutual Exclusion
    • Sequential Appearance
    • Progress
    • Hardware Independence

Synchronization & Busy Waiting

  • Synchronization = coordinating threads for safe access.
  • Waiting methods:
    • Busy Waiting → repeatedly checking condition.
    • Blocking → stop running, CPU given to another thread.
  • Busy Waiting disadvantages: wastes CPU cycles, reduces efficiency.

Problems with Simple Mutual Exclusion Protocols

  • Turn-Based Protocol → starvation (depends on cooperation).
  • Request-Based Protocol → deadlock (both wait forever).
ProtocolMain ProblemWhy?
Turn-BasedStarvationDepends on other thread giving turn
Request-BasedDeadlockBoth request simultaneously

Peterson's Algorithm

  • Combines request + turn.
  • Solves starvation & deadlock.
  • Uses ordinary shared variables.
  • Works for 2 processes.

Core Logic:

request[i] = true;
turn = other;
while (request[other] == true && turn == other)
    wait;
// critical section
request[i] = false;

Limitation of Peterson's Algorithm

  • Designed for 2 processes only.
  • Not scalable for N processes.
  • Leads to Lamport's Bakery Algorithm.

Lamport's Bakery Algorithm

  • Provides mutual exclusion for N processes.
  • Analogy: bakery queue system.
  • Steps:
    1. Request token → max(existing tickets) + 1.
    2. Compare tickets → smaller ticket enters first.
    3. Tie-breaking → process ID.
    4. Exit → set ticket = 0.

Peterson vs Bakery Algorithm

FeaturePeterson's AlgorithmLamport's Bakery Algorithm
Processes2N processes
VariablesRequest + TurnTicket numbers
IdeaPriority between two threadsQueue/token system
Tie-breakingTurnProcess ID
ScalabilityLimitedBetter
Hardware atomicityNot requiredNot required

Modern Synchronization

  • Languages provide higher-level mechanisms:
    • Synchronized blocks
    • Monitors
    • Locks
  • Safer, easier, more maintainable.

Complete Concept Flow

Concurrent Threads → Shared Data → Race Condition → Critical Section → Mutual Exclusion → Turn-Based (Starvation) → Request-Based (Deadlock) → Peterson (2 processes) → Bakery (N processes) → Modern Synchronization (Locks/Monitors).

One-Line Definitions

  • Race Condition → result depends on timing/order.
  • Critical Section → code accessing shared data.
  • Mutual Exclusion → only one thread at a time.
  • Busy Waiting → repeatedly checking condition, wasting CPU.
  • Starvation → process keeps waiting, denied resource.
  • Deadlock → processes wait indefinitely.
  • Peterson's Algorithm → request + turn, 2 processes.
  • Bakery Algorithm → tickets + process ID, N processes.
  • Synchronization → coordination for safe access.
  • Monitor → high-level synchronization abstraction.
  • Synchronized Block → language-level mechanism for mutual exclusion.

Revision

  • Race Condition → inconsistent shared data.
  • Critical Section → code accessing shared data.
  • Mutual Exclusion → only one enters.
  • Busy Waiting → waste CPU.
  • Turn-Based → starvation.
  • Request-Based → deadlock.
  • Peterson → 2 processes.
  • Bakery → N processes.
  • Modern → Locks/Monitors/Synchronized blocks.

Lecture 4: Test and Set

Synchronization

  • Synchronization = controlling multiple threads to safely access shared resources.
  • Prevents incorrect results caused by concurrent execution.

Race Condition

  • Occurs when threads access/modify shared data concurrently.
  • Final result depends on timing/order.
  • Example: counter = 10, two threads increment → expected 12, actual 11.

Critical Section

  • Portion of code accessing shared resources.
  • Examples: global variables, counters, DB records, files, memory.
  • Rule: Only one thread should execute critical section at a time.

Lost Update Problem

  • Common result of race condition.
  • Example: Two threads increment counter → one update overwritten.
  • Expected: 12, Actual: 11.

Atomicity

  • Atomic operation = indivisible unit.
  • Prevents race conditions and lost updates.
  • Example: Read → Modify → Write must be atomic.

Test-and-Set Primitive

  • Combines Test (check value) + Set (change value).
  • Must be atomic.
  • Software alone cannot guarantee atomicity → hardware/system primitive needed.

Semaphore (Dijkstra's Concept)

  • Protected integer used for synchronization.
  • Two atomic operations:
    • P (Wait/Passeren) → acquire resource.
    • V (Signal/Vrygeven) → release resource.

Semaphore Value

  • For mutual exclusion: S = 1.
  • S = 1 → resource available.
  • S = 0 → resource unavailable.

P Operation

  • If S > 0 → decrement and enter.
  • If S = 0 → block/wait.

V Operation

  • Increments semaphore value.
  • Wakes waiting thread if any.

Busy Waiting vs Semaphore

FeatureBusy WaitingSemaphore
Condition checkRepeatedly checksCan block
CPU usageWastes cyclesBetter utilization
Thread stateActiveSleeping until signaled
ManagementProgrammer pollingOS/runtime managed

Using Semaphores

Structure:

P(S)
// Critical Section
V(S)
  • P = request entry.
  • Critical Section = shared data access.
  • V = release resource.

Guarantees of Semaphore

  • Mutual Exclusion.
  • Reduced starvation risk (depends on scheduling).
  • Deadlock avoidance (if used correctly).

Risks with Semaphores

  • Programmer discipline required.
  • Problems:
    • Forgetting V → deadlock.
    • Incorrect placement → lock never released.
    • Extra V → breaks mutual exclusion.

Advantages

  • Synchronization between threads.
  • Supports mutual exclusion.
  • Blocks waiting threads → efficient.
  • More structured than manual protocols.

Limitations

  • Programmer must correctly match P and V.
  • Incorrect use can cause deadlock.
  • Still low-level compared to modern abstractions.

Evolution of Synchronization

Race Condition → Critical Section → Manual Protocols → Peterson's Algorithm → Atomic Test-and-Set → Semaphores → Higher-Level Support (Locks/Monitors/Synchronized Blocks).

Lecture 5: Monitors

Evolution Path

  • Elementary Protocols → Peterson's Algorithm, Lamport's Bakery Algorithm.
  • Semaphores → atomic P/V operations.
  • Monitors → language-level synchronization.
  • Condition Variables → multiple focused waiting queues.

Elementary Protocols

  • Use shared variables for synchronization.
  • Examples: Peterson's Algorithm, Bakery Algorithm.
  • Limitation: manual, error-prone, programmer must design logic.

Semaphores

  • Provide atomic operations:
    • P() → Wait
    • V() → Signal
  • Safer than manual protocols.
  • Weakness: programmer must correctly match P and V.

Monitors

  • Language-level structure combining:
    • Shared data
    • Functions operating on data
    • Mutual exclusion
  • Encapsulation ensures all access goes through synchronized methods.
  • Example: Bank monitor with transfer(), deposit(), withdraw(), audit().

Synchronization Hierarchy

LevelMechanismLimitation
Elementary ProtocolsShared variablesManual, error-prone
SemaphoresAtomic P/VProgrammer discipline
MonitorsLanguage-levelStructured, safer

External vs Internal Queue

  • External Queue → waiting outside monitor.
  • Internal Queue → inside monitor but waiting for condition.
FeatureExternal QueueInternal Queue
WhenBefore enteringAfter entering
StateNot startedAlready started
ReasonMonitor occupiedCondition false
ProceedMonitor freeCondition satisfied

wait() and notify()

  • wait() → suspends thread, releases monitor, moves to internal queue.
  • notify() → signals waiting thread, but notifier continues until exit.
Golden Rule: always use while(condition) { wait(); } → recheck condition after waking.

Condition Variables

  • Provide multiple internal queues for different conditions.
  • Allow focused notification → wake only relevant threads.
  • Prevent Thundering Herd Problem → avoid waking many irrelevant threads.

Example: Bank Transfer

  • Thread A waits if insufficient funds in Account J.
  • Thread B deposits into J → calls notify(J).
  • Thread A wakes, rechecks condition, proceeds if satisfied.

Important Concepts

  • Monitor → data + synchronized methods + mutual exclusion.
  • External Queue → waiting to enter.
  • Internal Queue → waiting for condition.
  • wait() → sleep + release monitor.
  • notify() → signal condition change.
  • Condition Variable → separate queues per condition.
  • Focused Notification → efficient wake-up.
  • Thundering Herd → many threads wake unnecessarily.

Complete Evolution Chain

Elementary Protocols → Semaphores → Monitors → wait()/notify() → Condition Variables → Efficient Concurrency.

Important Points

  • Monitor = encapsulated structure with mutual exclusion.
  • External Queue = waiting outside monitor.
  • Internal Queue = waiting inside monitor for condition.
  • wait() = suspends + releases monitor.
  • notify() = signals waiting thread.
  • Signal and Continue = notifier continues until exit.
  • while loop = recheck condition after waking.
  • Condition Variables = multiple queues for efficiency.
  • Thundering Herd = unnecessary wake-ups.

Revision

  • Monitor = Data + Methods + Mutual Exclusion.
  • External Queue = waiting to enter.
  • Internal Queue = waiting for condition.
  • wait() = sleep + release.
  • notify() = signal change.
  • while = recheck condition.
  • Condition Variables = focused queues.
  • Thundering Herd = avoid inefficiency.
