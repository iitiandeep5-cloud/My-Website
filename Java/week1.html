Nature, Types, Memory & Objects

01 Introduction

A programming language is a tool used to communicate computational ideas to a machine so it can execute them.

Hardware architecture

  • CPU / ALU — performs operations
  • Memory — stores data, cannot process it
  • Registers — small, high-speed storage inside the CPU

Low-level vs. high-level

low-level
  • Manual data movement between memory and registers
  • Workflow: load → operate → store
  • Tedious, error-prone, too many instructions
high-level
  • Abstraction closer to human thinking
  • Focus on logic/design, not hardware

Core abstractions

Variables are names associated with values.

x = 5
x = 10   # assignment

Conditional execution

if x > 0:
    print("Positive")
else:
    print("Negative")

Loops

for i in range(5):
    print(i)

Functions and procedures are reusable blocks of code that support recursion. Common data structures include lists, arrays, and dictionaries.

Language translation

compiler
  • Translates the entire program at once
  • Faster execution after compilation
interpreter
  • Executes line by line
  • Easier debugging, slower execution

High-level languages trade hardware control and micro-optimizations for ease of use and fewer errors.

Programming paradigms

Imperative — step-by-step instructions:

sum = 0
for i in numbers:
    sum += i

Declarative — focus on what result is needed:

sum(filter(lambda x: x > 0, numbers))

Type discipline

All data is stored as binary. Types interpret that data — int, float, bool, char — and prevent incompatible operations, e.g. 5 + [1,2] is an error.

Abstract Data Types & OOP

ADTs are defined by their operations, not their implementation — a Stack is defined by push/pop, whatever sits underneath. This is separation of concerns: a priority queue can be backed by a list or a binary heap without changing how it's used.

OOP focuses on data and operations together — classes encapsulate both.

Course context — Java is imperative, statically typed, and object-oriented. Advanced topics ahead: exception handling, concurrency, event-driven programming.

Key takeaways

  • Understand design decisions, trade-offs, and the diversity of languages.

02 Types

Why types are necessary

Memory stores everything as bits. Types give those bits meaning — 01000001 reads as the integer 65 or the character 'A' depending on its declared type.

Types also reflect real-world ideas — a Point in geometry, a BankAccount in finance — for readability and organization, and act as sanity checks in the same way dimensional analysis does in physics:

5 + "hello"  # invalid

Dynamic vs. static typing

dynamic (python)
  • Type bound to the value, not the variable
  • Runtime checking, flexible
  • Less syntax, faster to write
  • Typos silently create new variables
static (java, c, c++)
  • Types declared explicitly, fixed at compile time
  • Compile-time checking
  • Early error detection, optimization, reliability
x = 5
x = "Hello"          # dynamic — fine in Python

count = 10
coutn = count + 1    # typo → creates a new variable
int x = 5;
x = "Hello";          // static — invalid in Java

Error detection and static analysis

Catching errors earlier, at design or compile time, is cheaper than catching them later. Static analysis handles compile-time checking, though the Halting Problem (Turing) means full correctness can never be checked automatically — type systems just catch many common mistakes.

Performance

Static typing runs faster with less runtime overhead; dynamic typing is slower due to runtime type checks.

Type inference

The compiler deduces a type automatically, reducing syntax while keeping static-checking safety:

x = 7   # inferred as integer

Key takeaways

  • Types give meaning to binary data and improve readability and correctness.
  • Dynamic typing favors flexibility; static typing favors safety and efficiency.
  • Type inference combines convenience with static-checking safety.

03 Memory Management

Categories of variables

Local variables are declared inside a function, exist only while it runs, and are accessible only inside it:

def add():
    x = 5   # local variable

Global variables are declared outside functions, accessible by multiple functions, and live for the entire program:

count = 10
def show():
    print(count)

Dynamically created data is created during execution and accessed via pointers/references — common in linked lists, trees, and graphs.

Scope vs. lifetime

Scope defines where a variable can be accessed. A hole in scope happens when a variable exists but is hidden by another with the same name:

x = 10
def fun():
    x = 5   # hides global x

Lifetime is the duration from allocation to destruction — a variable can exist even when it's inaccessible, and its lifetime can outlast its scope across nested calls (persistence).

Stack and activation records

The stack is a LIFO structure for local variables. Each function call creates an activation record holding local variables, parameters, and return info, linked by a control link (previous record) and a return value link.

Each recursive call gets its own activation record:

fact(5)
  fact(4)
    fact(3)

Variable access is resolved by checking the current record, then control links, then global scope.

Parameter passing

call by value
  • A copy of the value is passed
  • Changes inside the function don't affect the original
call by reference
  • Parameter refers to the same memory location
  • Changes affect the original object
x = 5
def change(a):
    a = 10        # x is unchanged
lst = [1, 2]
def modify(x):
    x.append(3)   # lst becomes [1, 2, 3]

Caution — reassignment breaks the reference: x = [10, 20] creates a new object rather than mutating the old one.

The heap

The heap stores dynamic data that survives after the function that created it returns. It is not LIFO, and is accessed via pointers/references — e.g. linked-list nodes. In memory layout, the stack and heap grow from opposite ends to avoid colliding.

Memory management strategies

Manual (C) — the programmer allocates and frees memory, risking a memory leak (unused memory never freed) or a dangling pointer (freed memory still accessed).

Automatic / garbage collection (Java, Python) — uses mark and sweep: mark reachable objects, then sweep the unmarked ones as garbage. Easier and fewer errors, at the cost of pauses and unpredictable performance.

Key takeaways

  • Variables come in three flavors: local, global, dynamic.
  • Scope ≠ lifetime.
  • Stack handles activation records and recursion; heap handles persistent dynamic data.
  • Call by value vs. call by reference; manual vs. automatic memory management.

04 Abstraction & Modularity

Core principles

Abstraction hides unnecessary detail and shows only essential functionality — a driver uses the steering wheel, not the engine internals — reducing complexity and easing maintenance.

Modularity divides a system into independent modules (e.g. a website's login, database, and payments modules), enabling parallel teamwork and easier debugging.

Program and data refinement

Program refinement breaks a large task into smaller sub-tasks — e.g. printing 1000 primes splits into storage, fill, and print — so teams can work independently.

Data refinement modifies data structures as requirements evolve — e.g. BankAccount growing from just a balance to balance + transaction history. It's more sensitive than program refinement since many modules can depend on shared data.

Modular design

InterfaceSpecification
How to interactWhat it should do
StructureBehavior
 
withdraw(amount)

An interface defines function names, parameters, and return types; a specification defines what the component should do — here, that withdraw() decreases the balance by the given amount. Prototyping builds an early version to verify design and surface missing requirements.

Separation of concerns: if the interface and specification stay the same, the internal implementation can change freely — swapping Bubble Sort for Quick Sort, for instance.

Challenges in formal specification

  • Specifications can be long and hard to understand
  • The verification problem — full correctness can't be proven (Halting Problem)
  • In practice, teams rely on testing and informal requirements

Types of abstraction

Control abstraction — functions and procedures hide implementation detail (print(), sort()).

Data abstraction — ADTs define values and operations while hiding implementation, e.g. a Stack's push()/pop().

Encapsulation — internal data stays private, accessed only through public interfaces, for security, reduced complexity, and easier modification.

Foundations of OOP

OOP is built on ADTs plus encapsulation: combine data and functions inside objects and classes. Inheritance lets classes inherit features from others — e.g. Vehicle → Car — for code reuse, organization, and hierarchy.

Top-down vs. bottom-up

Top-downBottom-up
Starts with the big problemStarts with small components
Breaks tasks downCombines modules upward
Focus on designFocus on reusable parts

Top-down example: a banking system splits into login, transactions, database, reports. Bottom-up example: building a larger system out of existing libraries and modules.

Key takeaways

  • Abstraction hides complexity; modularity divides systems into manageable parts.
  • Interfaces define structure; specifications define behavior.
  • ADTs + encapsulation form the foundation of OOP.
  • Program refinement breaks tasks apart; data refinement affects shared structures.

05 Object-Oriented Programming

What is an object?

An object is an ADT with hidden internal data and public operations (methods). A bank account object keeps balance private, and exposes deposit(), withdraw(), checkBalance(). Objects scale from simple counters up to databases and OS components.

Historical context: Simula

OOP originated in the 1960s with Simula, built for simulations. Traditional if-else/switch-case solutions were complex and hard to maintain; Simula's innovation was that each object stores its own data and behavior — an object knows how to simulate itself.

The data-centric paradigm shift

traditional
  • Focus: control flow, sequence of operations
  • Data supports computation
object-oriented
  • Focus: data and objects first
  • Operations are defined on that data

OOP identifies objects first — Customer, Account, Transaction — then defines methods like deposit() and transfer() on them, which makes it easier to maintain when internal data changes.

Four distinguishing features of OOP

Abstraction

Separates the public interface from the private implementation; encapsulation hides internal data.

account.deposit(100)   # caller doesn't know how balance is stored

Refinement allows internal changes without affecting users of the interface.

Subtyping

A specialized type relationship — e.g. Vehicle → Car. The substitutability principle says a subtype can replace its parent type; the capability rule says a subtype must support all of the parent's operations.

Dynamic lookup

The method actually run is chosen at runtime, based on the object's real type — calling draw() on a Shape reference executes Circle's version if that's the real object. This differs from overloading, which is resolved at compile time.

Inheritance

Reuses code from a parent class — e.g. Employee → Manager — for code reuse and reduced duplication.

Subtyping vs. inheritance

Subtyping is about interface and substitutability; inheritance is about implementation and code reuse. A Stack can reuse a Deque's implementation (inheritance) without being a true subtype of Deque, since it shouldn't allow deleteRear(). So inheritance ≠ subtyping — though languages like Python and Java combine both into a single hierarchy for simplicity.

Key takeaways

  • Objects combine data and behavior; OOP originated with Simula.
  • Abstraction and encapsulation hide complexity; subtyping ensures substitutability.
  • Dynamic lookup enables runtime polymorphism; inheritance promotes code reuse.
  • Subtyping and inheritance are related but distinct.

06 Classes & Objects

Class vs. object

A class is a blueprint that defines data and functions:

class Student:
    pass

An object is a real instance created from that class:

s1 = Student()

Encapsulation hides data from direct access; message passing calls methods on objects, e.g. account.deposit(100).

Object mechanics and state

Instance variables store an object's data — each object holds its own copy. self in Python refers to the current object and is used to access its instance variables and methods:

self.x = x

The constructor is automatically called at object creation — in Python, __init__():

def __init__(self, x, y):
    self.x = x
    self.y = y

An object's state is the set of values held in its instance variables. Methods split into state-changing methods (modify data) and reporting methods (return values without changing state).

Data refinement and abstraction

Implementation transparency hides internal representation — a Point can be stored as Cartesian (x, y) or polar (r, θ) while the interface stays the same. Internal functions change with representation; external users are unaffected (code refinement).

Subtyping and inheritance

One class acquires properties and methods from another — e.g. Rectangle → Square — for code reuse, less duplication, and easier maintenance. The subtype must correctly initialize inherited variables.

Python's limitations, and why Java is more structured

  • Privacy limitations — Python cannot fully enforce private variables: p.x = 4 breaks encapsulation
  • Inconsistent subtypes — child classes may omit parent variables, causing runtime errors
  • Lack of type declarations — no explicit int, float, String
  • Weak visibility control — public/private enforcement is weak
Why Java — static type checking, strict visibility, and better subtype enforcement let the compiler catch errors early, giving stronger reliability, fewer runtime errors, and safer inheritance.

Key takeaways

  • Classes define structure and behavior; objects are real instances.
  • Constructors initialize state; encapsulation hides implementation.
  • Inheritance supports reuse; abstraction allows internal changes without affecting users.
  • Python is flexible but less strict; Java enforces stronger type safety and visibility.
