Lecture 1: Graphical Interfaces and Event-Driven Programming

Evolution of User-Computer Interaction

  • CLI (Command-Line Interface) → Sequential, syntax-based, powerful but less user-friendly.
  • GUI (Graphical User Interface) → Windows, icons, buttons, touchscreens; system must detect which component is interacted with.

Challenges in GUI Interaction

  • Must track: mouse (x,y), window positions, keyboard focus, Z-order.
  • Example: Overlapping windows → system decides which component was clicked.
  • Manual handling = tedious, error-prone, hard to scale.

Event-Driven Programming (EDP)

  • Program waits for events instead of polling.
  • Examples: button click, mouse move, key press, window close, timer completion.
  • Event sent to appropriate code automatically.

Low-Level vs High-Level Events

TypeExampleMeaning
Low-Level EventMouse click at (x,y)Raw hardware/OS input
High-Level Event"OK Button Clicked"Logical UI event

Java runtime converts raw input → meaningful events.

Abstraction in EDP

  • Hides low-level details (pixels, coordinates, Z-order).
  • Programmer works with buttons, checkboxes, windows instead.
  • Benefit: simpler, flexible, maintainable GUI programming.

Listener Pattern

Flow: Component → Event → Listener → Response
  • Component: Button, Window, Checkbox
  • Event: Click, Close, Timer done
  • Listener: Object/class that responds

Window Event Example

Steps when clicking Minimize/Maximize/Close:

  1. OS detects click
  2. GUI identifies component
  3. Event generated
  4. Listener notified
  5. Action performed

Connecting a Listener

  1. Create Component (e.g., Button)
  2. Define Listener (e.g., buttonPush())
  3. Associate Listener (Add Listener operation)
Flow: User Action → Event → Listener → Response

Callback Pattern

  • One object says: "When this happens, call this function."
  • Function executes later when event occurs.

Explicit vs Implicit Callbacks

  • Explicit: Programmer directly calls function (timerDone()).
  • Implicit (GUI): Runtime auto-calls listener when event occurs.

Inversion of Control (IoC)

  • Normal: Program → Function
  • Event-driven: Event → Runtime → Listener Function
  • Definition: Runtime controls when event-handling function executes.

Flexible Delegation

  • Event creator ≠ Event handler.
  • Example: Timer created by Class A, handled by Class B.
  • Benefit: Separation of concerns → modular programs.

Why EDP is Useful

  • Users act unpredictably (click, type, move mouse).
  • Benefits: responsive apps, reduced complexity, modularity, flexible delegation, easier maintenance.

Overall Flow

User Action → OS detects → Runtime identifies component → High-level event → Listener receives → Listener executes → App responds

Example: Click OK → OS detects → Java identifies button → Event generated → Listener executes buttonPush() → App responds.

Key Terms

  • Event: Action (e.g., button click)
  • Event Source/Component: Object generating event
  • Listener: Responds to event
  • Callback: Function executed on event
  • EDP: Execution triggered by events
  • Abstraction: Hide low-level details
  • IoC: Runtime decides when to call function
  • Z-Order: Stacking order of overlapping windows

Revision

  • GUI problem: Overlapping components → complex tracking
  • EDP solution: Convert raw input → high-level events
  • Listener Pattern: Component → Event → Listener → Response
  • Callback: Function triggered by event
  • IoC: Runtime controls execution
  • Advantage: Focus on logic, not hardware details

Lecture 2: The Swing ToolKit

Introduction

  • Event-Driven Programming (EDP) → Program responds to events (mouse clicks, key presses, timers, window actions).
  • AWT (Abstract Window Toolkit) → Low-level foundation.
  • Swing → High-level toolkit built on AWT, provides advanced GUI components.
AWTSwing
Low-level frameworkHigh-level toolkit
Basic event supportAdvanced GUI components
FoundationBuilt on AWT
Custom eventsEvent-listener mechanisms

Event Generators & Listeners

  • Event Generator → JButton, Timer, JFrame.
  • Listener → Waits for event, executes response.
  • Example: Timer → Listener → Response (loose coupling).

Relationships

  • Many-to-One → Multiple buttons → One listener.
  • One-to-Many → One button → Multiple listeners (e.g., Logout triggers several actions).

Registering a Listener

Must explicitly register:

button.addActionListener(this);

If not registered → event generated but no response.

Swing Naming Convention

  • JButton → Button
  • JPanel → Container
  • JFrame → Window

JButton & ActionListener

  • JButton generates ActionEvent.
  • ActionListener receives event → executes actionPerformed().
Flow: JButton → ActionEvent → ActionListener → actionPerformed()

ActionListener vs WindowListener

  • ActionListener → Button/menu actions (actionPerformed()).
  • WindowListener → Window events (open, close, minimize, activate).

WindowListener Methods

Seven methods:

  • windowActivated()
  • windowDeactivated()
  • windowIconified()
  • windowDeiconified()
  • windowOpened()
  • windowClosed()
  • windowClosing() → often used with System.exit(0).

Event Dispatch Thread (EDT)

  • Handles GUI events.
  • Heavy tasks must run in background threads.
  • Use:
EventQueue.invokeLater(() -> { /* GUI code */ });

Processing

  • Interleaved → GUI checked only between chunks → unresponsive.
  • Parallel → EDT handles GUI, background thread handles heavy work → responsive.

Example: Color-Changing Panel

  • JButton "Red" → JPanel background changes to red.
setBackground(Color.RED);
repaint();

Panel changes, not JFrame title bar.

Complete Flow

User clicks JButton → ActionEvent → ActionListener → actionPerformed() → GUI updated

Swing Structure

JFrame → ContentPane → JPanel → JButton

Key Methods

Revision

  • Swing = GUI toolkit
  • AWT = Foundation
  • JFrame = Window
  • JPanel = Container
  • JButton = Button
  • ActionEvent = Event
  • ActionListener = Event handler
  • actionPerformed() = Handles action
  • addActionListener() = Registers listener
  • WindowListener = Window events
  • EDT = GUI thread
  • invokeLater() = Schedule GUI code
  • System.exit(0) = End program

Lecture 3: More Swing Examples

Multi-Source Event Handling

  • One listener can handle multiple buttons.
  • Use getSource() to identify which button triggered the event.
if (e.getSource() == redButton) { /* action */ }

getBackground() and State Restoration

  • getBackground() → returns current panel background.
  • Helps preserve or restore state when no condition matches.

Multicasting

  • One event → multiple listeners.
  • Example: Color selection updates several panels simultaneously.
Benefit: Loose coupling, multiple independent updates.

Event Identification

  • getSource() → identifies actual object.
  • getActionCommand() → identifies event using command string.
getSource()getActionCommand()
Object identityCommand string
Local componentsDistributed communication
Example: redButtonExample: "Red"

Role of JFrame in Multicasting

  • Acts as mediator between panels.
  • Connects event generators and listeners.
  • Handles wiring and communication.

BorderLayout

  • Organizes GUI into NORTH, SOUTH, EAST, WEST, CENTER.
add(controlPanel, BorderLayout.NORTH);
add(statusPanel, BorderLayout.SOUTH);

Visual Boundaries & Empty Areas

  • Each JPanel has its own area.
  • Empty regions show JFrame background.
  • Useful for debugging layout.

JCheckBox – State-Based Component

  • JButton → momentary action.
  • JCheckBox → persistent state.
  • Use isSelected() to check state.
if (redCheckBox.isSelected()) { /* Red selected */ }

Compound State

  • Multiple checkboxes can be selected simultaneously.
  • Example: Red + Blue → Green background.

Observer Pattern

Source → Event → Listener → Response

Provides loose coupling and separation of concerns.

Explicit Listener Registration

  • Must call addActionListener().
  • Without registration → event lost, no response.

Developer Checklist

  1. Explicit registration → addActionListener()
  2. Observer pattern → Source → Listener → Response
  3. State management → isSelected()
  4. Source identification → getSource()
  5. Command identification → getActionCommand()
  6. Layout management → BorderLayout
  7. State preservation → getBackground()

Revision

  • Multi-source handling → getSource()
  • Distributed/multicast → getActionCommand()
