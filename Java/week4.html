Abstraction, Encapsulation, State

01 Abstract Classes & Interfaces

Class hierarchy and grouping

A class hierarchy organizes related objects under one structure — e.g. Shape as a parent class, with Circle, Square, and Rectangle as subclasses. Each subclass redefines methods like perimeter(): Circle → 2πr, Square → 4·side.

The need for abstract definitions

In large projects, meaningless default implementations (e.g. returning -1) can cause errors. The fix is an abstract method — declaration only, no body — forcing every subclass to implement its own version:

abstract double perimeter();

Abstract classes

If a class has even one abstract method, the class itself must be declared abstract.

  • Cannot be instantiated — new Shape(); is invalid
  • Variables and arrays are still allowed: Shape[] arr = new Shape[5]; can store Circle, Square, etc.
  • Dynamic dispatch — the correct subclass method is chosen at runtime

Generic capabilities — the Comparable example

Abstract classes and interfaces define reusable capabilities. The Comparable pattern's cmp() returns -1, 0, or +1, letting sorting algorithms like quicksort work with any comparable class.

Multiple inheritance and interfaces

Java disallows multiple inheritance of classes to avoid conflicts — e.g. two parent classes defining the same method would be ambiguous. Interfaces sidestep this: all methods are abstract by default, offering only specifications with no implementation, which eliminates the risk of conflicting code.

Extends vs. implements

extends inherits from a class; implements adopts an interface's capabilities:

class Circle extends Shape implements Comparable

This means Circle is a Shape, and Circle is Comparable.

Java's rule — a class can extend only one class, but can implement multiple interfaces — safely providing multiple capabilities.

Quick revision

  • Abstract methods are declaration only; abstract classes cannot be instantiated.
  • Subclasses must implement abstract methods; dynamic dispatch gives runtime polymorphism.
  • No multiple inheritance of classes — interfaces give safe multiple capabilities, one class implementing many.

02 Interfaces

Definition and core properties

An interface is a purely abstract structure — traditionally, all methods are abstract, providing only declarations, never implementations.

No state — interfaces cannot hold instance variables or object state; they describe behavior/capabilities, not data.

Keywords and multiple implementation

A class extends another class, but implements an interface:

class Circle implements Comparable

A class can extend only one superclass, but implement multiple interfaces:

class Circle extends Shape implements Comparable, Drawable

This avoids multiple-inheritance conflicts while still enabling multiple capabilities.

Purpose of interfaces — defining capabilities

Interfaces describe what a class can do. Sorting algorithms like Quicksort and Merge Sort require comparable objects — the Comparable interface defines a comparison method, cmp(). The interface fixes the method's name, parameters, and return type; correct logic depends on the developer's implementation.

Expected return values: -1 → smaller, 0 → equal, 1 → greater.

Modern Java enhancements

Originally fully abstract, interfaces now allow limited concrete methods.

a) Static methods

Belong to the interface itself — useful for utility/documentation helpers:

static void cmpdoc()

b) Default methods

Declared with default, providing an optional implementation classes inherit if they don't override it:

default void show() {
    System.out.println("Default Method");
}

Managing inheritance conflicts

interface vs interface
  • Two interfaces with the same default method → the class must override it
class vs interface
  • Superclass and interface define the same method → the class's method wins
Rule — classes win over interfaces.

Evolutionary philosophy of Java

Backward compatibility prevents old programs from breaking, and controlled growth avoids the complexity of full multiple inheritance. Java introduces safe features instead — interfaces, default methods, static methods — balancing new functionality against the stability of old code.

Quick revision

  • An interface is a purely abstract structure; classes implement it, and one class can implement several.
  • Interfaces define signatures, not guaranteed logic; modern interfaces allow static and default methods.
  • Interface clashes force an override; class-vs-interface clashes let the class method win.

03 Private Classes

Introduction to nested objects

In Java, one object can contain another inside its instance variables — helpful for organizing related data:

class Employee {
    Date joiningDate;
}

Public vs. private scope

Public nested classes are accessible by any class in the program — Date is public because many programs need it. Private nested classes are hidden, used only internally for encapsulation.

Motivation for private classes

Not every internal class should be visible — some exist only to support internal implementation. Classic example — LinkedList and Node:

class Node {
    int value;
    Node next;
}

Users care about the list of values, not how nodes are connected. Hiding Node improves encapsulation and flexibility — if the implementation later changes (singly → doubly linked list), user code stays unaffected.

Defining private inner classes

A class can be declared inside another and marked private — an inner class:

class LinkedList {
    private class Node {
        int value;
        Node next;
    }
}

Purpose: hide internal details, prevent outside access, increase encapsulation and security.

Visibility and access rules

host → inner
  • The outer class can create objects of the inner class
  • The outer class can access all members of the inner class
inner → host
  • The inner class can access private variables and methods of the outer class
class LinkedList {
    private int size;
    private class Node {
        void showSize() {
            System.out.println(size);
        }
    }
}

Inner and outer classes are treated as part of the same scope — similar to how two objects of the same class can access each other's private members.

Advanced utility — interfaces and state control

Private inner classes can work with interfaces to control how internal state is accessed and how data is exposed externally — giving better abstraction, safer data handling, and stronger encapsulation.

Quick revision

  • Objects can contain other objects; nested classes organize related data.
  • LinkedList commonly hides its Node objects behind a private inner class.
  • Outer and inner classes can access each other's private members; interfaces + private classes control state safely.

04 Controlled Interaction with Objects

Core principles of encapsulation

Encapsulation keeps internal implementation private and provides controlled access via public methods.

Accessor and mutator methods

Accessor methods (getters) retrieve instance variable values, e.g. getDate(). Mutator methods (setters) modify them, e.g. setDate().

The problem with simple getters and setters

Simple setters may allow invalid states — like the 31st of February — leading to inconsistent data. The fix is a validation function that checks all values together, e.g. setDate(day, month, year), for better data integrity and fewer incompatible states.

Need for advanced interaction control

Large systems — railway reservations, banking, online databases — need more than validation; they must control who can access data and how it's accessed.

Common threats — Denial of Service (flooding requests to block genuine users) and bots/scraping (automated data collection for black-marketing or price manipulation). The fix: queries should only work for authenticated users.

Interaction with state

Passing login details into every function is poor design:

getStatus(userID, password)

A better approach lets the system remember login state, session validity, and permission level, stored inside an object — interaction with state.

Technical implementation: private classes + public interfaces

A successful login returns a Query Object rather than granting direct database access.

private class QueryObject

The private class cannot be created manually by users, which prevents bypassing login validation. A public interface exposes only the allowed operations:

interface QIF
// returned as:
QIF obj

Users can call allowed methods, like getStatus(), without ever seeing the internal implementation.

Controlling usage and lifetime

  • Usage limits — the private query object tracks numQueries and stops responding past a limit, preventing automated abuse
  • Temporal limits — session timeout tracks login time and last activity, expiring like a banking app after inactivity
  • Powerful state management — the private object can access database data, maintain internal state, and regulate user activity intelligently

Quick revision

  • Encapsulation hides internal details; getters are accessors, setters are mutators.
  • Simple setters can create invalid states — validation improves data integrity.
  • Private inner classes secure implementation while public interfaces expose allowed operations; query objects enforce limits and timeouts.

05 Callbacks

Introduction to callbacks

A callback is when one object creates another to perform a task, and once it's done, the second object calls back a function on the original object — enabling controlled communication, asynchronous handling, and safe use of interfaces with private/internal classes.

Analogy — like a kitchen timer: you set it, keep working, and it notifies you when time is up.

Mechanism of parallel execution

Parallelism runs secondary tasks alongside the main program; Java's threads enable this.

class MyTask implements Runnable

The Runnable interface lets an object run as a separate thread — optimizing resources and supporting multitasking, e.g. running a clock or downloading files while browsing.

Evolution of callback implementation

Version 1 — tight coupling

Timer(MyClass owner)

Works only with one specific class — not reusable, tightly coupled.

Version 2 — using Object class

Timer(Object owner)

Accepts any class, but requires unsafe casting:

((MyClass)owner).timerDone();

Version 3 — using interfaces (best approach)

interface TimerOwner {
    void timerDone();
}

Any class can implement this interface, and the Timer accepts it directly:

Timer(TimerOwner owner)
// safe call:
owner.timerDone();

Benefits of interfaces in callbacks

  • Generic utility — works with any class implementing the interface
  • Decoupling — the Timer only knows the object can receive notifications, not its details
  • Abstraction — the receiver doesn't need to be the creator of the timer

Real-world example — web browsers

Downloading files runs in the background while browsing continues. If the user stops a download, the browser sends a notification to the background process — a working example of callback plus thread communication.

Quick revision

  • A callback lets one object notify another after a task completes, for asynchronous communication.
  • Threads run parallel tasks; the Runnable interface enables thread execution.
  • Tight coupling → Object-class casting → interfaces is the evolution toward flexible, reusable callbacks.

06 Iterators

Core theme — interaction with state

An object's behavior depends on its current internal state — as interaction continues, its responses change accordingly. This is implemented with private classes, private objects, and interfaces, to hide internal state and prevent external access.

The concept of a linear list

A linear list is an ordered sequence of values, commonly implemented two ways.

array-based
Object[] data;

Elements stored continuously in memory.

linked-list based
class Node {
    Object data;
    Node next;
}

Each node holds data plus a reference to the next.

Adding elements to a linked list means traversing until next == null, then appending.

Need for iterator abstraction

If arrays or head nodes were public, users could loop directly and break encapsulation. An iterator provides a standard way to traverse collections without exposing internal details.

Iterator interface

Defines two key methods:

  • has_next() — checks whether another element exists, returning true/false; must be checked even before the first access, since the list may be empty
  • get_next() — returns the next element and moves the iterator forward

Internal implementation and state tracking

The iterator must remember its current position — its state.

arrays
int index;

has_next() checks bounds; get_next() increments the index.

linked lists
Node current;
current = current.next;

get_next() moves the pointer forward.

Iterators are often implemented as private inner classes inside the list, so they can access its private data while remaining hidden externally — better security and encapsulation. Users request one via an object factory: calling get_iterator() returns a new iterator initialized at the start.

Usage patterns

Standard iteration:

while (iterator.has_next()) {
    Object x = iterator.get_next();
}

Nested iteration — two loops running simultaneously (e.g. comparing pairs) each need their own iterator object; the outer iterator tracks the outer loop while the inner one restarts each pass.

Modern iteration in Java

The enhanced for-loop is similar to Python-style iteration, but still uses iterators internally, relying on state, private classes, and interfaces:

for (Object x : collection)

Quick revision

  • Linear lists are ordered sequences, built as arrays or linked lists; iterators allow safe traversal.
  • has_next() checks availability, get_next() returns the element and advances — arrays track an index, linked lists track a node pointer.
  • Iterators are often private inner classes; multiple iterators enable nested loops, and the enhanced for-loop uses iterators under the hood.
