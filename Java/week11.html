Lecture 1: Monitors in Java

Definition

  • Monitor = Shared data + functions + mutual exclusion
  • Purpose → Protect shared data from race conditions.
  • Only one thread executes inside monitor at a time.

Thread Queues

  • External Queue → Waiting for lock.
  • Internal Queue → Already inside monitor, waiting for condition.
Easy Trick: External = Lock wait, Internal = Condition wait.

Java & Monitors

  • No separate keyword → uses synchronized.
  • Lock belongs to object instance, not class.
  • Lifecycle: Entry → Execution → Exit.

Thread Communication

  • wait() → Releases lock, moves to Internal Queue.
  • notify() → Wakes one waiting thread.
  • notifyAll() → Wakes all waiting threads.
  • Signal & Continue model → Not immediate transfer of lock.

Synchronization Styles

  • Method-level → Entire method locked.
  • Block-level → Only critical section locked → better performance.
  • Arbitrary Lock Objects → synchronized(o) or dedicated lock object.
  • Multiple locks → Greater concurrency.

Waiting & Interruption

  • Busy Waiting → CPU waste.
  • Monitor Waiting → Efficient, thread sleeps until notified.
  • InterruptedException → Must handle when using wait().
  • IllegalMonitorStateException → wait/notify must be inside synchronized block.

Advanced Locks

  • ReentrantLock → Explicit lock/unlock, supports reentrancy.
  • Must use finally to ensure unlock.
  • Semaphore vs ReentrantLock → Semaphore uses permits, less ownership semantics.

Important Points

  • Monitor → Mutual exclusion, protects shared data.
  • External Queue → Waiting for lock.
  • Internal Queue → Waiting for condition.
  • wait() → Releases lock, moves to Internal Queue.
  • notify/notifyAll → Wakes threads, not immediate lock transfer.
  • Busy vs Monitor Waiting → CPU waste vs efficient sleep.
  • ReentrantLock → Manual, flexible, must unlock in finally.

Lecture 2: Thread in Java

Multithreading Basics

  • Multithreading → Running multiple threads concurrently.
  • Benefits: Better CPU utilization, responsiveness, background tasks, multi-core efficiency.
  • Example:
    • Main Thread → UI
    • Thread 1 → Download
    • Thread 2 → File Processing
    • Thread 3 → Database Work

Ways to Create a Thread

Extending Thread

class MyThread extends Thread {
    public void run() {
        System.out.println("Thread is running");
    }
}

MyThread t = new MyThread();
t.start();

Limitation → Single inheritance.

Implementing Runnable

class MyTask implements Runnable {
    public void run() {
        System.out.println("Task is running");
    }
}

Thread t = new Thread(new MyTask());
t.start();

Runnable = Task logic, Thread = Execution mechanism. Preferred approach.

Thread vs Runnable

InheritanceUses single extendsPreserves inheritance
FlexibilityLowerHigher
Task & ThreadCoupledSeparated
ReusabilityLowerBetter
Production UseLess preferredPreferred

start() vs run()

  • run() → Normal method call, sequential execution.
  • start() → Creates new thread, executes run() concurrently.
Golden Rule: run() = normal call, start() = new thread.

Thread Lifecycle

Six states in Thread.State:

  • NEW → Created, not started.
  • RUNNABLE → Eligible to run.
  • BLOCKED → Waiting for lock.
  • WAITING → Waiting indefinitely.
  • TIMED_WAITING → Waiting with timeout.
  • TERMINATED → Finished execution.

Interrupts

  • interrupt() → Requests interruption.
  • interrupted() → Static, checks current thread, clears flag.
  • isInterrupted() → Instance, checks specific thread, does not clear flag.
MethodTypeClears Flag?
interrupt()InstanceSets status
interrupted()StaticYes
isInterrupted()InstanceNo

Scheduling & Control

  • yield() → Hint to scheduler, thread remains RUNNABLE.
  • join() → Current thread waits for another to finish.
Memory Trick:
  • yield() = "Give chance"
  • join() = "Wait for completion"

Revision

  • Thread creation → Extend Thread / Implement Runnable.
  • Runnable preferred for flexibility.
  • start() vs run() → start() creates new thread.
  • States → NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
  • Interrupt methods → interrupt(), interrupted(), isInterrupted().
  • yield() → Scheduling hint.
  • join() → Synchronization, wait for another thread.

Lecture 3: Concurrent Programming: An Example

Introduction

  • Bridge Problem → Example for concurrency, synchronization, shared resources, and thread coordination.
  • Cars = Threads, Bridge = Shared Resource, Direction = Shared State.
  • Goal → Allow maximum concurrency while preventing opposite-direction cars from entering together.

Bridge Rules

  • Rule 1: Same direction → Allowed.
  • Rule 2: Opposite direction → Must wait.
  • Rule 3: Empty bridge → Direction can change.
  • Rule 4: Multiple same-direction cars allowed simultaneously.

Key Problems

  • No FIFO Guarantee → Java's wait()/notifyAll() does not ensure strict order.
  • Unlucky Timing → A waiting car may be delayed if another same-direction car enters before it acquires the lock.

Shared State

  • bcount (int) → Number of cars on bridge.
  • direction (boolean) → Current direction (true = North, false = South).
  • Synchronization required to avoid race conditions.

Crossing Phases

  • ENTER → Synchronized, checks direction & updates state.
  • TRAVEL → Not synchronized, simulates crossing with sleep().
  • LEAVE → Synchronized, decreases bcount, notifies when empty.

enter() Method

Guard condition:

if (carDirection != direction && bcount > 0) wait();
  • If bridge empty → direction = carDirection.
  • Update: bcount++.

wait() Usage

  • Releases lock, moves thread to waiting state.
  • Must be inside synchronized block.
  • Always recheck condition after waking → use while loop, not if.

Travel Phase

  • Use Thread.sleep() outside synchronized block.
  • Prevents blocking other same-direction cars.
  • Handle InterruptedException.

leave() Method

synchronized void leave() {
    bcount--;
    if (bcount == 0) notifyAll();
}
  • Decreases bcount.
  • NotifyAll only when bridge becomes empty → avoids unnecessary wakeups.

Synchronization Principle

  • Protect shared state (bcount, direction).
  • Do not lock entire journey.
  • Synchronize only critical sections.

Coarse vs Fine-Grained Locking

  • Coarse-Grained → One lock for entire operation, simple but low concurrency.
  • Fine-Grained → Lock only critical sections, better throughput and concurrency.

General Concurrency Lessons

  • Shared resources (databases, files, queues, memory structures) follow same principle.
  • Synchronize state transitions, allow independent work concurrently.
  • Notify only on meaningful state changes.

Linked List Analogy

  • One lock for entire list → limits concurrency.
  • Fine-grained (hand-over-hand locking) → individual node locks allow disjoint updates concurrently.

Important Points

  • Bridge = shared resource, cars = threads.
  • Only one direction at a time.
  • bcount tracks cars, direction tracks orientation.
  • Enter condition → wait if opposite direction & bcount > 0.
  • Travel → sleep outside synchronized block.
  • Leave → bcount--, notifyAll when empty.
  • Synchronize shared state only.
  • Fine-grained locking improves concurrency.

Revision Sheet

  • Cars = Threads, Bridge = Shared Resource.
  • One direction at a time, multiple same-direction cars allowed.
  • ENTER → check condition, update bcount.
  • TRAVEL → sleep outside lock.
  • LEAVE → bcount--, notifyAll if empty.
Key principle: Protect shared state + allow independent work = good concurrency design.

Lecture 4: Thread Safe Collection

Concurrency & Collections

  • Multiple threads may access the same collection simultaneously.
  • Standard collections (arrays, lists, maps) are not thread-safe.
  • Problems without synchronization:
    • Race conditions
    • Lost updates
    • Inconsistent data
    • Incorrect results

Example: Bank accounts → transfers + audit thread → inconsistent totals if read occurs mid-transaction.

Lost Update Problem

  • Classic issue: two threads overwrite each other's updates.
  • Expected result: 9 → Actual result: 8.
  • Key idea: Read → Modify → Write must be synchronized.

Locking Approaches

  • Global Locking → One lock for entire collection.
    • Simple, safe, but poor scalability.
  • Fine-Grained Locking → Separate locks for independent portions.
    • More complex, but higher concurrency and throughput.

Comparison Table

SimplicityHighLower
ConcurrencyLowHigh
ContentionHighLower

Correctness Concepts

  • Linearizability → Atomicity of individual operations.
  • Serializability → Correctness of entire transaction sequence.
  • Important: Thread-safe ≠ Transaction-safe.

Concurrent Data Structures

  • Techniques: localized locks, atomic operations, specialized algorithms.
  • Arrays → lock individual indices.
  • Linked Lists → hand-over-hand locking (lock coupling).
  • Trees → complex, may require multi-node locks during rotations.

Standard Java Concurrent Collections

  • ConcurrentHashMap → Thread-safe map, fine-grained synchronization.
  • BlockingQueue → Producer-Consumer communication.
  • ConcurrentSkipListMap → Thread-safe sorted map.

Producer-Consumer Pattern

  • Producers generate work → BlockingQueue → Consumer processes work.
  • Benefits:
    • Decoupling producers & consumers.
    • Simplified synchronization.
    • Backpressure (bounded queue prevents overload).
    • Efficient resource utilization.

Backpressure & Empty Queue

  • Queue full → Producers wait.
  • Queue empty → Consumers wait.
  • Prevents busy waiting and uncontrolled memory growth.

Architectural Principles

  • Goal = Maximum safe concurrency + Minimum unnecessary blocking.
  • Synchronize only what must be synchronized.
  • Allow independent operations to run concurrently.

Important Points

  • Collections are not thread-safe by default.
  • Global lock → simple but low concurrency.
  • Fine-grained lock → complex but high concurrency.
  • Linearizability → single operation correctness.
  • Serializability → transaction correctness.
  • Thread-safe ≠ transaction-safe.
  • Prefer java.util.concurrent classes.
  • Producer-Consumer → clean architecture with BlockingQueue.

Revision Sheet

  • Race conditions / Lost updates → Need synchronization.
  • Global Lock → Simple, low concurrency.
  • Fine-Grained Lock → Complex, high concurrency.
  • Linearizability → One operation.
  • Serializability → Whole transaction.
  • ConcurrentHashMap / BlockingQueue / ConcurrentSkipListMap → Key Java classes.
  • Producer-Consumer → Decoupling + backpressure.
Main Idea: Protect shared state + allow independent work = high-performance concurrency.
