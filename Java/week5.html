Lecture 1: Polymorphism Revisited

Polymorphism

  • Definition: One interface, many forms.
  • Same method call performs different actions depending on the object.
Animal a = new Dog();
a.sound(); // Output: Bark
  • Achieved through Dynamic Dispatch.

Inheritance-Based Polymorphism

  • Works via inheritance.
  • Dog is a subclass of Animal.
  • Dog IS-A Animal, so:
Animal a = new Dog();

Dynamic Dispatch

  • Definition: Runtime method selection based on actual object.
class Animal {
    void sound() { System.out.println("Animal Sound"); }
}
class Dog extends Animal {
    void sound() { System.out.println("Bark"); }
}
  • Dog overrides Animal.sound().

Benefits of Dynamic Dispatch

  • Avoids multiple if-else checks.
  • Cleaner, maintainable, and extensible code.

Heterogeneous Collection

  • Collection can store different subclasses of the same parent.
  • Example: List<Animal> can hold Dog, Cat, Cow.

Structural Polymorphism

  • Focuses on capabilities, not inheritance.
  • Examples:
    • Reverse: Rearrange elements.
    • Search: Use equals().
    • Sort: Use compareTo().

Equality in Java

  • Default equals() checks object identity.
  • Must override equals() for meaningful equality.

Object Class

  • Root of all Java classes.
  • Enables collections like Object[] to store mixed types.

Problems with Object

  • Type information lost.
  • Requires casting.
  • Risk of runtime errors.
  • Allows unrelated mixed data.

Generic Programming

  • Introduced to solve Object's problems.
  • Uses type parameters <T>.

Benefits of Generics

  • Type safety
  • No casting
  • Compile-time error detection
  • Homogeneous collections

Type Parameters

class Box<T> { ... }
Box<String> strBox = new Box<>();

Generic Compatibility Constraints

  • S extends T ensures type compatibility.
  • Example: Dog extends Animal.

Why Constraints are Useful

  • Prevents runtime crashes by enforcing compile-time checks.

Keywords

  • Polymorphism: One interface, many forms.
  • Inheritance-based Polymorphism: Achieved via inheritance.
  • Dynamic Dispatch: Runtime method selection.
  • Method Overriding: Child redefines parent method.
  • Heterogeneous Collection: Different subclasses together.
  • Structural Polymorphism: Based on capabilities.
  • equals(): Compares equality.
  • Object Identity: Same memory reference.
  • Object Class: Root of all classes.
  • Type Casting: Convert Object back to original type.
  • Generics: Type-safe, reusable code.
  • Type Parameter <T>: Placeholder for data type.
  • Type Safety: Prevents incorrect data types.
  • S extends T: Compatibility constraint.

2-Minute Revision

  • Polymorphism → Same method, different behavior.
  • Inheritance-based polymorphism → Parent-child relationship.
  • Dynamic dispatch → Runtime method selection.
  • Method overriding → Child redefines parent.
  • Heterogeneous collections → Store different subclasses.
  • Structural polymorphism → Based on capabilities.
  • equals() → Equality check.
  • Object class → Root of all classes.
  • Problems with Object → Type loss, casting, runtime errors.
  • Generics → Type safety, no casting, compile-time checks.
  • Constraints → Prevent runtime crashes.

Lecture 2: Generic Programming in Java

Introduction to Structural Polymorphism

  • Definition: Structural polymorphism means writing functions based on what an object can do (its capability) instead of which class it belongs to.
  • Focus is on the required operation, not the inheritance hierarchy.

Example: A sorting function doesn't care whether objects are Student, Employee, or Ticket. It only requires one capability: objects must be comparable.

Why Generics Were Introduced

Before Java Generics, programmers used the Object class for everything:

Object obj = new Ticket();

Problems with this approach:

  • No homogeneity (mixed types in collections).
  • Manual type casting required.
  • Loss of type information.
  • Errors detected only at runtime.

Generics were introduced to make Java safer, reusable, easier to write, and error-free. The biggest improvement: compile-time error detection.

Carton Analogy

Think of every object as inside a sealed carton (box). Different operations require different levels of knowledge:

  • Outside the Carton (Reverse): Rearranging elements without knowing what's inside.
    • Example: A B C D → D C B A
  • Inside the Carton (Search): Requires equality check using equals().
    • Example: Find "Apple" inside Apple Mango Banana.
  • Inside the Carton (Sort): Requires comparison using compareTo().
    • Example: 9 3 6 1 → 1 3 6 9

Type Variables <T>

  • A type variable is a placeholder for any data type.
  • Example: <T> can be Integer, String, Student, Ticket, or Date.

Mathematical Analogy: Generics work like the universal quantifier (∀). Once T is chosen, it remains fixed throughout the method or class.

Type Inference: Java automatically determines T.

Date[] arr;
reverse(arr); // Compiler infers T = Date

Generic Methods

Generic methods ensure input, internal variables, and output are of the same type.

  • Reverse Method: Needs only swapping.
  • Find Method: Requires equality. Compiler detects invalid searches at compile time.

Evolution of Type Safety

FeatureBefore GenericsAfter Generics
HomogeneityNot guaranteedGuaranteed
Type CheckingRuntimeCompile-time
CastingManual requiredNo casting
Logic VerificationRuntime errorsCompiler catches

Advanced Constraints (extends)

  • Sometimes source and target types differ.
  • Example: Dog is a subtype of Animal.
  • Constraint: <S extends T> ensures compatibility.
public <S extends T> void arrayCopy(S[] source, T[] target)

This allows safe assignments like Dog[] → Animal[].

Parameterized Classes

Generic classes use type variables in the class itself.

class LinkedList<T> { ... }
LinkedList<Ticket> list = new LinkedList<>();

Binding: When T = Ticket, every occurrence of T becomes Ticket. This ensures homogeneity and prevents inserting unrelated types.

Type Masking (Shadowing)

Correct Code:

class LinkedList<T> {
    public void insert(T data) { ... }
}

Wrong Code:

class LinkedList<T> {
    public <T> void insert(T data) { ... }
}

This redeclares <T> locally, hiding the class-level T.

Danger: allows inserting unrelated types into a homogeneous collection.

Rule:

  • Instance methods → use class T, never redeclare.
  • Static methods → must declare their own <T>.

Advantages of Generics

  • Compile-time type checking
  • No manual casting
  • Code reuse
  • Safer collections
  • Cleaner code
  • Better readability
  • Homogeneous collections
  • Fewer runtime errors

Limitations: Due to type erasure (for backward compatibility), some restrictions exist, but generics still greatly improve safety and quality.

Exam Keywords

  • Structural Polymorphism: Depends on required capabilities, not inheritance.
  • Generics: Type-safe, reusable code using type parameters.
  • Carton Analogy: Reverse = no need to look inside; Search = needs equality; Sort = needs comparison.
  • Homogeneity: Collection contains only one data type.
  • Type Variable <T>: Placeholder for any data type.
  • Type Inference: Compiler automatically determines type.
  • Arbitrary but Fixed: Once T is chosen, it remains fixed.
  • Generic Method: Method using a type parameter.
  • Parameterized Class: Generic class like LinkedList<T>.
  • Binding: Replacing T with a real type.
  • <S extends T>: Subclass-to-superclass compatibility.
  • Type Masking: Redeclaring <T> inside a generic class method.
  • Instance Method Rule: Use class T.
  • Static Method Rule: Must declare its own <T>.

2-Minute Revision

  • Structural polymorphism → capability-based, not inheritance-based.
  • Reverse → swaps positions; Search → needs equals(); Sort → needs compareTo().
  • Pre-generics → mixed collections, casting, runtime errors.
  • Generics → type variables <T>, compile-time safety.
  • Type inference → compiler auto-detects type.
  • Arbitrary but fixed → once chosen, T stays constant.
  • Generic methods → consistent input/output types.
  • <S extends T> → safe subtype-to-supertype relationships.
  • Parameterized classes → bind T to a real type.
  • Avoid type masking in instance methods; static methods must declare <T>.

Lecture 3: Java Generics and Subtyping

Introduction to Structural Polymorphism

  • Definition: Structural polymorphism is a feature of Generics that allows writing one piece of code that works with many data types, while keeping programs type-safe.
  • Instead of writing separate code for Student, Ticket, Date, etc., type variables <T> are used so the same code works for all types.

Advantages:

  • Code reusability
  • Type safety
  • Less duplicate code
  • Works with inheritance (subtyping)

Array Covariance

  • Covariance: If ETicket extends Ticket, then ETicket[] is considered a subtype of Ticket[].
ETicket[] elecArr = new ETicket[10];
Ticket[] ticketArr = elecArr;

Problem:

ticketArr[5] = new Ticket(); // Runtime error
  • Causes ArrayStoreException because the actual array is ETicket[].

Limitation: Compiler cannot detect aliasing problems; errors appear only at runtime. This motivated the introduction of Generics.

Generics Use Invariance

  • Invariance: Generics do not allow subtype-to-supertype assignments.
LinkedList<String> list = new LinkedList<>();
LinkedList<Object> objList = list; // Not allowed

Reason: Prevents unsafe assignments and runtime crashes.

Advantages of Invariance

  • Safer code
  • No aliasing problems
  • Better type checking
  • No ArrayStoreException

Generic Functions

  • Generic functions use type parameters.
public <T> void print(T[] arr)
  • Works for Integer, String, Ticket, Student.

Type Quantifier <T>: Means "for every type T."

When <T> is not needed:

  • If the function never uses T internally (e.g., printing elements). In such cases, wildcards ? are used.

Wildcards (?)

  • Definition: Represents some unknown type.
  • Example: LinkedList<?>

Difference Between <T> and ?

Feature<T>?
Has a nameYesNo
ScopeThroughout methodOnly where needed
UsageArguments, return type, variablesMainly parameters
ConsistencyMaintains type consistencyRepresents unknown type

Restriction: Cannot add elements to LinkedList<?>. Safe only for reading.

Rule: Wildcards → Reading; <T> → Writing and type consistency.

Bounded Wildcards

  • Upper Bound: ? extends T → Unknown subtype of T.
    • Example: List<? extends Shape> includes Shape, Ellipse, Circle. Used for reading.
  • Lower Bound: ? super T → Unknown supertype of T.
    • Example: List<? super Dog> includes Dog, Animal, Object. Used for writing.

Memory Trick: extends → Read (Producer); super → Write (Consumer)

Transitivity in Inheritance

  • Inheritance is transitive: Circle extends Ellipse, Ellipse extends Shape → Circle is also a subtype of Shape.
  • Wildcards respect transitivity: ? extends Shape includes Shape, Ellipse, Circle.

Goal of Generics

  • Detect errors during compilation instead of runtime.
  • Compiler understands inheritance, wildcards, type variables, and relationships to ensure safer programs.

Keywords

  • Structural Polymorphism: Generic code based on capabilities, not classes.
  • Covariance: S[] is subtype of T[] if S extends T.
  • ArrayStoreException: Runtime error from wrong type in covariant array.
  • Aliasing: Two references pointing to the same object.
  • Invariance: LinkedList<String> ≠ LinkedList<Object>.
  • Generic Function: Function using <T>.
  • Type Quantifier <T>: "For every type T."
  • Wildcard ?: Represents unknown type.
  • Upper Bound ? extends T: Subtype restriction (read).
  • Lower Bound ? super T: Supertype restriction (write).
  • Transitivity: Subclass inherits all superclasses.

Comparison Table

FeatureArraysGenerics
Type RelationshipCovariantInvariant
Type CheckingRuntimeCompile-time
SafetyLess safeMore safe
Common ErrorArrayStoreExceptionCompile-time error
FlexibilityRiskySafe

PECS Rule (Producer Extends, Consumer Super)

  • Producer Extends: ? extends T → Use when collection produces/returns data (read).
  • Consumer Super: ? super T → Use when collection consumes/accepts data (write).

2-Minute Revision

  • Structural polymorphism → capability-based generic code.
  • Arrays are covariant → may cause ArrayStoreException.
  • Generics are invariant → safer, compile-time checks.
  • Generic functions use <T> for type safety.
  • Wildcards ? → unknown type, mainly for reading.
  • ? extends T → read/producer.
  • ? super T → write/consumer.
  • Inheritance is transitive → wildcards include indirect subclasses.
  • Generics move type errors from runtime to compile time.

Lecture 4: Reflection

What is Reflection?

  • Definition: Reflection is a special feature in Java that allows a program to inspect and manipulate itself at runtime.
  • Normally, Java programs decide everything at compile time. Reflection enables decisions at runtime.
  • In simple terms: A program can look at itself and work with its own classes, methods, constructors, and fields.

Uses of Reflection

  • Inspect objects at runtime
  • Call methods dynamically
  • Create objects during execution
  • Build debugging/testing tools

Two Pillars of Reflection

  • Introspection (Observation): Examines program structure. Examples: class type, methods, fields, constructors. Only reads information.
  • Intercession (Modification): Changes program behavior dynamically. Examples: create objects, call methods, modify fields.
IntrospectionIntercession
ObserveModify
Read infoPerform ops
InspectionIntervention

Why instanceof is Not Enough

  • instanceof works only when the type is known at compile time.
  • Problem: If classes are unknown (Object o1, o2), instanceof cannot help.
  • Another limitation: instanceof does not work properly with generics due to type erasure.
  • Reflection solves these issues.

getClass()

  • Every object has getClass() (inherited from Object).
Student s = new Student();
Class c = s.getClass();
  • Returns a Class object containing metadata (methods, fields, constructors, modifiers).

Reification: Abstract class type becomes a real Class object.

Note: Only one Class object exists per loaded class in JVM.

Comparison:

o1.getClass() == o2.getClass()

True if both belong to the same class.

Structural Decomposition

Reflection breaks a class into parts:

  • Constructors → Represented by Constructor class
  • Methods → Represented by Method class
  • Fields → Represented by Field class

API Methods

  • getConstructors() → Returns constructors
  • getMethods() → Returns public methods
  • getFields() → Returns public fields

Method Signature: Depends only on parameter types and order, not names.

Operational Intercession

Reflection performs dynamic operations:

  • Dynamic Object Creation:
Class c = Class.forName("Student");
Object obj = c.newInstance();
  • Dynamic Method Invocation:
method.invoke(obj, args);
  • Field Manipulation: Read or change field values dynamically.

Reflection and Access Control

  • Standard Reflection: getMethods() returns only public methods.
  • Declared Methods: getDeclaredMethods() and getDeclaredFields() return all members (including private).

Uses: Debugging, testing, frameworks, IDEs.

Security: JVM security policies can restrict reflective access to private members.

Real-World Uses

Reflection is widely used in:

  • IDEs
  • Testing frameworks
  • Dependency injection
  • Serialization
  • Debuggers
  • ORM frameworks

Example: BlueJ IDE uses reflection to let students create objects, call methods, and view variables without writing main().

Limitation: Reflection cannot create brand-new Java classes at runtime (unlike Python or Smalltalk).

Importance of Reflection

Reflection is essential for:

  • Dynamic programming
  • Framework development
  • Debugging and testing
  • IDE development
  • Runtime inspection and object creation

Keywords

  • Reflection: Inspect and manipulate at runtime.
  • Introspection: Observation of program structure.
  • Intercession: Modification of behavior dynamically.
  • Runtime: Execution phase.
  • instanceof: Type check when known.
  • getClass(): Returns Class object.
  • Reification: Abstract type → real Class object.
  • Class Object: Stores metadata.
  • Method Signature: Defined by parameter types/order.
  • getConstructors(): Returns constructors.
  • getMethods(): Returns public methods.
  • getFields(): Returns public fields.
  • getDeclaredMethods()/getDeclaredFields(): Return all members.
  • Class.forName(): Load class dynamically.
  • newInstance(): Create object dynamically.
  • Method.invoke(): Call method dynamically.
  • Encapsulation: Restricts access.
  • JVM Security Policy: Restricts reflection.

2-Minute Revision

  • Reflection → inspect and manipulate at runtime.
  • Two pillars: Introspection (observe) and Intercession (modify).
  • instanceof insufficient for unknown types → use Reflection.
  • getClass() returns Class object with metadata.
  • One Class object per loaded class.
  • Reflection inspects constructors, methods, fields.
  • Method signature depends on parameter types/order.
  • Class.forName() loads class, newInstance() creates object.
  • Method.invoke() executes methods dynamically.
  • Declared methods/fields expose private members.
  • Reflection powers IDEs, testing frameworks, debuggers, and dependency injection.
  • Cannot create brand-new classes at runtime.

Lecture 5: Java Generics at Run Time

Type Erasure

  • Definition: Type Erasure is the technique Java uses to implement Generics.
  • During compilation, the compiler checks type safety. After checking, it removes all generic type information before creating bytecode.
  • Generics exist only at compile time. At runtime, the JVM does not know the actual generic type.

Reason: Introduced in Java 5 to maintain backward compatibility with millions of existing programs. Allows old code and new generic code to coexist.

Compile Time vs Runtime

  • Compile Time: Compiler distinguishes List<String>, List<Integer>, List<Employee>.
  • Runtime: All become simply List.

How Type Erasure Works

Unbounded Generic:

class Box<T>
// After erasure →
class Box<Object>

Bounded Generic:

class Box<T extends Shape>
// After erasure →
class Box<Shape>

Memory Trick: <T> → erased to Object; <T extends Shape> → erased to Shape

Advantages

  • Keeps JVM simple
  • Only one class file generated
  • Saves memory
  • Supports old programs

Limitations: JVM cannot distinguish between List<Integer> and List<String> at runtime.

Runtime Limitations

  • Generic information disappears at runtime.

instanceof Limitation:

if(list instanceof LinkedList<String>) // Illegal

Reflection Problem:

  • LinkedList<Employee> and LinkedList<Date> are different at compile time.
  • At runtime, both appear as LinkedList.class.

Method Overloading & Type Erasure

  • Normal overloading works (print(int), print(String)).

Problem with generics:

print(List<String>)
print(List<Date>)
// After erasure → both become
print(List<Object>)

Signature Collision: Two methods become identical after erasure → compiler error.

Method Signature Depends On: Method name, parameter types, parameter order (Not parameter names)

Arrays and Generics

  • Arrays: Covariant → Dog[] can be treated as Animal[].
  • Generics: Invariant → List<Dog> is not List<Animal>.

Generic Arrays Restriction

  • Declaration allowed: T[] arr;
  • Instantiation not allowed: new T[100] → compiler error.

Workaround:

(T[]) new Object[100]

Programmer takes responsibility for type safety.

Primitive Types and Generics

  • Generics work only with objects, not primitives.
  • Example: List<int> → illegal.

Wrapper Classes

Boxing/Unboxing

  • Boxing: primitive → wrapper object.
  • Unboxing: wrapper → primitive.
  • Auto-boxing/unboxing introduced in Java 5.

Wrapper Objects: Immutable. Changing value creates a new object.

Hidden Cost: Extra objects → more memory → slight performance overhead.

Advantages of Generics

  • Compile-time type safety
  • Reusable code
  • No unnecessary casting
  • Cleaner, more readable code
  • Fewer runtime errors

Limitations of Generics

  • Uses type erasure
  • JVM cannot remember generic types
  • Cannot overload methods differing only in generic parameters
  • Cannot use generics with instanceof
  • Cannot create generic arrays directly
  • Primitive types cannot be used directly

Keywords

  • Type Erasure: Compiler removes generic type info before bytecode.
  • Backward Compatibility: Old and new code coexist.
  • Compile-time Type Safety: Checked during compilation.
  • Runtime Illusion: Generic info erased at runtime.
  • Unbounded Generic <T>: Erased to Object.
  • Bounded Generic <T extends Shape>: Erased to Shape.
  • Signature Collision: Overloaded methods identical after erasure.
  • Covariant Arrays: Dog[] → Animal[].
  • Invariant Generics: List<Dog> ≠ List<Animal>.
  • Generic Array Restriction: new T[] illegal.
  • Wrapper Class: Object version of primitive.
  • Boxing/Unboxing: Conversion between primitive and wrapper.
  • Auto-boxing/Auto-unboxing: Automatic conversion.
  • Immutable Wrapper: Wrapper objects cannot be modified.

  • Ensures backward compatibility.
