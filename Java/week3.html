From Objects to Polymorphism

01 The Philosophy of OO Programming

A shift in programming philosophy

Procedural programming (1960s–70s) follows Niklaus Wirth's formula: Algorithms + Data Structures = Programs. It focuses first on algorithms and functions, dividing large programs into smaller procedures, with data often shared globally.

Object-oriented programming shifts the focus from functions to data — identify objects first (Customer, Bank Account, Order), where each object combines data and behavior.

Managing complexity with OOP

procedural
  • 2,000 global functions — hard to manage
oop
  • 100 classes × 20 methods — organized, modular

Classes divide the system into manageable units, so errors are localized to a handful of object methods rather than spread across thousands of functions.

Key concepts of OO design

  • Nouns = objects — Item, Order, Payment, Address
  • Verbs = methods — Add Item, Ship Order, Cancel Order

Core properties of objects

  • State — data stored inside an object (e.g. an Order's state: Empty, In Cart, Shipped)
  • Behavior — methods that manipulate state (Add Item, Cancel Order)
  • Encapsulation — hide internal data, access only via methods, for security and reliability
  • Identity — every object is unique, even two orders with identical items

Relationships between classes

Dependence & coupling — an Order depends on an Account for payment; coupling is the degree of that dependency, and the goal is to minimize it.

Composition — objects contain other objects (an Order contains Items).

Inheritance — creating a new class from an existing one (ExpressOrder inherits Order) for code reuse and easier extension.

Languages built around OOP — Java, C++, Python.

Conclusion

  • OOP focuses on objects and data, helping manage large, complex systems through better organization, easier debugging, reusability, and security via encapsulation.

02 Subclasses and Inheritance

Introduction to inheritance

A new class (subclass/child) is created from an existing class (superclass/parent). This is an "is-a" relationship — a subclass is a specialized version of the superclass. Example: a Manager is-an Employee, so Manager inherits Employee's features and adds new ones.

class Manager extends Employee

Benefit: code reusability — the subclass inherits fields and methods, avoiding duplication.

The this keyword

this refers to the current object — this.salary is the salary of the current object.

java
  • this is implicit, e.g. salary = this.salary
python
  • An explicit self parameter is required

Privacy and encapsulation in subclasses

Private variables of the parent class cannot be accessed directly by a subclass:

private double salary;
// subclass cannot do: salary = 50000;
// must use a public method like setSalary()

This matters because encapsulation protects data, separates concerns so the subclass remains unaffected by internal changes in the parent, and improves security, reliability, and maintainability.

The super keyword and constructors

super calls the parent constructor — needed because private variables must be initialized through it:

super(name, salary);

A subclass constructor has the special privilege of invoking the parent constructor via super.

Subtyping and substitutability

A subclass object can be used wherever the parent type is expected (upcasting):

Employee e = new Manager();   // valid

This is a one-way relationship — the reverse isn't allowed:

Manager m = new Employee();   // invalid

Employee lacks Manager-specific features, like secretary or bonus methods.

Arrays and polymorphism

Employee[] staff = new Employee[10];

An array of Employee can dynamically store subtype objects like Manager, with a runtime check ensuring compatibility and safe storage.

Method overriding (preview)

A subclass redefines a method inherited from its parent to customize behavior — e.g. bonus calculation: Employee → salary * 0.1, Manager → salary * 0.2.

Conclusion

  • Inheritance enables code reusability, better organization, extension of existing classes, and reduced duplication.
  • Key concepts: extends, this, super, encapsulation, upcasting, method overriding.

03 Dynamic Dispatch and Polymorphism

Inheritance and method overriding

class Manager extends Employee

Employee is the parent/superclass, Manager the child/subclass — the subclass inherits instance variables and methods, but private fields still require getters/setters to support encapsulation.

Method overriding lets a subclass redefine an inherited method — e.g. a different bonus calculation for Employee vs. Manager — marked with the @Override annotation.

The super keyword calls a parent's constructor or method, letting a subclass reuse and extend parent logic ("piggybacking"):

super.bonus();

Static type vs. dynamic type

Static type is the declared type at compile time:

Employee e;   // static type = Employee

Dynamic type is the actual object at runtime:

e = new Manager();   // dynamic type = Manager

Upcasting is valid:

Employee e = new Manager();   // valid

But the static type restricts which methods are accessible — e.g. e.setSecretary(); is invalid if that method is only defined on Manager.

Dynamic dispatch (late binding)

The runtime decides which overridden method to execute, based on the actual object type rather than the variable's declared type:

Employee e = new Manager();
e.bonus();   // calls Manager's bonus()

All methods in Java are dynamically dispatched by default, enabling runtime polymorphism across heterogeneous collections — e.g. Employee[] staff holding both Employees and Managers.

Three forms of polymorphism

"Many forms" — functions behave differently depending on context.

a) Runtime / inheritance polymorphism

Based on inheritance and dynamic dispatch; occurs at runtime, depending on the actual object type.

b) Overloading (static polymorphism)

Same method name, different parameters; resolved at compile time, based on argument types/number.

c) Structural polymorphism (generics)

Functions that work for many types based on shared capabilities — e.g. a sorting function that works on integers, strings, or objects, as long as they're comparable. Widely used in generic programming and the collections framework.

Type casting and reflection

Object casting:

Manager m = (Manager) e;

Primitive casting:

int x = (int) 5.7;   // x = 5

Wrong casting causes runtime errors, e.g. Manager m = (Manager) new Employee(); is invalid. The instanceof predicate checks type before casting:

if (e instanceof Manager)

Reflection (introspection) lets a program examine its own structure at runtime — inspecting object types, methods, and classes.

Conclusion

  • Key concepts: inheritance, method overriding, super, static vs. dynamic types, dynamic dispatch, polymorphism, type casting, reflection.

04 The Java Class Hierarchy

Multiple inheritance and Java's design choice

Multiple inheritance means a class inherits from more than one parent. Java does not support this for classes, unlike C++, to avoid ambiguity — if two parents both define show(), inheritance becomes unclear. Inheriting multiple parents also brings in their whole hierarchies (the transitivity problem), adding complexity and potential conflicts. Single inheritance is a bottleneck when features are needed from multiple sources.

The universal Object class

Every class has exactly one parent, forming a single tree structure rooted at Object:

class Employee   // actually means: class Employee extends Object

All classes — Employee, Manager, String, Date — ultimately extend Object.

Important methods inherited from Object

toString() converts an object into a string representation — System.out.println(myObject) internally calls myObject.toString(), useful for debugging, printing, displaying info.

equals(Object o) — by default, checks reference equality (same memory location); a == b is true only if both refer to the same object.

Polymorphism and genericity

A higher-level type can store a lower-level object:

Object obj = new Employee();   // valid

This enables generic programming:

void print(Object o)   // accepts any object

Benefit: reusability, flexibility, generic coding.

Overriding methods and signature matching

Method overriding requires the signature — name and parameter types — to match exactly:

boolean equals(Date d)   // does NOT override equals(Object o)

The correct strategy:

boolean equals(Object o) {
    if (o instanceof Date) {
        Date d = (Date) o;
        // compare day, month, year
    }
}

Dynamic dispatch and nearest match

At runtime, Java checks the actual object type, searches upward through the hierarchy, and finds the nearest compatible method — the most specific one wins:

Object o = new Employee();
o.toString();   // calls Employee's toString() if overridden

The static type (declared variable type) determines accessibility; the dynamic type (actual object) determines which overridden method executes.

Conclusion

  • Key concepts: multiple inheritance, the Object class, toString() and equals(), polymorphism, generic programming, method overriding, dynamic dispatch, signature matching.

05 Subtyping vs Inheritance

Subtyping: capability and compatibility

Subtyping focuses on what an object can do — its interface/capabilities — not how it's implemented. Type B is a subtype of A if B supports all of A's capabilities and may add extra features.

Substitution principle — if B is a subtype of A, any code expecting A can safely use B:

Employee e = new Manager();   // valid — Manager can do everything Employee can, plus more

A subtype may override or change implementation, but it cannot remove or forbid parent functions. Focus: interfaces, capabilities, compatibility.

Inheritance: code and implementation reuse

Inheritance focuses on reusing existing code — Type B inherits from A if B uses code already written in A, avoiding duplication:

super.bonus();   // reuse Employee's bonus
// Manager may extend it: super.bonus() * 2

Focus: implementation, internal structure, reusability.

Conflict between subtyping and inheritance

Example structures — Queue (insert rear, delete front), Stack (insert front, delete front), Deque (insert/delete both ends).

subtyping view
  • Deque supports all Queue + Stack operations, so Deque is a subtype of both
inheritance view
  • Deque can't easily reuse Stack/Queue's limited code
  • The reverse works — Stack/Queue can inherit from Deque, hiding the extra functions

So subtyping says Deque → subtype of Stack/Queue, while inheritance runs the other way — Stack/Queue inherit from Deque. Subtyping ≠ inheritance.

Comparison

FeatureSubtypingInheritance
FocusInterface / capabilitiesImplementation / code reuse
Main ideaWhat it doesHow it is built
PurposeCompatibilityReusability
CheckingCompile-time & runtime compatibilityReuse parent functions

When both concepts match

Manager reuses Employee's code (inheritance), and Manager can perform Employee's tasks (subtyping) — so Manager is both a subtype and an inherited class.

Conclusion

  • Subtyping asks: can this object be used here? Inheritance asks: can this code help build another class?
  • Though often used together in Java, C++, and Python, subtyping and inheritance are theoretically separate concepts.

06 Java Modifiers

Access modifiers: public and private

Encapsulation hides internal object data, allows controlled access via methods, and protects state and security.

public — accessible from outside the class, commonly used for methods/interfaces:

public void display()

private — accessible only inside the same class, commonly used for instance variables:

private int salary;

Benefits of private variables: data protection, better control, prevents invalid changes, maintains consistency.

Accessor and mutator methods

Accessor (getter) — retrieves object data, read-only, e.g. getSalary(). Mutator (setter) — updates object data while maintaining a valid state, e.g. setSalary().

Design note — avoid separate setters like setDay(), setMonth(), setYear(), which risk invalid dates. Better: setDate(day, month, year), validating all values together.

Private methods

Internal helper functions — e.g. extendStack() in a stack implementation, resizing an array internally without the user's awareness. Benefit: improves abstraction and simplicity.

The static modifier

static means belonging to the class, not to individual objects.

Static methods can be used without creating an object:

public static void main(String[] args)
Math.sqrt()

Static variables are shared among all objects — only one copy exists:

// public static constants:
Math.PI, Integer.MAX_VALUE

// private static counters:
private static int lastOrderId;
Concurrency warning — multiple users updating static variables simultaneously risk duplicate IDs — related to multithreading.

The final modifier

Final variables are constants — cannot change once assigned:

final int MAX = 100;

Final methods prevent overriding in subclasses:

final void display()

Benefit: protects important logic and controls subclass behavior.

Summary of modifier combinations

Modifier combinationPurpose
Private instance variableEncapsulation and data hiding
public static finalGlobal constants

Conclusion

  • Modifiers help developers protect data, reuse code safely, share information efficiently, and prevent accidental changes.
  • Key concepts: public, private, static, final, encapsulation, getters/setters, private helper methods, constants, concurrency.
